# FEAT-3561: ll-next core with deterministic cross-verb recommendations

## Summary

Build the stateless, advisory `ll-next` CLI: two candidate generators (`implement-issue`, `refine-issue`), deterministic per-verb scoring on FEAT-3681's scorer, gates and coverage, a fixed round-robin cross-type fill, and a generated JSON Schema, then record the walking-skeleton go/pause checkpoint. This is part (a) of EPIC-3710 after an Opus pre-implementation review (2026-10-03) split the original nine-verb scope and the 2026-10-07 review split the loop/blocker generators out so the checkpoint precedes them. It writes **no** history events, runs **no** git subprocess and bumps **no** history DB schema version; the new output contract has its own version below. `resolve-blocker`/`run-loop` are FEAT-3769 (blocked by this issue's checkpoint); events/explicit acceptance are FEAT-3711; pressure is deferred as FEAT-3722; the backtest FEAT-3712 was cancelled after a source-audit no-go; `capture-issues`/`run-sprint` are FEAT-3713; the finding-backed verbs are deferred as FEAT-3714.

## Current Behavior

`ll-issues next-issue`/`next-issues` rank implementation targets, `ll-issues next-action` selects the first refinement step across the active backlog, and `ll-loop next-loop` scores loop runs. No command compares action types. `next-action` has no per-issue target argument; the arena needs a pure per-issue adapter rather than calling that CLI for every candidate.

## Expected Behavior

`ll-next` emits up to N recommendations with an action type, target, copyable invocation/instruction, per-axis evidence, within-type utility, coverage, bucket rank and selection reason. It is **advisory only**; `--execute` is deferred until each verb has a typed, safe dispatcher. All four existing `next-*` CLIs keep their behavior. Missing data, unavailable goals and missing gates stay explicit rather than becoming guessed scores or negative outcomes. The command reads project files only: no `history.db` access, no git subprocess, no writes. (Git evidence enters with FEAT-3713's scan-activity loader, which owns the arena Git read policy.)

## Motivation

A user deciding what to do next needs a legible choice across implementation, refinement, blockers and loops. Shipping the deterministic, stateless core first keeps the release inspectable, avoids the schema-bump and acceptance-attribution risk, and lets FEAT-3769/3721/3711/3713 build on a stable candidate/score contract. The core is deliberately the smallest slice that can answer "is the arena useful?" (implement + refine + explain); loop-specific and root-blocker work waits for that decision.

## Proposed Solution

### Action taxonomy and candidate sources

Each generator specifies its target and a copyable action; it yields no candidate when its source is absent and never invents required arguments. Candidate identity is `(action_type, target_key)`, where `target_key` is namespaced (`issue:FEAT-123`; follow-ups add `loop:NAME` (FEAT-3769), `sprint:NAME` and `scan:SCOPE_HASH` (FEAT-3713)). `target` remains the readable issue ID/name. A display command is copyable text, **not** a shell string executed by `ll-next`. Store the exact intended operation in `action_key` (e.g. `format-issue`, `confidence-check`, or `manage-issue:implement`) for subsequent acceptance attribution.

Keep target deduplication separate from invocation matching. Preserve a typed action specification (slash arguments or shell argv, plus `working_directory`) and an `action_fingerprint` from canonical semantic arguments, including each registered variant's resolved inputs and definition provenance (the loop variant's input/context, effective definition source and SHA-256 content digest belong to FEAT-3769). Canonicalize keyed context in sorted key order while retaining meaningful positional/list argument order. Exclude display quoting, ephemeral run IDs and timestamps from that fingerprint. Define one pure action grammar/parser/canonicalization module here, with render/parse round-trip fixtures for declared slash argument syntax and shell argv; FEAT-3711 preserves this identity. The cancelled FEAT-3712 would reuse it for label parsing if revisited, but requires no additional core work. Automatic invocation matching belongs to deferred FEAT-3722 and requires evidence of all semantic arguments; running the same action with different or unrecorded inputs is not exact acceptance. No new execution telemetry is required by this core.

Fingerprint a registered semantic projection of the action specification rather than every serialized assessment field. Source/scope identity is supplied by the injected snapshot; parsing a displayed command does not recover the historical definition bytes or ambient config and must perform no hidden I/O. Mutable assessment provenance can accompany the immutable offer without becoming fingerprint material. FEAT-3769 (loop) and FEAT-3713 (sprint/scan) extend this seam with their definition/scope identity; assessed member-status snapshots remain provenance. Core render/parse fixtures pin literal command arguments for the core slash variants, while each consuming child owns fixtures for its new action variant.

Pin the serialized `action_spec` as a **tagged union**: every spec carries a required string `variant` discriminator naming its registered variant (the core registers the slash-command variant used by `implement-issue`/`refine-issue`; FEAT-3769 adds `loop`; FEAT-3713 adds the sprint and scan variants), the output Schema models one `oneOf` branch per variant, and the registry owns the discriminator names. FEAT-3711 freezes persisted discriminators and field meanings, so name them once here rather than letting a child invent them after offers are stored. Fingerprint material never contains absolute filesystem paths: use project-root-relative paths (or a variant-defined `builtin:` form) and exclude `working_directory`; the absolute canonical root appears only as `working_directory`/provenance, and project scope is carried by FEAT-3711's `project_key`. A fingerprint therefore does not change when a checkout moves.

Variant-specific identity (the loop definition's limited top-level-bytes fingerprint scope, same-buffer capture, resolution order and logical-name history join) is owned by FEAT-3769, which registers the `loop` variant; this slice contains no loop loading, resolution or history code.

Resolve the project root once at the CLI boundary using the existing `paths.find_project_root` lookup before constructing config/state; with no configured root, return exit 2 with a concise diagnostic and no initialization. Root/subdirectory invocations must see the same project/config/sources, while a nested repository must not inherit an outer project's root. Include `project_root` in the envelope and the canonical root as every action's `working_directory`. Human output states that copied actions run from that directory: existing `ll-loop`/`ll-sprint` commands do not uniformly resolve an ancestor project from cwd. Do not invent a shared project-root flag or change those executors in this issue.

| Verb | Candidate source / required action |
|---|---|
| `implement-issue` | Ready, unblocked leaf issue; emit all required `/ll:manage-issue TYPE ACTION ID` arguments (`BUG` → `bug fix`, `FEAT` → `feature implement`, `ENH` → `enhancement improve`). |
| `refine-issue` | Leaf issue needing formatting, verification, scoring or further refinement; reuse the existing ordered checks through a pure per-issue adapter. Missing readiness scores lead to `confidence-check`, never implementation. Apply the arena's outcome-waiver policy to the score comparison so a valid waived outcome does not cause endless refinement. Record exhausted refinement caps as a diagnostic; do not silently repeat a capped step. |

`generic` is not a verb; work outside the taxonomy can be captured as an issue. `resolve-blocker` and `run-loop` are FEAT-3769 (blocked by this issue's recorded checkpoint decision); `pay-tech-debt`, `update-docs` and `meta` are deferred (FEAT-3714); `capture-issues` and `run-sprint` are FEAT-3713.

Weights are initial defaults pinned by fixtures and overridable only through keyed `next` config (FEAT-3681 owns the config foundation; this issue adds consumed per-verb entries). Each verb's default weights **sum to 1.0** (the geometric aggregate still renormalizes present weights when an axis is missing). `—` means inapplicable.

| Axis (source) | implement-issue | refine-issue |
|---|---|---|
| priority (canonical filename, then frontmatter) | 0.30 | 0.30 |
| confidence / outcome (frontmatter scores) | 0.30 | — |
| readiness-gap (frontmatter scores vs `commands.confidence_gate`) | — | 0.30 |
| leverage / fan-out (dependency graph) | 0.20 | 0.15 |
| effort, inverse (Impact-section `Effort` field, strict map) | 0.10 | — |
| staleness (capture date) | — | 0.15 |
| momentum (Session Log timestamps in the issue file) | 0.10 | 0.10 |

FEAT-3769 adds the `resolve-blocker` (0.25 priority / 0.50 leverage / 0.15 effort / 0.05 staleness / 0.05 momentum) and `run-loop` (0.50 frequency / 0.30 recency / 0.20 success) columns; the registry and keyed config are extended in place.

**No goal-alignment axis in v1.** A repo scan (2026-10-03) found `next_goal_alignment` in 0 of 3622 issues and a prose `.ll/ll-goals.md` has no parser, so the axis would be missing for every candidate. Do not add the `next_goal_alignment` frontmatter field; revisit when a goals/EPIC-map syntax and parser exist. The decision-rule compliance gate and the decisions-based historical-signal axis are **out of scope**: decision rules carry only issue-scoped structure today, so compliance cannot be evaluated deterministically. Revisit once rules have machine-evaluable scope.

### Snapshot and axis adapters

Capture one timezone-aware UTC `as_of` and load project state once. `ProjectState` contains parsed issue content/frontmatter, the full dependency graph, effective merged config, captured formatting policy and source diagnostics; FEAT-3769 adds validated loop definitions and filesystem loop history, and FEAT-3713 adds sprint, scan-scope and scoped-commit evidence. Generators/scorers accept this state without reading the clock, cwd, live files or database themselves. This seam also supports injected/historical fixtures without implementing the cancelled backtest. Avoid helpers such as the current autodev resolver that reload cwd/config or `is_formatted(path)` unless adapted to the injected content and policy.

Formatting depends on more than issue bytes: `is_formatted` loads per-type section definitions and `_gate_program_design` reads `.ll/program-design-cutover.json`; the default template loader can also consult the environment. Capture the existing resolved section requirements and cutover state (including absence) once at collection, and pass that evidence to the pure refinement adapter. Preserve the existing format-log shortcut, Program Design grandfathering/opt-out semantics and legacy `next-action` template resolution (bundled templates or the existing `CLAUDE_PLUGIN_ROOT` override); do not silently introduce a different resolution order or full design grading. Captured policy and its diagnostics are assessment provenance, not action-fingerprint material. A fixed-state fixture changes/removes live templates and the cutover stamp after capture and proves that format eligibility, the recommended refinement step and explain evidence do not change. A local probe with identical issue bytes/section definitions changed `is_formatted` from true to false merely by adding the cutover stamp; content-only adaptation would not satisfy the snapshot contract.

The deterministic contract is over the captured/injected source buffers and evidence, including diagnostics and coverage. Live collection is not an atomic filesystem/git snapshot; later children add bounded collectors whose wall-clock budgets can vary availability even with the same `as_of`. Fixed-clock determinism fixtures supply the same captured state, rather than claiming repeated live reads always yield identical evidence. Pure scoring and selection remain deterministic for that state.

This slice runs **no git subprocess**: the core performs zero Git calls and its generators, adapters and collectors never invoke `git`. The arena Git read policy (enforcing global `--no-lazy-fetch`, disabled external diff/textconv/signature helpers, `GIT_OPTIONAL_LOCKS=0`, promisor-safe unavailability) is defined by FEAT-3713, the first and only v1 git consumer. Staleness uses recorded dates only: a repo probe (2026-10-07) found every one of the 68 active open/blocked issues carries `captured_at` or `discovered_date`, so a git-introduction-time fallback would never fire on live data while dragging in a partial-clone/version-support surface. If a later slice needs git-derived dates it extends FEAT-3713's collector rather than adding a second policy.

Build an ID-to-source-paths inventory across all statuses in configured category directories and existing `config.legacy_issue_dirs()` before selecting targets or deriving terminal IDs; read each source file once. Do not obtain this inventory from the active-only default of `find_issues`. The shared `find_issues` loader can return duplicate IDs, and `DependencyGraph.from_issues` silently overwrites its ID-keyed nodes; neither establishes unique identity. An ID present in multiple files is ambiguous even if their metadata agrees. Retain every path in a deterministic diagnostic, apply `fail(ambiguous_issue_id)` to actions targeting that ID, and leave prerequisites referring to it unresolved; an active/terminal collision must never satisfy an edge. Preserve potential one-sided `blocks` declarations from every conflicting source for this check. Do not choose a file by enumeration order, newest mtime, priority or terminal status. Fan-out requiring traversal through an ambiguous node stays missing unless unambiguous evidence already proves curve saturation; never trust the overwritten node as exact reachability. Unaffected targets remain eligible. Sprint members and modeled issue-reference inputs use this same inventory; deduplication after generation cannot repair ambiguous source identity. Keep the shared parser's filename-derived ID authority rather than treating frontmatter `id` as an additional alias, and do not change legacy loaders/executors in this slice.

Unique full filename identity also needs **numeric-source uniqueness** before emitting an issue action. `resolve_issue_path` gathers numeric-ID matches and prefers matching frontmatter identity before filename type; `manage-issue` and refinement commands use `ll-issues path`, and sprint loading uses the same resolver. Distinct full IDs sharing a number can therefore dispatch a different source without triggering the full-ID check. Group the same captured all-status source inventory by the anchored filename number **as a string**, retaining its exact digit spelling. More than one parsed source with that number makes every affected issue action fail `ambiguous_issue_id`, with the shared number and all paths in explain. This deliberately rejects even a collision the current resolver could disambiguate; `normalize-issues` already treats shared cross-type numbers as a defect. Preserve filename digits in emitted operands; do not normalize `001` to `1`. Apply the invariant to issue refinement/root-blocker actions, FEAT-3713's declared members and modeled inputs that actually use this resolver; it does not prove parity for a loop's arbitrary custom lookup (FEAT-3769 inputs). Graph/prerequisite identities remain unique full filename IDs, with the preceding duplicate-full-ID rule unchanged and no frontmatter aliases. In tests, compare every emitted operand's real resolver result with its assessed source, including unique-number/stale-frontmatter fixtures. Add no production resolver replica, per-target CLI/file rereads or executor changes. This proves source parity over the captured state, not immunity to later file changes.

That guarantee requires the assessed action source itself to pass `parse_issue_filename`, with its parsed type/number agreeing with the emitted full ID. The shared issue parser can infer an ID from an unnormalized filename such as `P3-001-old.md`; a canonical `P3-BUG-001-new.md` then wins runtime anchoring even though the canonical-number group contains just one source. Retain unnormalized sources as graph/explain evidence, but exclude their runtime-resolved actions with `unsupported_issue_filename` and a normalization diagnostic. Apply this source-validity check to every declared sprint member before filtering; canonical filenames in legacy directories remain supported. Do not require the legacy resolver to emulate the arena's inferred identity.

Resolve lifecycle status once from the captured source, retaining field presence and provenance. A present frontmatter status, after the shared parser's existing synonym canonicalization, is authoritative over `completed_at`: an explicitly reopened `open` issue with a leftover completion marker stays nonterminal and cannot satisfy a prerequisite. Diagnose the conflicting marker without rewriting it. Do not blindly use `IssueInfo.status`, which currently turns even explicit `open` plus any truthy `completed_at` into `done`. When status is absent, retain the existing legacy completion-marker fallback with `legacy_completed_at` provenance; absence without that marker defaults to `open`. Invalid explicit status remains ineligible and unresolved. Graph construction, terminal-edge resolution, action gates and FEAT-3713 member filtering all consume this same resolved value; shared parser/legacy behavior remains unchanged.

Resolve priority with the shared `issue_parser.resolve_priority` authority: a valid canonical filename prefix wins over frontmatter, then valid frontmatter is the fallback. Pass `default=None` in the arena adapter; do not trust `IssueInfo.priority_int` after its parser has substituted the lowest configured priority for missing/invalid metadata. Record the chosen source and any filename/frontmatter disagreement. Use this same resolved value for priority axes, tie-breaking, minimum evidence and sprint mean priority; a missing value stays missing rather than becoming a present P5. The axis table does not introduce a frontmatter-only policy.

Assess each discovered target once before filtering source validity or eligibility, retaining every source path for ambiguous identities. An assessment retains gates, unresolved inputs and exclusion reasons, even when no runnable action can be constructed. Normal selection projects only eligible, fully resolved candidates; `--explain` renders the same assessment, including a rejected implementation gate or unsupported/ambiguous issue source (FEAT-3769 extends this to a source-valid loop with missing inputs). Do not discard rejected targets during generation and then implement a separate explain policy. A nonexistent target remains distinct from an existing but excluded target; explain may have `display_command=null`, while every selected recommendation must have a complete command.

The geometric helper in FEAT-3681 accepts only finite scores in `[0, 1]`. Its legacy next-loop curves are uncapped; **do not pass their values directly to the geometric scorer or change the old command to fix the arena**. Pin these arena-only defaults:

**Lower-bounded curves (Opus review, 2026-10-03).** The geometric mean floors a zero axis at `1e-6`, so a raw curve that reaches 0 acts as a near-veto: with the old curves a leaf with no dependents took a 6.6× penalty on leverage (`1e-6^0.15 = 0.126` vs `0.83` at one dependent), P5 took `0.016` vs P4 `0.617`, and a fresh issue took `0.126` on staleness. Every non-gate curve below is therefore mapped into `[lo, 1]` (`lerp(lo, 1, x)` = `lo + (1 - lo)·x`) so a worst-case value never collapses the score; the `1e-6` floor remains only a guard for degenerate input. **Policy at nominal default weights on a complete axis set:** for every non-gate axis with weight `w`, `(score_at_worst / score_at_best)^w ≥ 0.6`; pin this with a property test over the default weights, and record the `lo` values. If P5 should be excluded from recommendations, that must be an explicit gate, not a curve side effect.

| Axis | Raw value and bounded curve |
|---|---|
| priority | `x = (5 - priority_int) / 5` for `P0..P5`; score `lerp(0.2, 1, x)`. Invalid/missing priority stays missing. |
| confidence / outcome | `x = outcome_confidence / 100` for a valid `0..100` value; score `lerp(0.2, 1, x)`. `confidence_score` is the separate readiness gate, not an interchangeable score. |
| readiness-gap | `x` = maximum normalized shortfall against readiness and outcome thresholds, each `max(0, (threshold - score) / max(threshold, 1))`; score `lerp(0.2, 1, x)`. Both valid scores required, otherwise missing. A valid outcome waiver removes the outcome shortfall. |
| leverage / fan-out | `x = min(1, log1p(count) / log1p(10))` over distinct downstream `open`/`blocked` leaf issues through `blocked_by`, one-sided `blocks` and `depends_on`; score `lerp(0.5, 1, x)`. Traverse only nonterminal nodes. Count exactly below 10; at saturation report `count_lower_bound=10`, `saturated=true` and `≥10` with a bounded sample, never an invented exact total. Count each dependent once; report cycle/missing-node diagnostics separately. Zero dependents is a valid present value (score 0.5), not missing. |
| effort, inverse | Parse the Impact-section `Effort` field, accepting both label spellings `- **Effort**:` and `- **Effort:**` (a repo probe on 2026-10-07 counted 2,795 of the former and 21 of the latter among 3,671 issue files; the latter includes this epic's own children, so a single-spelling parser would silently drop the axis for exactly the issues ll-next is built from). The numeric/`effort` frontmatter is effectively absent. Map the value by a **strict leading-token map**, case-insensitive: `trivial`/`small`/`low`/`s` → 1, `medium`/`m` → 2, `large`/`high`/`l` → 3 (a range such as `small-medium` or `Medium–Large` takes its first token; anything else is missing, with the raw text retained as the missing reason). Score `1 / effort`. Never infer effort from priority, and do not use `IssueInfo.effort`'s priority-inferred fallback. Fixtures cover both label spellings. If the adapter proves unreliable in fixtures, cut the axis rather than widen the map. |
| staleness | `x = min(1, age_days / 30)` from `captured_at`, then `discovered_date`; a missing/malformed/future-only date makes the axis missing with its reason. Never use checkout mtime and never run git for a date (see the no-git rule above). Score `lerp(0.3, 1, x)`. |
| momentum | `x = exp(-log(2) * age_days / 7)` from the latest valid Session Log timestamp at/before `as_of`; score `lerp(0.3, 1, x)`. |

The worst/best-factor property uses the **nominal default weights on a complete axis set** (FEAT-3769 and FEAT-3713 extend the property test to their curves, e.g. loop frequency's `0.4` floor, `0.4^0.5 ≈ 0.632`). Missing-axis renormalization and user weight overrides can increase an axis's effective influence; report the effective weights in explain rather than claiming the `0.6` factor holds for those cases. All non-gate curves still have a positive floor.

The pure refinement adapter uses the arena readiness result for its score-driven step. A ready issue with a valid outcome waiver gets no repeated confidence/refinement action merely because its waived outcome is below threshold; formatting/verification checks remain independently applicable. Preserve this intentional arena policy difference from legacy next-action in a fixed fixture.

Dates must have a documented UTC normalization (date-only capture/Session Log values mean midnight UTC; timestamp values without an offset use documented UTC interpretation with provenance). Malformed/future-only dates and absent history remain missing, with their reason; no fake zero recency or success `1.0` for unseen targets. Curves are fixed defaults in this slice; expose consumed per-verb weights/caps and the existing confidence thresholds, not unused configurable-curve/gate frameworks.

### Scoring, gates and coverage

- Use FEAT-3681's weighted geometric aggregate over present non-gate axes, weights renormalized after missing axes are excluded. No make-up term. An ordinary zero curve score uses the documented floor; only an explicit gate vetoes.
- Eligibility is explicit: issue action targets are `open` or `blocked` leaf issues; exclude `done`, `cancelled`, `deferred`, `in_progress` and EPIC containers. Build dependencies from **all** nonterminal statuses, including deferred, and resolve edges only against known `done`/`cancelled` issues. Unknown dependency IDs fail closed here, even though `DependencyGraph.from_issues` currently warns and drops them. Cycles yield diagnostics rather than an invented root blocker.
- Required gate results are `pass`, `fail` or `missing`, separate from numeric axes. `implement-issue` requires satisfied hard blockers **and** `depends_on`, and valid readiness/outcome scores against the effective merged confidence thresholds (defaults `85/65`); honor `outcome_gate_waived` for the outcome comparison only. Both score fields must still be present. This is the conservative arena policy, aligned with `check-readiness --honor-waiver`, not the readiness-only manage-issue/ll-auto gate. `commands.confidence_gate.enabled: false` does not make an unassessed issue ready for the arena. FEAT-3769's `resolve-blocker` applies this same policy: it requires satisfied dependencies and its displayed implementation step also requires these readiness checks. Non-negotiable eligibility/input checks cannot be disabled by weight `0` or a gate override.
- Validate the raw readiness/outcome domains once for both gates and axes: integers or digit strings representing `0..100`, excluding booleans, floats, negatives, values above 100 and nonfinite values. Preserve absent versus invalid reasons; an invalid high score cannot pass a gate or be clamped into valid evidence. A waiver is only boolean true or the case-insensitive string `true`; other truthy values do not waive anything. Invalid/missing scores request `confidence-check` and never reach numeric scoring as trusted values. Do not rely on existing coercers, which accept out-of-range digit values.
- An explicit `status: blocked` independently vetoes implementation even if no dependency edge remains; expose that status instead of assuming its unspecified blocker vanished. A blocked issue can still be refined. A root-blocker implementation with this status is rejected until its blocking reason/status is resolved.
- Coverage is **reported, not multiplied**. Store `resolved_axes` and `applicable_axes` as integers plus a display string (counting only applicable **positive-weight nongate** axes) for output and `--explain`. There is **no coverage multiplier**: renormalization already handles missing axes, and a multiplier would penalize the same gap twice and rank issues down for metadata hygiene (e.g. ~half of issues lack `captured_at`). Instead the **per-verb minimum-coverage table below** applies. A candidate below the minimum is treated as cold start (below), not excluded. Within each verb, order scored candidates by `selection_score = utility` (kept as a distinct field equal to `utility` for contract stability, so later slices can adjust it without a schema change), then valid priority (where applicable, missing/invalid after valid priorities), then `target_key` ascending. For these scored verbs, effective positive-weight applicability must be nonempty after config validation; an all-zero effective weight set is a config error, not cold start. FEAT-3713's evidence-only scan singleton has no weights and is an explicit extension of this contract.
- Cold start is **per verb**: gate-passing candidates with no resolved scoring axes, or below the minimum-coverage rule, have `utility=null` and `selection_score=null`, sort after scored candidates in their bucket, and use priority/target-key fallback. This lets a bucket whose candidates have no history (FEAT-3769's never-run loops) appear even when issue buckets have data. Gates run first and are never bypassed by fallback. Exit 1 means no eligible candidate across the requested buckets, with distinct empty-source, gate-failed and gate-missing diagnostics.

| Verb | Minimum evidence for numeric utility after eligibility gates |
|---|---|
| implement-issue / refine-issue (and FEAT-3769's resolve-blocker) | Valid priority metadata plus at least one resolved **positive-weight** non-priority axis. Priority counts in coverage only when its weight is positive; disabling that weight does not disable the metadata prerequisite or force an otherwise scorable issue into fallback. |

Missing minimum evidence yields the documented null-utility fallback, not an eligibility veto. Later verbs declare their own rows; do not apply the issue-priority requirement to every future action type.

### Cross-type fill (stateless)

Rank within each verb by `selection_score`; fill `--top N` slots by **round-robin in fixed canonical verb order** (the registry's order: `implement-issue`, `refine-issue`, then `resolve-blocker`, `run-loop`, `run-sprint`, `capture-issues` as their slices register), taking each verb's best remaining candidate per round, with a per-type cap (default 2, keyed config). A namespaced `target_key` appears at most once (first by round-robin order). On a duplicate, continue down that bucket without consuming a slot or its cap; stop only at N or exhaustion. Preserve alternate verbs/actions and the blocker fan-out reason on the selected target so deduplication does not hide its leverage. `--explain VERB TARGET` describes that candidate and the alternate candidates for the same target. Utility is never compared numerically across verbs. `pressure` is `null` here; `bucket_order` is an input so a later slice could substitute an order without changing candidate ranks or dedup semantics (the pressure feature itself is deferred as FEAT-3722).

When `--top` is omitted, perform exactly one pass through requested buckets: each contributes its best remaining nonduplicate target, or nothing. Continue within that bucket past duplicates, but do not start a second round to pad a dedup-exhausted bucket with another implementation target. An empty pass exits 1. This gives each available verb a first-round opportunity and prevents a hardcoded top-3 from starving the later-registered verbs. Explicit `--top N` uses multi-round fill/caps up to N or exhaustion; canonical-order bias under an explicit short limit is documented. Target dedup can make a verb unavailable; preserve its alternate-action annotation.

### CLI and data contract

- `ll-next [--json] [--top N] [--type VERB ...] [--explain VERB TARGET]` (default: one pass through requested buckets). Validate positive explicit N and caps, known verbs, and incompatible explain/top/type combinations at the CLI boundary. Explain evaluates the named source even if gates reject it; absent target exits 1 with a diagnostic. No `--execute`.
- Exit 0: recommendations/fallback or an existing target assessment emitted; exit 1: no eligible candidate or absent explain target; exit 2: config/usage error (concise stderr, empty stdout, no traceback). JSON is an envelope with `schema_version`, `project_root`, `as_of`, `selection_policy`, `recommendations`, nullable `explanation`, and structured `diagnostics`; valid empty results still validate against the schema. Normal selection sets `explanation=null`. ### Signatures

All-status source inventory (`parse_issue_filename` for anchored identity) and captured policy → `ProjectState` → `assess_candidates` → eligible projection through `generate_candidates` → FEAT-3681's `weighted_geometric` → `select_candidates` → human/JSON rendering; explain renders the same assessments and alternates without selecting incomplete actions. No event is written and no git is run.
