# FEAT-3713: ll-next capture-issues and run-sprint generators

## Summary

Add capture-issues (a configured codebase scan) and run-sprint generators with meaningful eligibility gates, pure filesystem/config loading and FEAT-3721's shared read-only HistorySnapshot (decoupled from FEAT-3711 after the 2026-10-04 Opus review). Sprint ranking has pinned axes; the single scan candidate uses activity evidence with freshness explicitly unknown. Keep the existing verb names; the capture description explicitly says it recommends a scan, not an arbitrary single-issue capture.

## Current Behavior

FEAT-3561, FEAT-3769 and FEAT-3721 are done: the four-verb arena, `slash`/`loop` action variants (output schema version 2) and independently callable shared reader are landed. Their dependency edges remain for provenance and no longer block this issue; FEAT-3711 remains independent. Sprint directory is configurable; SprintManager's constructor creates it, and Sprint.from_dict reads the clock for a default creation date. The sprint executor builds a member-only dependency graph that drops outside prerequisites and dispatches every member not removed by its exact terminal-status filter. Its CLI telemetry records `exit_code=0` for a normal handler return of 1, so that field does not establish success. Orchestration rows identify per-issue picks and contain no sprint name, and the temporary sprint-state file is removed after completion. Skill invocation args do not reliably record the actual historical scan scope. These sources cannot be treated as complete sprint/scan history merely because they exist.

## Expected Behavior

Recommend existing valid sprint definitions and scans with configured, existing scope when their persisted/computed evidence supports doing that work. Show concrete commands with all inputs resolved and distinguish unavailable history from never-run/never-scanned. No auto-clustering, execution, directory creation, history migration or new telemetry-producing subsystem.

## Motivation

These two verbs round out real project choices, but broad scan events and per-issue orchestration outcomes must not fabricate target-specific freshness. Pinning eligibility/curves and using the shared reader makes the recommendations inspectable and repeatable.

## Proposed Solution

### Sources, identity and actions

| Verb | Source / action |
|---|---|
| run-sprint | Existing `NAME.yaml` in effective `config.sprints.sprints_dir`, resolved relative to the project root; one candidate per valid named definition with eligible remaining leaf issues. Emit shell argv `ll-sprint run -- NAME` through the core's shlex.join renderer. No ephemeral EPIC sprint or auto-clustering. |
| capture-issues | One candidate for the **entire configured scan scope**, using effective scan.focus_dirs and exclude_patterns. Require at least one existing eligible directory; diagnose empty/nonexistent/invalid scope. Display plain `/ll:scan-codebase` and describe its configured directories beside it. The command's `--focus` means a concern such as security, not a directory argument; do not invent a scope flag/positional argument. |

Sprint target is `sprint:NAME`, with NAME the file stem; require a string declared name exactly equal to that stem. Only the runtime-supported `.yaml` files are candidates; diagnose `.yml` definitions rather than emitting an unresolvable command. Reject names matching `^EPIC-\d+$` case-insensitively because `SprintManager.load_or_resolve` dispatches those to ephemeral EPICs before reading YAML. Preserve literal operands and the core’s working-directory/option-parser contract, including leading dashes; quoting alone is insufficient. Scan target_key is `scan:SCOPE_HASH`: deterministic hash of normalized project-relative directories plus exclude patterns, with readable target `project` and a separate scope description (`--explain capture-issues project` resolves the current scope). A changed scope recomputes activity evidence and cannot inherit explicit recommendation identity from an old scope. Keep the hash local/deterministic, not an absolute-path credential-bearing payload.

Pin the **offered definition/scope** separately from mutable assessment evidence. Read each sprint's bytes once, parse that same buffer and retain a normalized project-relative definition source plus SHA-256 digest in `action_spec` and its semantic fingerprint; the resolved absolute path is assessment provenance only. The YAML digest covers its membership/options; even cosmetic YAML edits change this fingerprint, matching the core's loop policy. Keep assessed member IDs/statuses in the immutable typed `members` offer field below, outside the fingerprint: a member's completion changes the assessment but not the definition identity. Config-level concurrency defaults are not definition identity. Store normalized sorted focus directories and exclusions directly in the scan `action_spec`, so scope participates in the fingerprint and the immutable event payload without reverse-engineering `SCOPE_HASH`. Definition identity includes no runtime clock, event ID or mutable status. Human output/explain states that `ll-sprint run -- NAME` loads the definition current when run and `/ll:scan-codebase` resolves the scan config current when invoked; the snapshot records the assessed offer and cannot freeze those later executions. No new dispatcher or runtime flag is introduced.

### Pinned action and integration contract

The landed `next_arena/actions.py` reserves `sprint`/`scan`; its `slash` action-key projection requires a final issue operand and cannot represent the zero-argument scan. Register the two variants without changing existing `slash`/`loop` shapes or meanings:

| Variant | Required serialized fields | Action key / display |
|---|---|---|
| `sprint` | `variant`, `target` (exact NAME), `definition_source` (normalized project-relative POSIX path), `definition_digest` (`sha256:<64 lowercase hex>`), `fingerprint_scope` (`v1/top-level-bytes`), `working_directory` (absolute project root), `members` (array of `{issue_id, status}`) | `run-sprint` / `ll-sprint run -- NAME` |
| `scan` | `variant`, `target` (constant `project`), `focus_dirs` and `exclude_patterns` (normalized, deduplicated, sorted string arrays), `working_directory` (absolute project root) | `scan-codebase` / `/ll:scan-codebase` |

`members` captures every distinct declared member in first-occurrence sprint-file order, including safely removed terminal members, with the core's canonical lifecycle status. Use immutable records internally, not parallel ID/status arrays. Require this field in offered sprint payloads and preserve it through spec serialization/deserialization and FEAT-3711's lossless shown/accept/feedback path; `Candidate.evidence` alone is not a persisted offer contract. Fingerprint allowlists are sprint `(variant, target, definition_source, definition_digest, fingerprint_scope)` and scan `(variant, target, focus_dirs, exclude_patterns)`. Neither includes members, working directory, absolute paths or observation time. The scan target key uses the full SHA-256 hex digest of UTF-8 canonical JSON of `{focus_dirs, exclude_patterns}`, following `actions.py::action_fingerprint`'s JSON conventions; do not store a second scope hash in `action_spec`. Reuse the core definition-source validation; a configured sprint directory outside the project cannot supply that relative identity and retains an exclusion diagnostic. Action-key dispatch follows the variant, preserving the seven slash mappings and avoiding cross-variant key collisions.

Register sprint/scan candidate domains and update `cli/next.py::main_next` explain lookup plus `render.py::scope_subject`, `target_not_found` and `bucket_diagnostics`. Also touch the other landed domain-specific sites (2026-10-07 source review): `registry.py` (`DOMAIN_SPRINT`/`DOMAIN_SCAN` beside `DOMAIN_ISSUE`/`DOMAIN_LOOP`, the two `VerbSpec` entries, `ArenaSettings` activity fields); `candidates.py::_assess_verb` (raises `KeyError` for a registered verb with no arm, so register and wire in one change, each arm returning `[]` when its domain was not collected); `render.py::collect_diagnostics` (its `loop:`-prefix branch keeps per-definition validation noise out of a full pass — give sprint/scan the same treatment) and `render_explain_text`'s absent-target noun; the `config/features.py::resolve_arena_settings` allowed-key tuple (it special-cases only `refine_cap`) with the matching `config-schema.json` per-verb blocks. Sprint targets/diagnostic subjects use `sprint:NAME`; scan `--explain capture-issues project` resolves the current `scan:SCOPE_HASH` even when its scope/activity gate fails. Neither domain acquires phantom issue assessments or issue-only absence wording. The config resolver currently rejects every empty weight set: give the evidence-only scan an explicit no-weights contract, reject supplied `weights` (including `{}`), consume its activity settings, and retain all-zero errors for scored verbs. Claim the next output schema version at merge time, preserving any FEAT-3711 fields already landed and old-variant round trips.

Collection stays demand-driven: issue/loop/sprint-only modes perform zero Git calls, capture-only modes request no generator history, and no discovered sprint definitions means no sprint-history request/target resolution. With recording disabled (or FEAT-3711's `--no-record`), capture-only modes also resolve/open no history store; optional recording's independent post-selection schema probe is unaffected. The existing loop loading policy remains independent. Help/usage/config errors precede new collection; pure generators consume captured evidence and never resolve storage themselves.

### Scope canonicalization

Pin scope canonicalization: normalize project-relative paths/separators and harmless `.` segments, deduplicate and sort directory entries, and canonicalize exclusions without changing their matching semantics. Equivalent scope ordering hashes identically; changing exclusions or directory meaning changes identity. Validate traversal/symlink targets against the project's declared scan boundary, and use the same scope matcher for commit counting and activity-gate evidence. Reuse/adapt the pure scan-relevance policy anchored by `codequery/codegraph.py::_is_scan_relevant`, `config.dirs.dir_prefix` and `git_operations.file_matches_pattern`; do not invent a separate Git pathspec/negation policy for the activity count. Preserve literal Git filenames when adapting path normalization. The arena's explicitly empty scan scope remains ineligible even though the existing codegraph helper treats an empty list as unrestricted. Do not compare a textual path prefix (`src` versus `src-extra`) or diverge from the declared exclusion semantics.

V1 treats any configured focus-directory path traversing a directory symlink below the resolved project root as unsupported, including an inside-project alias: retain the whole-scope assessment with `symlink_scope_unsupported` and no offer, rather than dropping that entry. Check intermediate directory components as well as the final directory. Boundary validation alone cannot turn `alias -> src` into Git's physical `src/...` paths, and silently resolving only directories could change alias-based exclusion meaning. No symlink translation framework or partial-scope offer is added.

The existing `file_matches_pattern` unconditionally converts backslashes in its `file_path` argument to slashes. On POSIX a backslash in a NUL-delimited Git filename is a literal character. The slash-separated synthetic fixture below is a distinct path; its exact exclusion must not suppress the literal-backslash fixture. Use an arena-only pure literal-Git-path adapter, or a shared opt-in seam preserving existing callers' defaults and exclusion-pattern semantics; do not change global gitignore behavior. Normalize configured directory syntax separately from Git-emitted path bytes. Pin literal backslash and newline filenames in both matching and streaming fixtures; do not call the unchanged normalizing helper and claim literal-path evidence.

Synthetic fixture data:

```text
literal filename: src/a\b.py
different path:   src/a/b.py
```

Extend the injected ProjectState with parsed sprint content, current sprint-state evidence, the sprint-history `HistorySnapshot`, normalized scan scope and batched scoped-commit evidence loaded once at the CLI boundary. Follow FEAT-3769's loop-domain pattern: each is an optional frozen field where `None` means "not collected" (distinct from collected-and-empty); the CLI fills the history field with `dataclasses.replace` after sprint discovery supplies the candidate names, so `assess_candidates(state, *, settings)` and its explain/determinism callers keep their signature and no out-of-band `history` argument exists. The state evidence is `<working_directory>/.sprint-state.json` — the executor's cwd-relative, single, sprint-unkeyed file (JSON `sprint_name`/`completed_issues`; only `--resume` reads it) — read once; the emitted plain command deletes it unconditionally as a fresh start ("delete any old state"), including a state belonging to another sprint, and the `active-state-unknown` diagnostic says so without becoming a veto. Both verbs use FEAT-3561's **assessment-first** path: an existing sprint or configured scan scope retains its failing/missing gates and diagnostics for `--explain`, even when no runnable candidate can be emitted. Pure generators project eligible assessments without reading git, config, the clock or live files. An excluded existing target is not an absent explain target.

### run-sprint eligibility and scoring

- Load definitions through a pure read-only parser, **not SprintManager or an unadapted Sprint.from_dict**, and inject issue content/config/HistorySnapshot. An omitted creation date stays missing; do not read the clock to invent it. Invalid YAML/name/options, missing referenced issue, EPIC member or cycles reject that definition with a diagnostic; deduplicate repeated member IDs before denominators/waves, recording the normalization without editing the YAML.
- Pin definition validation rather than inheriting `SprintOptions.from_dict`'s unchecked values: the YAML root is a mapping and `issues` is an array of full issue-ID strings. `options` absent or YAML null uses the runtime defaults; otherwise it must be a mapping. Supplied `max_iterations`, `timeout` and `max_workers` must be positive integers, excluding booleans, floats and numeric strings; omitted keys retain `100/3600/2`. Unknown option keys produce an ignored-key diagnostic because the runtime ignores them; do not claim they change execution or reject an otherwise usable definition for that reason. Only `max_workers` is currently consumed by the sprint executor; loaded `timeout`/`max_iterations` remain definition bytes without a claimed execution effect. A malformed definition is excluded independently without aborting assessment of valid sibling definitions. Preserve the bytes/digest even for excluded targets in explain.
- Resolve members and their prerequisites through the core's unique issue-source inventory. Repeated IDs inside one sprint definition may be normalized as above; an ID found in multiple issue files is a different ambiguity and vetoes that sprint or any prerequisite requiring it. In particular an active/terminal file collision cannot be removed as completed work, and an arbitrary graph overwrite cannot establish member readiness. Reuse core diagnostics/paths rather than introducing another ID authority.
- Before removing terminal members or building waves, check **every declared member** against the core's anchored-source validity and captured filename-number groups. `SprintManager._find_issue_path` delegates to `resolve_issue_path`, whose frontmatter-first numeric selection can resolve a distinct full filename ID to another file. More than one parsed source sharing that member's exact filename number vetoes the whole plain sprint offer as `ambiguous_issue_id`, with the shared number and all source paths in explain. An inferred ID from an unnormalized source fails `unsupported_issue_filename`; a lone differently typed canonical source could otherwise displace it. Checking only remaining members is insufficient: a supposedly terminal member can resolve to an active file the command would dispatch. Preserve exact filename digits, full-ID graph identity, existing resolver behavior and snapshot-only guarantees; no resolver replica, per-member live reads, silently substituted IDs or executor repair.
- Reuse the core's captured-source lifecycle status and provenance, including explicit-status precedence over stale completion markers. An explicitly reopened member with `completed_at` remains remaining work, and a similarly reopened outside prerequisite remains unresolved; do not drop either through `IssueInfo.status`'s completion inference. Absent-status legacy terminal records keep the core's existing fallback and labeled provenance.
- Verify every terminal removal against the plain command's exact captured predicate, `fm.get("status", "open") in ("done", "cancelled")`, before emitting it. `cli/sprint/run.py` does not apply the absent-status `completed_at` fallback or strip explicit status whitespace, and its member graph does not filter terminal `IssueInfo` values. Thus both `legacy_completed_at` records and `status: ' done '` / `' cancelled '` records would be removed by the arena but dispatched by the unfiltered command. Veto the whole sprint as `executor_membership_mismatch`, retaining affected IDs, raw parsed status and lifecycle provenance, with the explicit canonical terminal-status remedy. Do not silently recommend a subset, waive core lifecycle semantics, rewrite source files or fix the executor here. Exact parsed `done`/`cancelled` remain safely removable; an explicit reopened `open` member remains work. This check precedes member-only waves and scoring and is visible in explain.
- Remaining work means `open`/`blocked` leaves after known `done`/`cancelled` are removed. Deferred/in-progress issues remain in the global nonterminal dependency graph and continue to block edges; they are not runnable members. Because the emitted plain `ll-sprint run NAME` currently dispatches all nonterminal declared members, any declared deferred/in-progress member vetoes the candidate with a diagnostic. Do not silently score a subset while emitting a command for the whole definition. Partial `--only` recommendations are outside this slice. No remaining eligible work yields no candidate. There is no proven-live veto in v1: SprintState has no PID/process-ownership signal, and cli_events cannot prove liveness. A sprint-state file or unfinished matching invocation yields `active-state-unknown` diagnostics, never a permanent veto. Absence of such evidence also does not prove idle. Document that recommendations cannot prevent concurrent duplicate sprint work; new liveness telemetry is a separate feature.
- Use the full-project graph to check each remaining member's prerequisites before constructing sprint-local waves. Any unresolved nonterminal prerequisite outside the remaining sprint members, unknown prerequisite, or relevant cycle vetoes the entire run-sprint candidate; the current executor drops outside edges, so a ready first wave cannot make a later externally blocked wave safe. Diagnose unrelated project cycles separately without rejecting an otherwise independent sprint.
- Before allowing pending internal edges, reject list-form relationship values whose normalization hides executor ordering differences. The core's `state.py::_split_ids` strips/drops blank list entries, while `IssueParser.parse_file` preserves list entries for `blocked_by`, `depends_on` and `blocks`. For a remaining member's captured frontmatter, a string list entry `e` with `e != e.strip()` whose stripped ID names another remaining member vetoes the sprint as `executor_dependency_mismatch`, including one-sided `blocks`. Also veto a truthy list/scalar `blocked_by`/`blocks` value whose core-normalized IDs are empty when captured body fallback supplies an internal remaining-member edge: `blocked_by: ['']` or a whitespace/comma-only scalar can suppress that body edge in the executor. Retain source/target, relationship kind and raw entry/list in explain. Exact list IDs, exact empty `[]` and valid scalar CSV/exact empty strings retain the shared valid behavior. This narrow syntactic check may veto a redundant edge conservatively; do not simulate the executor's resolver/waves, change normalization or add live member reads.
- Once outside prerequisites are proven satisfied, construct waves over only the remaining sprint members with their internal edges. **Do not compute global execution waves and project them onto the sprint**: `get_execution_waves` marks every preceding global wave processed, which would invent completion of outside work. The first sprint-local wave must be nonempty and **every remaining member**, including later waves, must pass the core implementation status/readiness/outcome-or-waiver and unresolved-decision gates. Internal sprint prerequisites are the sole permitted pending gate: the member graph sequences them, and they are not assumed completed in the ProjectState. A later member with missing/invalid/below-threshold scores or an independent status veto cannot be hidden behind a ready first wave; reject the whole unfiltered run with member-specific diagnostics. The executor's readiness-only check is weaker than the arena's outcome policy, so do not rely on it to uphold this contract. No speculative score improvements or decision resolution from earlier-wave execution. Reusing the core `decision_unresolved` veto for every member is deliberately more conservative than sprint processing, which can attempt `decide-issue --auto`; the arena does not assume a current true flag will be resolved. Do not change ll-sprint's execution policy in this generator issue.
- The internal-prerequisite allowance applies to `status: open` members with pending internal edges. An explicit `status: blocked` retains the core's independent veto even if all recorded edges are internal: edges alone do not prove the status has no other blocking reason. Keep blocked members in the remaining-work denominator and explain their veto; do not silently waive or rewrite that status. Fixtures distinguish a valid open later-wave member from a status-blocked member with the same dependency edge.
- Ready share denominator is distinct remaining `open`/`blocked` members; numerator is those passing all core implementation gates **now**, including dependency gates (the runnable first wave). All members’ metadata/status readiness is required above; the axis still varies with the fraction immediately unblocked, and is not a measure of speculative later-wave improvement. Mean priority uses those same members, not terminal/deferred siblings. No divide-by-zero or priority inferred from another issue.

| Axis | Weight | Raw / bounded curve |
|---|---|---|
| dependency-ready share (`ready_share`) | 0.50 | Share in `[0,1]` under the core readiness policy; score `lerp(0.4, 1, share)`. |
| mean priority (`priority`) | 0.30 | Mean of the core **already bounded** priority scores for remaining members (range `[0.2,1]`); do not apply another lower-bound mapping. If any member priority is invalid/missing the axis stays missing, rather than averaging a selectively known subset or inventing P0. |
| time since latest observed ended invocation (`since_last_run`) | 0.20 | `x = min(1, witness_age_days / 30)` from the newest qualified ended witness in the bounded read; score `lerp(0.2, 1, x)`. Missing/unparseable/future-only/unscoped/unavailable evidence stays missing. Intentional bounded truncation with a qualified witness can score under the explicitly limited policy below. |

The parenthesized axis keys are public contract (config `next.verbs.run-sprint.weights.<key>`, `axes.py::AXIS_BOUNDS` — which the nominal-weight property test iterates — the closed `axes` name enum in `output-schema.json` and the `config-schema.json` weight block): `ready_share` is new with bounds `(0.4, 1.0)`; `priority` is the existing key unchanged (`(0.2, 1.0)`, here the member mean); `since_last_run` is new with bounds `(0.2, 1.0)`. Do not reuse `recency` (run-loop's recent-is-high decay: opposite polarity) or `staleness` (0.3 floor, issue-age semantics).

Dependency-ready share measures currently satisfied dependency gates, not concurrency. `ll-sprint` additionally splits waves for file contention; do not reuse that policy or turn Files-to-Modify hints into a new scoring input here.

Qualified sprint history is `cli_events` for binary ll-sprint with exact name and complete argument capture under a narrow pure projection of the real CLI grammar: `run NAME`, alias `r NAME`, and either form with `--` before the one literal operand qualify. This includes the option-safe command the arena emits (`ll-sprint run -- NAME`). No execution options are modeled for whole-sprint history in v1: `--only`, `--skip`, `--type`, `--label`, `--config`, `--resume`, `--dry-run`, help/version and any other option exclude the row with its reason. Tokens after `--` are literal operands, so `run -- -dash` is not an option-bearing invocation. Reuse/extend the core pure action grammar; do not invoke `main_sprint` or its telemetry wrapper to parse historical args. A valid ended-wrapper time is derived from ts + duration_ms. This is evidence of an ended named invocation with `outcome_unknown`, not a successful or productive sprint. The current `cli_event_context` only sees exceptions, so a normally returned failure is incorrectly recorded as `exit_code=0`; do not use that zero as proof of success. Missing duration/time fields do not fabricate completion. Excluded invocations retain their arguments in provenance and cannot establish whole-sprint recency. Per-issue orchestration_runs, issue membership overlap and deleted sprint-state files cannot establish the named sprint's last run. Any future success-based qualification needs verified producer timing/version provenance; historical zeros do not become trustworthy retroactively.

Producer semantics are source-verified: `main_sprint` passes `sys.argv[1:]` (without argv[0]) to `cli_event_context`, whose UTC `ts` is captured at invocation entry before the telemetry insert; `duration_ms` is integer wall-clock elapsed time captured on wrapper exit. Derived end time is an approximation from separate clock captures and millisecond granularity, not a monotonic completion-observation timestamp. Require a parseable timestamp and a nonnegative integer duration whose derived end is representable; invalid args/timestamps/durations skip that row with FEAT-3721's counted `partial(malformed_row)` coverage while retaining valid qualified witnesses. A null duration denotes unfinished evidence and yields no ended witness. Unexpected reader/decoder exceptions still make the request unavailable. Keep these producer facts in fixtures so a later producer change cannot silently reinterpret old rows.

Label this axis `name-based-definition-unknown`: existing CLI rows have no sprint-definition digest or historical member snapshot. Exact invocation-name/argument qualification does not prove the current YAML definition ran. Retain this limited name-based recency signal, as the core does for loops, without claiming exact definition-version evidence or enabling automatic acceptance matching.

Also label incomplete coverage `witness_in_window`: use the newest qualified **ended** witness among the completely observed rows, not the first matching ID or an assertion about the whole store. A witnessed invocation remains real when an ID-span/returned-row/payload/deadline cap prevents complete traversal. Its `witness_age_days` is an upper bound on the true latest-run age, and its age-based curve can be optimistic; expose that limitation in human/JSON/explain evidence beside the numeric axis. Clock rollback, out-of-order ingestion and an earlier-started longer run ending later can hide a newer qualifying end outside the walk. Preserve `latest_qualified_unknown=true` when completeness is unproved; no witness in an incomplete walk means missing, never never-run. Unscoped ownership or unexpected read/decode failure cannot supply scoring witnesses. Eligibility remains entirely history-independent, and this observed-witness policy neither establishes successful work nor matches automatic acceptance. Keep the fixed axis floor/weight; do not silently promote the witness to exact recency or add a new scoring framework. A **complete** walk (`reached_start`) with no qualified witness is equally `missing` (reason `no_qualified_witness`), never a never-run `x=1`: `cli_events` capture is gated by `analytics.capture.cli_commands`, `analytics.enabled=false` and `LL_ANALYTICS_CAPTURE`, lock-timeout drops go to a sidecar, and an empty table reads as `available` + `reached_start`, so absent rows cannot prove the sprint never ran (do not infer historical capture config from today's settings; explain says "no qualified invocation observed"). The effective lookback is the reader's ID window, not the curve's 30 days: `MAX_ID_SPAN` (50,000 IDs) spanned about 4.5 days on this repository's store (ID 475,710 = 2026-10-03T17:48Z against a newest row of 2026-10-08T05:52Z; store-dependent), so a busy-store live walk can only reach `x ≲ 0.15` (axis ≈ 0.2–0.32). Docs and explain must not promise a 30-day lookback, and fixtures inject snapshots for ages beyond a live window. The curves and the shared reader stay unchanged.

Use the ended invocation timestamp for the recency axis and require both start and derived end at/before `as_of`, with a finite nonnegative duration. An array at the existing 50-argument capture boundary is incomplete unless producer provenance proves otherwise. A `--only`/`--skip` invocation cannot establish recency for the offered unfiltered whole sprint; exclude filters and other unmodeled semantic options from that axis, while retaining the exclusion reason. FEAT-3721's partial history cannot establish an exact newest invocation; its completely read qualified rows can supply only the limited witnessed axis above. Temporary sprint state alone cannot prove process liveness or establish historical success; stale/unverifiable state is diagnostic and this slice performs no state cleanup or new liveness telemetry.

### capture-issues eligibility and evidence

v1 is **activity-backed only**. Pin `next.verbs.capture-issues.activity_threshold=20` scoped commits and `activity_lookback_days=30`, with positive integer validation and keyed local merge/reset behavior. The thresholds are initial defaults, not optimized claims. Do not add `stale_days`, a scan-age axis, scan-freshness queries or configurable scan weights: existing telemetry cannot prove a completed exact-scope scan, and this verb has only one candidate to order.

- Count distinct commits reachable from the ProjectState's captured HEAD at/before as_of that touch normalized scope after exclusions, once per commit across overlapping directories, within the fixed lookback. Use one streamed batched git process, not one subprocess per directory/commit or an unbounded buffered result; define commit time as committer UTC time. Pin literal/NUL-delimited record/path framing — `--format=%x00%H %ct`, so every record starts with an empty NUL token (a path is never empty; an empty-path commit has no `\n` separator, every other record exactly one before its first path) rather than a control-byte sentinel a filename can embed (a tracked file named `\x01<40 hex>\x02<digits>` is indistinguishable from a `%x01…%x02` header and forges commit records; 2026-10-07 scratch-repo probe) — plus `--root`, `--no-renames` and first-parent **merge diffs**, without `--first-parent` ancestry traversal: an in-scope deletion/rename-out and an out-of-scope rename-in both count, and reachable side-branch commits are still assessed. Filter time without pruning reachable ancestry merely because parent/child dates are nonmonotonic: pass `--since-as-filter=<epoch of as_of − lookback>` (Git 2.37, below the 2.45 floor; a non-terminating `--since`), so Git emits only in-window records and a quiet, mature repository's traversal can complete exactly instead of exhausting the record cap on out-of-window history (probe on this repository: 9,023 reachable commits, 1,764 in the 30-day window; output 1.94 MB → 0.65 MB, 0.47 s → 0.20 s; the plain epoch spelling is accepted). The loader still discards records whose committer time is after `as_of`, and the record/byte/time budgets count emitted records. Fixtures cover backdated/future commits, merges, deletions, renames and unusual filenames; a missing/non-git repository or unsupported required git flag makes activity unknown, never zero.
- Pin project-relative Git output: `paths.py::find_project_root` can return a `.ll`-only project below a containing repository boundary, while ordinary Git names are repository-relative. Run both Git calls from the captured resolved project root and pass explicit `--relative` to the existing streamed log, before applying the literal-path scope matcher. This removes outside-project paths and rebases nested paths without another metadata query or prefix parser; empty file lists do not count. A temporary nested newline-project probe with `--root --diff-merges=first-parent --no-renames -z --name-only --relative` retained root/side/merge paths and literal backslash/newline filenames, and omitted outside-only changes. Preserve this combination in a regression fixture; do not assume project root equals Git root or let `diff.relative` defaults choose coordinates.
- **Own the arena Git read policy** (moved from FEAT-3561, whose core runs no git; this slice is the only v1 git consumer). Every arena Git call uses the enforcing global `git --no-lazy-fetch` option before its subcommand; an older Git rejects it, yielding unavailable evidence with no retry. The environment variable alone is insufficient because an unsupported version can silently ignore it. Collect metadata/raw paths with external diff, textconv and signature helpers disabled (`--no-ext-diff`, `--no-textconv`, `--no-show-signature` on log/show), explicit format and no color. Set `GIT_OPTIONAL_LOCKS=0` so an index refresh git attempts on its own cannot introduce a write. A partial clone's missing promisor objects must make the affected evidence unavailable; do not fetch objects or mutate the object store to satisfy an advisory read. This is an arena-only read policy, not a change to existing Git helpers/executors; support/degradation stays within the existing Git-call bounds. **Minimum Git version: 2.45.0.** Git's 2.45.0 release notes introduce the global `git --no-lazy-fetch` option; the 2.44.0 and 2.46.0 notes do not mention it (2026-10-07 source check). One installed Git cannot establish a *first* release by probe, so cite the release notes and test (a) skip-gated that the installed Git accepts the flag and (b) with an injected Git usage-error result (exit 129, `unknown option`) that an unsupported Git maps to `git_unsupported`. Document the minimum in `CLI.md`/`CONFIGURATION.md`, and make the diagnostic name the option and that minimum, so `capture-issues` vanishing on an older system Git is an explained exclusion in `--explain`, not silent absence. No separate version-probe subprocess. Accepted v1 trade-off: common LTS distribution Gits (Ubuntu 24.04 ships 2.43, Debian 12 ships 2.39) predate 2.45, so `capture-issues` is `git_unsupported` there until Git is upgraded (backports/PPA); the only safe degrade path needs a partial-clone check (a third subprocess or `.git/config` parsing), which is not worth new contract for an evidence-only singleton. Reopen only if users report it.
- Apply that policy to the activity query: enforcing global `--no-lazy-fetch`, disabled external diff/textconv/signature helpers and controlled raw/name-only output. Missing objects/unsupported controls yield unavailable activity, not an exact zero or a retry that enables fetching. A nonzero exit not caused by this collector's intentional cap/deadline/saturation stop is a failure: discard that collection's tentative count/lower bound rather than treating an observed process error as bounded success. User diff/pretty/signature settings must not change stream framing or run helpers. This adds no Git calls or new Git-wrapper framework.
- Disable inherited `GIT_TRACE*` outputs in the child environment, with `GIT_TRACE2`, `GIT_TRACE2_EVENT` and `GIT_TRACE2_PERF` explicitly `0` to override early config-provided trace targets. A read-only Git command otherwise can create an ambient trace file before command-line trace suppression takes effect. This is local child-environment isolation, with no persistent Git/environment edits or extra subprocesses.
- Capture HEAD and shallow-repository status in one batched `rev-parse` call owned by this slice (the core runs no git). Traversing all available shallow ancestry does not prove a complete lookback count: below threshold, report partial/shallow-history and a missing activity gate; a qualified observed threshold lower bound may still pass. Unknown shallow status cannot establish completeness. Do not deepen/fetch the clone or add another subprocess. Full-history traversal still has the existing record/byte/time caps.
- Bound the loader with fixed internal defaults: at most 5,000 completed commit records, 16 MiB combined stdout/stderr consumed and a shared 2-second monotonic subprocess budget. Inject the clock/stream for deterministic tests; these bounds are not a new config surface. Stop/reap the process on a work cap, expiry or proven threshold saturation, keeping bounded buffers and draining neither an unbounded stderr nor an unbounded remainder. Count only fully decoded records; a truncated record is not evidence. Recheck the budget while reading/decoding, disclose nonpreemptive OS/decoding limits, and keep the existing total-subprocess bound. A subprocess-count assertion alone is not a work bound.
- A fully consumed successful traversal within the budgets provides exact `scoped_commit_count`. Once observed distinct in-window commits reach `activity_threshold`, the gate may pass with `scoped_commit_count=null`, a proven `scoped_commit_count_lower_bound`, `saturated=true` and `≥N` evidence; exact total is unknown. If a cap/deadline truncates traversal **below** the threshold, return partial coverage with a missing activity gate, never an invented exact zero/low count or a failed gate. Unexpected git/decode errors make activity unavailable; intentional bounded termination is distinct. Retain window/as_of/captured HEAD, threshold, scope hash, visited-record/byte counts and truncation reason in evidence. Explain renders exact, lower-bound-satisfied or unknown distinctly. Machine speed can change availability, never manufacture a gate pass.
- Label every v1 scan offer `scan-freshness-unknown`. `capture-issue`, scan-product, a concern-limited `--focus` scan, unscoped skill_events, issue discovery markers and absence of recent events do not prove a full scoped scan. Do not infer historical config from today's settings.
- Treat the eligible singleton as evidence-only: `axes={}`, coverage `0/0`, `utility=null` and `selection_score=null`, using the core's gate-passing bucket fallback. There is no fabricated numeric freshness score or unused weight setting. This bucket participates in the same round-robin/cap/dedup rules.
- No scan-tracking store, conditional verified-scan reader/fixture framework or dispatcher in this slice. A future completed scoped producer needs a separate issue before scan age/suppression can be enabled. Activity alone can keep the same scan suggestion present until the lookback/threshold changes; document this limitation and include it in the six-verb usability check.
