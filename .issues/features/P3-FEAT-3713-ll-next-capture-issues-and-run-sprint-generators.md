# FEAT-3713: ll-next capture-issues and run-sprint generators

## Summary

Add capture-issues (a configured codebase scan) and run-sprint generators with meaningful eligibility gates, pure filesystem/config loading and FEAT-3721's shared read-only HistorySnapshot (decoupled from FEAT-3711 after the 2026-10-04 Opus review). Sprint ranking has pinned axes; the single scan candidate uses activity evidence with freshness explicitly unknown. Keep the existing verb names; the capture description explicitly says it recommends a scan, not an arbitrary single-issue capture.

## Current Behavior

FEAT-3561 and FEAT-3769 cover implement-issue, refine-issue, resolve-blocker and run-loop. Sprint directory is configurable; SprintManager's constructor creates it, and Sprint.from_dict reads the clock for a default creation date. The sprint executor builds a member-only dependency graph that drops outside prerequisites and dispatches every nonterminal declared member. Its CLI telemetry records `exit_code=0` for a normal handler return of 1, so that field does not establish success. Orchestration rows identify per-issue picks and contain no sprint name, and the temporary sprint-state file is removed after completion. Skill invocation args do not reliably record the actual historical scan scope. These sources cannot be treated as complete sprint/scan history merely because they exist.

## Expected Behavior

Recommend existing valid sprint definitions and scans with configured, existing scope when their persisted/computed evidence supports doing that work. Show concrete commands with all inputs resolved and distinguish unavailable history from never-run/never-scanned. No auto-clustering, execution, directory creation, history migration or new telemetry-producing subsystem.

## Motivation

These two verbs round out real project choices, but broad scan events and per-issue orchestration outcomes must not fabricate target-specific freshness. Pinning eligibility/curves and using the shared reader makes the recommendations inspectable and repeatable.

## Proposed Solution

### Sources, identity and actions

| Verb | Source / action |
|---|---|
| run-sprint | Existing `NAME.yaml` in effective `config.sprints.sprints_dir`, resolved relative to the project root; one candidate per valid named definition with eligible remaining leaf issues. Emit shell argv `ll-sprint run NAME` through shlex.join. No ephemeral EPIC sprint or auto-clustering. |
| capture-issues | One candidate for the **entire configured scan scope**, using effective scan.focus_dirs and exclude_patterns. Require at least one existing eligible directory; diagnose empty/nonexistent/invalid scope. Display plain `/ll:scan-codebase` and describe its configured directories beside it. The command's `--focus` means a concern such as security, not a directory argument; do not invent a scope flag/positional argument. |

Sprint target is `sprint:NAME`, with NAME the file stem; require a string declared name exactly equal to that stem. Only the runtime-supported `.yaml` files are candidates; diagnose `.yml` definitions rather than emitting an unresolvable command. Reject names matching `^EPIC-\d+$` case-insensitively because `SprintManager.load_or_resolve` dispatches those to ephemeral EPICs before reading YAML. Preserve literal operands and the core’s working-directory/option-parser contract, including leading dashes; quoting alone is insufficient. Scan target_key is `scan:SCOPE_HASH`: deterministic hash of normalized project-relative directories plus exclude patterns, with readable target `project` and a separate scope description (`--explain capture-issues project` resolves the current scope). A changed scope recomputes activity evidence and cannot inherit explicit recommendation identity from an old scope. Keep the hash local/deterministic, not an absolute-path credential-bearing payload.

Pin the **offered definition/scope** separately from mutable assessment evidence. Read each sprint's bytes once, parse that same buffer and retain the resolved definition path plus SHA-256 digest in `action_spec` and its semantic fingerprint. The YAML digest covers its membership/options; even cosmetic YAML edits change this fingerprint, matching the core's loop policy. Keep the assessed remaining-member IDs/statuses in immutable offer provenance, outside the fingerprint: a member's completion changes the assessment but not the definition identity. Config-level concurrency defaults are not definition identity. Store normalized sorted focus directories and exclusions directly in the scan `action_spec`, so scope participates in the fingerprint and the immutable event payload without reverse-engineering `SCOPE_HASH`. Definition identity includes no runtime clock, event ID or mutable status. Human output/explain states that `ll-sprint run NAME` loads the definition current when run and `/ll:scan-codebase` resolves the scan config current when invoked; the snapshot records the assessed offer and cannot freeze those later executions. No new dispatcher or runtime flag is introduced.

Pin scope canonicalization: normalize project-relative paths/separators and harmless `.` segments, deduplicate and sort directory entries, and canonicalize exclusions without changing their matching semantics. Equivalent scope ordering hashes identically; changing exclusions or directory meaning changes identity. Validate traversal/symlink targets against the project's declared scan boundary, and use the same scope matcher for commit counting and activity-gate evidence. Reuse/adapt the pure scan-relevance policy anchored by `codequery/codegraph.py::_is_scan_relevant`, `config.dirs.dir_prefix` and `git_operations.file_matches_pattern`; do not invent a separate Git pathspec/negation policy for the activity count. Preserve literal Git filenames when adapting path normalization. The arena's explicitly empty scan scope remains ineligible even though the existing codegraph helper treats an empty list as unrestricted. Do not compare a textual path prefix (`src` versus `src-extra`) or diverge from the declared exclusion semantics.

The existing `file_matches_pattern` unconditionally converts backslashes in its `file_path` argument to slashes. On POSIX a backslash in a NUL-delimited Git filename is a literal character. The slash-separated synthetic fixture below is a distinct path; its exact exclusion must not suppress the literal-backslash fixture. Use an arena-only pure literal-Git-path adapter, or a shared opt-in seam preserving existing callers' defaults and exclusion-pattern semantics; do not change global gitignore behavior. Normalize configured directory syntax separately from Git-emitted path bytes. Pin literal backslash and newline filenames in both matching and streaming fixtures; do not call the unchanged normalizing helper and claim literal-path evidence.

Synthetic fixture data:

```text
literal filename: src/a\b.py
different path:   src/a/b.py
```

Extend the injected ProjectState with parsed sprint content, current sprint-state evidence, normalized scan scope and batched scoped-commit evidence loaded once at the CLI boundary. Both verbs use FEAT-3561's **assessment-first** path: an existing sprint or configured scan scope retains its failing/missing gates and diagnostics for `--explain`, even when no runnable candidate can be emitted. Pure generators project eligible assessments without reading git, config, the clock or live files. An excluded existing target is not an absent explain target.

### run-sprint eligibility and scoring

- Load definitions through a pure read-only parser, **not SprintManager or an unadapted Sprint.from_dict**, and inject issue content/config/HistorySnapshot. An omitted creation date stays missing; do not read the clock to invent it. Invalid YAML/name/options, missing referenced issue, EPIC member or cycles reject that definition with a diagnostic; deduplicate repeated member IDs before denominators/waves, recording the normalization without editing the YAML.
- Pin definition validation rather than inheriting `SprintOptions.from_dict`'s unchecked values: the YAML root is a mapping and `issues` is an array of full issue-ID strings. `options` absent or YAML null uses the runtime defaults; otherwise it must be a mapping. Supplied `max_iterations`, `timeout` and `max_workers` must be positive integers, excluding booleans, floats and numeric strings; omitted keys retain `100/3600/2`. Unknown option keys produce an ignored-key diagnostic because the runtime ignores them; do not claim they change execution or reject an otherwise usable definition for that reason. A malformed definition is excluded independently without aborting assessment of valid sibling definitions. Preserve the bytes/digest even for excluded targets in explain.
- Resolve members and their prerequisites through the core's unique issue-source inventory. Repeated IDs inside one sprint definition may be normalized as above; an ID found in multiple issue files is a different ambiguity and vetoes that sprint or any prerequisite requiring it. In particular an active/terminal file collision cannot be removed as completed work, and an arbitrary graph overwrite cannot establish member readiness. Reuse core diagnostics/paths rather than introducing another ID authority.
- Before removing terminal members or building waves, check **every declared member** against the core's anchored-source validity and captured filename-number groups. `SprintManager._find_issue_path` delegates to `resolve_issue_path`, whose frontmatter-first numeric selection can resolve a distinct full filename ID to another file. More than one parsed source sharing that member's exact filename number vetoes the whole plain sprint offer as `ambiguous_issue_id`, with the shared number and all source paths in explain. An inferred ID from an unnormalized source fails `unsupported_issue_filename`; a lone differently typed canonical source could otherwise displace it. Checking only remaining members is insufficient: a supposedly terminal member can resolve to an active file the command would dispatch. Preserve exact filename digits, full-ID graph identity, existing resolver behavior and snapshot-only guarantees; no resolver replica, per-member live reads, silently substituted IDs or executor repair.
- Reuse the core's captured-source lifecycle status and provenance, including explicit-status precedence over stale completion markers. An explicitly reopened member with `completed_at` remains remaining work, and a similarly reopened outside prerequisite remains unresolved; do not drop either through `IssueInfo.status`'s completion inference. Absent-status legacy terminal records keep the core's existing fallback and labeled provenance.
- Verify that the plain command's member filtering agrees with that assessment before emitting it. `cli/sprint/run.py` currently skips only members whose parsed frontmatter `status` is `done`/`cancelled`; it does not apply the absent-status `completed_at` fallback, and its member graph does not filter terminal `IssueInfo` values. A declared member classified terminal solely by `legacy_completed_at` would therefore be removed from the arena's remaining set but still dispatched by the unfiltered command. Veto that sprint as `executor_membership_mismatch`, naming the affected IDs and the need to record their explicit terminal status. Do not silently recommend a subset, waive core lifecycle semantics, rewrite source files or fix the executor here. Explicit terminal members remain safely removable; an explicit reopened `open` member remains work. This check precedes member-only waves and scoring and is visible in explain.
- Remaining work means `open`/`blocked` leaves after known `done`/`cancelled` are removed. Deferred/in-progress issues remain in the global nonterminal dependency graph and continue to block edges; they are not runnable members. Because the emitted plain `ll-sprint run NAME` currently dispatches all nonterminal declared members, any declared deferred/in-progress member vetoes the candidate with a diagnostic. Do not silently score a subset while emitting a command for the whole definition. Partial `--only` recommendations are outside this slice. No remaining eligible work yields no candidate. There is no proven-live veto in v1: SprintState has no PID/process-ownership signal, and cli_events cannot prove liveness. A sprint-state file or unfinished matching invocation yields `active-state-unknown` diagnostics, never a permanent veto. Absence of such evidence also does not prove idle. Document that recommendations cannot prevent concurrent duplicate sprint work; new liveness telemetry is a separate feature.
- Use the full-project graph to check each remaining member's prerequisites before constructing sprint-local waves. Any unresolved nonterminal prerequisite outside the remaining sprint members, unknown prerequisite, or relevant cycle vetoes the entire run-sprint candidate; the current executor drops outside edges, so a ready first wave cannot make a later externally blocked wave safe. Diagnose unrelated project cycles separately without rejecting an otherwise independent sprint.
- Once outside prerequisites are proven satisfied, construct waves over only the remaining sprint members with their internal edges. **Do not compute global execution waves and project them onto the sprint**: `get_execution_waves` marks every preceding global wave processed, which would invent completion of outside work. The first sprint-local wave must be nonempty and **every remaining member**, including later waves, must pass the core implementation status/readiness/outcome-or-waiver gates. Internal sprint prerequisites are the sole permitted pending gate: the member graph sequences them, and they are not assumed completed in the ProjectState. A later member with missing/invalid/below-threshold scores or an independent status veto cannot be hidden behind a ready first wave; reject the whole unfiltered run with member-specific diagnostics. The executor's readiness-only check is weaker than the arena's outcome policy, so do not rely on it to uphold this contract. No speculative score improvements from earlier-wave execution. Do not change ll-sprint's execution policy in this generator issue.
- The internal-prerequisite allowance applies to `status: open` members with pending internal edges. An explicit `status: blocked` retains the core's independent veto even if all recorded edges are internal: edges alone do not prove the status has no other blocking reason. Keep blocked members in the remaining-work denominator and explain their veto; do not silently waive or rewrite that status. Fixtures distinguish a valid open later-wave member from a status-blocked member with the same dependency edge.
- Ready share denominator is distinct remaining `open`/`blocked` members; numerator is those passing all core implementation gates **now**, including dependency gates (the runnable first wave). All members’ metadata/status readiness is required above; the axis still varies with the fraction immediately unblocked, and is not a measure of speculative later-wave improvement. Mean priority uses those same members, not terminal/deferred siblings. No divide-by-zero or priority inferred from another issue.

| Axis | Weight | Raw / bounded curve |
|---|---|---|
| dependency-ready share | 0.50 | Share in `[0,1]` under the core readiness policy; score `lerp(0.4, 1, share)`. |
| mean priority | 0.30 | Mean of the core **already bounded** priority scores for remaining members (range `[0.2,1]`); do not apply another lower-bound mapping. If any member priority is invalid/missing the axis stays missing, rather than averaging a selectively known subset or inventing P0. |
| time since latest observed ended invocation | 0.20 | `x = min(1, witness_age_days / 30)` from the newest qualified ended witness in the bounded read; score `lerp(0.2, 1, x)`. Missing/unparseable/future-only/unscoped/unavailable evidence stays missing. Intentional bounded truncation with a qualified witness can score under the explicitly limited policy below. |

Dependency-ready share measures currently satisfied dependency gates, not concurrency. `ll-sprint` additionally splits waves for file contention; do not reuse that policy or turn Files-to-Modify hints into a new scoring input here.

Qualified sprint history is `cli_events` for binary ll-sprint with exact name and complete argument capture under a narrow pure projection of the real CLI grammar: `run NAME`, alias `r NAME`, and either form with `--` before the one literal operand qualify. This includes the option-safe command the arena emits (`ll-sprint run -- NAME`). No execution options are modeled for whole-sprint history in v1: `--only`, `--skip`, `--type`, `--label`, `--config`, `--resume`, `--dry-run`, help/version and any other option exclude the row with its reason. Tokens after `--` are literal operands, so `run -- -dash` is not an option-bearing invocation. Reuse/extend the core pure action grammar; do not invoke `main_sprint` or its telemetry wrapper to parse historical args. A valid ended-wrapper time is derived from ts + duration_ms. This is evidence of an ended named invocation with `outcome_unknown`, not a successful or productive sprint. The current `cli_event_context` only sees exceptions, so a normally returned failure is incorrectly recorded as `exit_code=0`; do not use that zero as proof of success. Missing duration/time fields do not fabricate completion. Excluded invocations retain their arguments in provenance and cannot establish whole-sprint recency. Per-issue orchestration_runs, issue membership overlap and deleted sprint-state files cannot establish the named sprint's last run. Any future success-based qualification needs verified producer timing/version provenance; historical zeros do not become trustworthy retroactively.

Producer semantics are source-verified: `main_sprint` passes `sys.argv[1:]` (without argv[0]) to `cli_event_context`, whose UTC `ts` is captured at invocation entry before the telemetry insert; `duration_ms` is integer wall-clock elapsed time captured on wrapper exit. Derived end time is an approximation from separate clock captures and millisecond granularity, not a monotonic completion-observation timestamp. Require a parseable timestamp and a nonnegative integer duration whose derived end is representable; invalid args/timestamps/durations skip that row with FEAT-3721's counted `partial(malformed_row)` coverage while retaining valid qualified witnesses. A null duration denotes unfinished evidence and yields no ended witness. Unexpected reader/decoder exceptions still make the request unavailable. Keep these producer facts in fixtures so a later producer change cannot silently reinterpret old rows.

Label this axis `name-based-definition-unknown`: existing CLI rows have no sprint-definition digest or historical member snapshot. Exact invocation-name/argument qualification does not prove the current YAML definition ran. Retain this limited name-based recency signal, as the core does for loops, without claiming exact definition-version evidence or enabling automatic acceptance matching.

Also label incomplete coverage `witness_in_window`: use the newest qualified **ended** witness among the completely observed rows, not the first matching ID or an assertion about the whole store. A witnessed invocation remains real when an ID-span/returned-row/payload/deadline cap prevents complete traversal. Its `witness_age_days` is an upper bound on the true latest-run age, and its age-based curve can be optimistic; expose that limitation in human/JSON/explain evidence beside the numeric axis. Clock rollback, out-of-order ingestion and an earlier-started longer run ending later can hide a newer qualifying end outside the walk. Preserve `latest_qualified_unknown=true` when completeness is unproved; no witness in an incomplete walk means missing, never never-run. Unscoped ownership or unexpected read/decode failure cannot supply scoring witnesses. Eligibility remains entirely history-independent, and this observed-witness policy neither establishes successful work nor matches automatic acceptance. Keep the fixed axis floor/weight; do not silently promote the witness to exact recency or add a new scoring framework.

Use the ended invocation timestamp for the recency axis and require both start and derived end at/before `as_of`, with a finite nonnegative duration. An array at the existing 50-argument capture boundary is incomplete unless producer provenance proves otherwise. A `--only`/`--skip` invocation cannot establish recency for the offered unfiltered whole sprint; exclude filters and other unmodeled semantic options from that axis, while retaining the exclusion reason. FEAT-3721's partial history cannot establish an exact newest invocation; its completely read qualified rows can supply only the limited witnessed axis above. Temporary sprint state alone cannot prove process liveness or establish historical success; stale/unverifiable state is diagnostic and this slice performs no state cleanup or new liveness telemetry.

### capture-issues eligibility and evidence

v1 is **activity-backed only**. Pin `next.verbs.capture-issues.activity_threshold=20` scoped commits and `unknown_history_lookback_days=30`, with positive integer validation and keyed local merge/reset behavior. The thresholds are initial defaults, not optimized claims. Do not add `stale_days`, a scan-age axis, scan-freshness queries or configurable scan weights: existing telemetry cannot prove a completed exact-scope scan, and this verb has only one candidate to order.

- Count distinct commits reachable from the ProjectState's captured HEAD at/before as_of that touch normalized scope after exclusions, once per commit across overlapping directories, within the fixed lookback. Use one streamed batched git process, not one subprocess per directory/commit or an unbounded buffered result; define commit time as committer UTC time. Pin literal/NUL-delimited record/path framing, `--root`, `--no-renames` and first-parent **merge diffs**, without `--first-parent` ancestry traversal: an in-scope deletion/rename-out and an out-of-scope rename-in both count, and reachable side-branch commits are still assessed. Filter time without pruning reachable ancestry merely because parent/child dates are nonmonotonic. Fixtures cover backdated/future commits, merges, deletions, renames and unusual filenames; a missing/non-git repository or unsupported required git flag makes activity unknown, never zero.
- **Own the arena Git read policy** (moved from FEAT-3561, whose core runs no git; this slice is the only v1 git consumer). Every arena Git call uses the enforcing global `git --no-lazy-fetch` option before its subcommand; an older Git rejects it, yielding unavailable evidence with no retry. The environment variable alone is insufficient because an unsupported version can silently ignore it. Collect metadata/raw paths with external diff, textconv and signature helpers disabled (`--no-ext-diff`, `--no-textconv`, `--no-show-signature` on log/show), explicit format and no color. Set `GIT_OPTIONAL_LOCKS=0` so an index refresh git attempts on its own cannot introduce a write. A partial clone's missing promisor objects must make the affected evidence unavailable; do not fetch objects or mutate the object store to satisfy an advisory read. This is an arena-only read policy, not a change to existing Git helpers/executors; support/degradation stays within the existing Git-call bounds. **Minimum Git version:** establish the first Git release that accepts the global `--no-lazy-fetch` option with a recorded probe/learning test (skip-gated when Git is absent) instead of asserting a number from memory; document it in `CLI.md`/`CONFIGURATION.md`, and make the unsupported-Git diagnostic name the option and that minimum, so `capture-issues` vanishing on an older system Git is an explained `git_unsupported` exclusion in `--explain`, not silent absence. No separate version-probe subprocess.
- Apply that policy to the activity query: enforcing global `--no-lazy-fetch`, disabled external diff/textconv/signature helpers and controlled raw/name-only output. Missing objects/unsupported controls yield unavailable activity, not an exact zero or a retry that enables fetching. A nonzero exit not caused by this collector's intentional cap/deadline/saturation stop is a failure: discard that collection's tentative count/lower bound rather than treating an observed process error as bounded success. User diff/pretty/signature settings must not change stream framing or run helpers. This adds no Git calls or new Git-wrapper framework.
- Capture HEAD and shallow-repository status in one batched `rev-parse` call owned by this slice (the core runs no git). Traversing all available shallow ancestry does not prove a complete lookback count: below threshold, report partial/shallow-history and a missing activity gate; a qualified observed threshold lower bound may still pass. Unknown shallow status cannot establish completeness. Do not deepen/fetch the clone or add another subprocess. Full-history traversal still has the existing record/byte/time caps.
- Bound the loader with fixed internal defaults: at most 5,000 completed commit records, 16 MiB combined stdout/stderr consumed and a shared 2-second monotonic subprocess budget. Inject the clock/stream for deterministic tests; these bounds are not a new config surface. Stop/reap the process on a work cap, expiry or proven threshold saturation, keeping bounded buffers and draining neither an unbounded stderr nor an unbounded remainder. Count only fully decoded records; a truncated record is not evidence. Recheck the budget while reading/decoding, disclose nonpreemptive OS/decoding limits, and keep the existing total-subprocess bound. A subprocess-count assertion alone is not a work bound.
- A fully consumed successful traversal within the budgets provides exact `scoped_commit_count`. Once observed distinct in-window commits reach `activity_threshold`, the gate may pass with `scoped_commit_count=null`, a proven `scoped_commit_count_lower_bound`, `saturated=true` and `≥N` evidence; exact total is unknown. If a cap/deadline truncates traversal **below** the threshold, return partial coverage with a missing activity gate, never an invented exact zero/low count or a failed gate. Unexpected git/decode errors make activity unavailable; intentional bounded termination is distinct. Retain window/as_of/captured HEAD, threshold, scope hash, visited-record/byte counts and truncation reason in evidence. Explain renders exact, lower-bound-satisfied or unknown distinctly. Machine speed can change availability, never manufacture a gate pass.
- Label every v1 scan offer `scan-freshness-unknown`. `capture-issue`, scan-product, a concern-limited `--focus` scan, unscoped skill_events, issue discovery markers and absence of recent events do not prove a full scoped scan. Do not infer historical config from today's settings.
- Treat the eligible singleton as evidence-only: `axes={}`, coverage `0/0`, `utility=null` and `selection_score=null`, using the core's gate-passing bucket fallback. There is no fabricated numeric freshness score or unused weight setting. This bucket participates in the same round-robin/cap/dedup rules.
- No scan-tracking store, conditional verified-scan reader/fixture framework or dispatcher in this slice. A future completed scoped producer needs a separate issue before scan age/suppression can be enabled. Activity alone can keep the same scan suggestion present until the lookback/threshold changes; document this limitation and include it in the six-verb usability check.

## Program Design

### Types

- Reuse ProjectState, HistorySnapshot, AxisScore, GateResult, CandidateAssessment and Candidate. Source availability and missing reasons remain typed data, not invented scores.

- `assess_run_sprints(state: ProjectState, history: HistorySnapshot) -> list[CandidateAssessment]` — pure, retains definition/full-graph/input exclusions for explain.

- **Out of scope:** auto-clustered/EPIC sprints, execute, new scan telemetry store/dispatcher, changing existing sprint/scan execution, learned thresholds, finding-backed verbs.

## Impact

- **Priority:** P3

## Use Case

A user whose remaining sprint members all meet the metadata/status gates and whose first wave is unblocked sees the named sprint. A project with enough recent scoped commits receives a scan suggestion with freshness explicitly unknown instead of an invented last-scan age. While that activity threshold remains met, the advisory suggestion may recur; explicit acknowledgement alone does not prove a scan completed.

## Acceptance Criteria

- [ ] Pure generators honor configured directories/scope and never create directories, run actions, write history or migrate; absent/invalid sources produce diagnostics and no invented action.
- [ ] Sprint fixtures cover terminal/deferred/in-progress/EPIC/missing/duplicate members, relevant and unrelated cycles, external blockers/prerequisites on first and later members, nonempty member-only first wave, all-members metadata/status readiness, rejection of a later-wave missing/low score or invalid waiver, and active-state-unknown diagnostics without an invented live-veto fixture. Reserved EPIC names, filename/name mismatch, unsupported .yml, option-like operands and quoted names recover the actual runtime target. Deferred/in-progress declared members and any unresolved outside prerequisite veto the whole emitted plain run command; global-wave projection cannot invent prerequisite completion.
- [ ] Sprint-definition fixtures pin mapping/list shape, absent/null options and runtime defaults, positive integer option domains, ignored unknown keys and isolation of malformed siblings. Open internal-dependency members can occupy later waves; the same edge does not waive a blocked-status veto. Dependency-ready share is labeled as distinct from concurrency/file-contention scheduling.
- [ ] Duplicate issue-file IDs (including active/terminal collisions and ambiguous outside prerequisites) veto affected sprint offers independent of file order; this is distinct from normalizing a repeated member ID in one YAML definition. Core identity diagnostics are reused and unrelated sprints remain eligible.
- [ ] Numeric-source collision fixtures include individually unique `FEAT-001`/`BUG-001` filename IDs with frontmatter-biased runtime selection and an apparently correctly disambiguating variant: both veto the whole offer as `ambiguous_issue_id`, including when the affected declared member is assessed terminal before filtering. Explain retains the number/all paths; unique-number members remain usable and tests verify actual resolver parity with assessed sources. Reuse the core inventory without production resolver duplication, per-member I/O or global resolver changes.
- [ ] A declared member whose full ID is inferred from an unnormalized filename vetoes the offer before terminal filtering, including beside a differently typed canonical numeric match. Core `unsupported_issue_filename` diagnostics are reused; anchored member sources in legacy directories remain supported.
- [ ] A reopened member with a stale completion marker remains in the member assessment, and an explicitly reopened outside prerequisite vetoes the run instead of being inferred completed. Core lifecycle provenance/fallback is reused without modifying sprint execution or the shared issue parser.
- [ ] A mixed sprint containing a ready member and an absent-status legacy completion record is excluded with `executor_membership_mismatch`, including the conflicting ID/provenance in explain. Replacing only that record's metadata with explicit `done`/`cancelled` restores eligibility when other gates pass; an explicitly reopened `open` member is assessed as remaining work. No whole-sprint offer can silently omit a member that the copied plain command would dispatch under this legacy filter.
- [ ] Historical grammar fixtures qualify `run NAME`, `r NAME`, `run -- NAME` and `run -- -dash`, exclude option-bearing invocations with reasons, and pin argv-without-binary/entry-time/duration producer semantics. A malformed args/time/duration row alongside a valid ended witness yields partial row-validation coverage, not total source loss; unfinished null-duration rows never establish completion. Derived-end overflow is a row exclusion, not an uncaught exception.
- [ ] Sprint history uses exact parsed non-dry-run ended named CLI evidence with outcome unknown; a handler returning 1 while telemetry records 0 cannot establish success. Per-issue orchestration and temporary state do not fabricate recency, and different/truncated filters or arguments cannot establish whole-sprint recency.
- [ ] Capture fixtures cover empty/missing scope, sufficient/insufficient/unknown activity, freshness-unknown labeling, absence of unused scan-age/weight settings, scope/exclusion changes, overlapping directories, excluded paths and non-git state.
- [ ] A fake streaming git process pins record/byte/time caps, bounded memory and stop/reap behavior: threshold saturation passes with a truthful lower bound; exhausted work below threshold yields a missing gate; a complete successful short traversal yields an exact count. Backdated ancestry, future commits, first-parent merge diffs with side-branch traversal, root commits, rename-in/out, literal NUL-delimited filenames and git/decode errors cannot fabricate activity evidence. Unsupported flags degrade to unknown; total git calls remain ≤2.
- [ ] A recorded probe/learning test establishes the minimum Git release accepting the global `--no-lazy-fetch` option (skip-gated when Git is absent); the minimum is documented, and an older Git yields a `git_unsupported` exclusion naming the option and minimum in `--explain`, with no retry, no fetch and no effect on other verbs.
- [ ] The activity collector applies the arena Git read policy with enforcing lazy-fetch suppression; a tiny local partial clone with missing trees yields unavailable activity without a fetch/object-pack write. Configured diff/textconv/signature helpers are never invoked, and user output settings cannot alter record framing. An observed nonzero process exit discards tentative counts rather than passing on partial output; no fallback enables helpers or fetching. Shallow traversal below threshold yields a missing gate, while an observed threshold lower bound may pass; shallow detection shares HEAD capture and keeps the ≤2-call bound.
- [ ] Literal-Git-path scope/exclusion fixtures distinguish POSIX backslashes and newlines from directory separators; the exact exclusion of the slash-separated synthetic fixture does not suppress its distinct literal-backslash counterpart. The consumed matcher seam preserves existing callers' normalization and pattern semantics, and matching/stream decoding retain the same literal path identity.
- [ ] Definition/scope identity fixtures cover a same-named sprint's changed YAML, read-once parse/hash consistency, a member-status-only change (same fingerprint, changed provenance), reordered equivalent scan scope (same fingerprint), and changed directories/exclusions (different target/fingerprint). Historical CLI recency is labeled name-based/definition-unknown; offer/explain text describes later execution's current-definition/config lookup.
- [ ] Fixed weights/explicit curve floors/thresholds and verb-specific positive-weight coverage are pinned; sprint default-weight worst/best factors pass and mean priority is bounded exactly once. Ready sprints without history remain scored; all-missing sprint scoring axes and the eligible evidence-only scan singleton use gate-respecting fallback. Config consumer/schema/export/serialization/merge/reset/error tests pass.
- [ ] Canonical order, omitted-top opportunity, caps/dedup, --type/explain/Schema integration cover all six verbs, including collisions between issue/loop/sprint display names.
- [ ] Sprint-history fixtures separate exact invocation qualification from whole-store latest-run completeness: intentional capped walks with a valid ended witness can score with `witness_in_window`, witness-age upper-bound/optimistic-score disclosure and `latest_qualified_unknown`; a capped walk without a witness remains missing. Clock rollback, out-of-order IDs and a longer earlier-started run cannot become false exact recency. Unscoped/read-failed sources, filtered/truncated arguments and future-ending invocations cannot supply the witnessed axis. Scan freshness is always explicitly unknown in v1; activity-backed selection works without scan-age/query/producer/weight code. FEAT-3721's local-only reader/no-record behavior is preserved with no migration/producer registration. Acceptance integration is conditional on FEAT-3711 and does not create a hard dependency.
- [ ] Sprint/issue overlap is annotated as alternative choices; requested history sources are loaded only for run-sprint, and at most two git subprocesses serve scan activity (the core runs none). Both verbs retain excluded existing targets for shared `--explain` assessment, and injected sprint/scope/commit/state evidence keeps generation free of live I/O and clock reads.
- [ ] Six-verb output/command-usability evidence is recorded, including the recurrent activity-backed scan limitation. Required invocations are copyable with literal quoting/no invented scope flag; docs and `python -m pytest scripts/tests/` pass.
