# BUG-2758: ll-init writes inert Write() permission rule for handoff prompt

## Summary

`ll-init` seeds `.claude/settings.local.json` with the permission entry
`Write(.ll/ll-continue-prompt.md)`. Claude Code's file-permission check only
consults `Edit(path)` rules — a single `Edit(...)` rule covers every
file-editing tool (Write, Edit, NotebookEdit) — so the `Write(...)` form is
never matched. The rule is inert: `/ll:handoff` still triggers an interactive
permission prompt on every run, defeating the entry's whole purpose, and
Claude Code now emits a startup warning about it:

```
Permission allow rule (.claude/settings.local.json): Write(.ll/ll-continue-prompt.md)
is not matched by file permission checks — only Edit(path) rules are.
Use Edit(.ll/ll-continue-prompt.md) instead (Edit rules cover all file-editing tools).
```

Because the entry is generated by `ll-init`, every project initialized by
little-loops carries the dead rule and the warning.

## Current Behavior

`ll-init` writes `Write(.ll/ll-continue-prompt.md)` into `permissions.allow` of
`.claude/settings.local.json`. Claude Code's file-permission check ignores
`Write(...)` rules, so the entry never matches: `/ll:handoff` still prompts
interactively for the write, and Claude Code prints a startup warning naming the
unmatched rule. Re-running `ll-init` re-appends the same dead entry.

## Impact

Every project initialized by little-loops carries a dead permission rule. Two
concrete costs: (1) a startup warning on every Claude Code session, and (2) an
interactive permission prompt on every `/ll:handoff` run, which breaks
unattended automation paths (`ll-auto`, `ll-parallel`, `ll-sprint`) that rely on
handoff writing without a human present. Severity is low (P3) — the workaround
is a one-line manual edit — but the defect ships to every new install.

## Root Cause

`scripts/little_loops/init/writers.py:51` — the last element of the
`_LL_PERMISSIONS` tuple is the literal string
`"Write(.ll/ll-continue-prompt.md)"`. `merge_settings()`
(`writers.py:199`) writes that tuple into `permissions.allow` of the target
settings file.

Two structural details make the fix non-trivial:

1. **Trailing position is load-bearing.** `merge_settings` builds the canonical
   list as `canonical[:-1] + extra_permissions + [canonical[-1]]`
   (`writers.py:238`), i.e. it inserts caller-supplied extras *before* the last
   element, assuming that last element is the handoff-prompt entry.
2. **Idempotency sweep matches by exact string.** `allow = [e for e in allow if
   e not in _LL_PERMISSIONS]` (`writers.py:231`). Changing the constant to the
   `Edit(...)` form means the legacy `Write(...)` string is no longer in
   `_LL_PERMISSIONS`, so re-running `ll-init` on an existing project will leave
   the stale `Write(...)` entry in place *and* append the new `Edit(...)` one —
   the warning would persist alongside a working rule.

## Steps to Reproduce

1. Run `ll-init` in a fresh project (or inspect this repo's
   `.claude/settings.local.json:26`).
2. Observe `"Write(.ll/ll-continue-prompt.md)"` in `permissions.allow`.
3. Start Claude Code — the warning above is printed at session start.
4. Run `/ll:handoff` — the write to `.ll/ll-continue-prompt.md` still prompts
   for permission despite the allow entry.

## Expected Behavior

`ll-init` writes `Edit(.ll/ll-continue-prompt.md)`, the handoff-prompt write is
auto-approved, and no startup warning is emitted. Re-running `ll-init` on a
project that already has the legacy `Write(...)` entry migrates it rather than
duplicating it.

### Ordering Constraint (confirmed)

`writers.py:238` — `canonical = canonical[:-1] + list(extra_permissions) + [canonical[-1]]`.
The trailing-position assumption holds regardless of whether the last element is
the `Write(...)` or `Edit(...)` form, so swapping the string alone does not break
`test_extra_permissions_inserted` (`test_init_core.py:952-959`) — that test
asserts `skill_idx < write_idx` by *value lookup*, so it only needs its literal
updated, not its logic.

### Migration-Sweep Placement

The legacy sweep must run against the **incoming** `allow` list, i.e. alongside
`writers.py:231`, before `allow.extend(canonical)` at `:240`. Placing it after
the extend would strip a freshly-appended canonical entry if the two constants
ever overlap.

## Implementation Steps

1. In `scripts/little_loops/init/writers.py`, change `_LL_PERMISSIONS[-1]` from
   `Write(.ll/ll-continue-prompt.md)` to `Edit(.ll/ll-continue-prompt.md)`.
2. Add a legacy-entry sweep in `merge_settings()` so the old
   `Write(.ll/ll-continue-prompt.md)` string is stripped from `allow` in
   addition to the current `_LL_PERMISSIONS` membership filter. Define it as a
   module-level constant (e.g. `_LEGACY_LL_PERMISSIONS`) so the migration
   intent is explicit and future retirements have a home.
3. Update the two docstring references in `writers.py:208` and `writers.py:215`.
4. Update the three assertions in `scripts/tests/test_init_core.py:930`, `:940`,
   `:958`, and add a regression test asserting that a settings file
   pre-seeded with the legacy `Write(...)` entry ends up with exactly one
   `Edit(...)` entry and zero `Write(...)` entries after `merge_settings()`.
5. Update all three configure-skill copy sites in `skills/configure/areas.md`:
   `:849` (the permission-set description string), `:858` (the "Remove any
   existing `Write(.ll/ll-continue-prompt.md)` entry" instruction), and `:862`
   (the "Skip / Remove entries" removal instruction). The two removal
   instructions (`:858`, `:862`) should name **both** forms so re-running
   configure cleans up the legacy entry as well as the new one.
6. Fix this repo's own `.claude/settings.local.json:26` so the warning clears
   locally.

## Out of Scope

`skills/spike/SKILL.md` declares `Write(.ll/spikes/**)` in its `allowed-tools`
frontmatter (asserted by `scripts/tests/test_spike_skill.py:132`). That is a
different mechanism from `settings.json` permission rules and was not verified

## Resolution

Fixed 2026-07-24. `_LL_PERMISSIONS[-1]` is now `Edit(.ll/ll-continue-prompt.md)`
(Edit rules cover every file-editing tool). A new module-level
`_LEGACY_LL_PERMISSIONS` tuple holds retired entries and is swept from the
incoming `allow` list in `merge_settings()` alongside the canonical filter, so
re-running `ll-init` on a project with the old `Write(...)` rule migrates it
instead of duplicating. Docstrings, the three `test_init_core.py` assertions, and
all three `skills/configure/areas.md` copy sites updated; a regression test
(`test_migrates_legacy_write_handoff_permission`) asserts exactly one `Edit(...)`
and zero `Write(...)` entries after merge. This repo's own (gitignored)
`.claude/settings.local.json` was migrated locally.
