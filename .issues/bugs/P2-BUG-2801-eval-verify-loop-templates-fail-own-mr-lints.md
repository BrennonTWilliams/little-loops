# BUG-2801: create-eval-from-issues/verify-issue-loop templates fail the repo's own loop lints

## Summary

Two of `create-eval-from-issues`' generation paths emit loop YAML that trips
the repo's own `ll-loop validate` gates: (1) Variant B's `discover`/`execute`
states write scratch state to a bare `/tmp/<harness-name>-processed.txt` path
instead of `${context.run_dir}` (MR-3), and (2) `verify-issue-loop` and
`create-eval-from-issues`' learning-tests-off template synthesize
`llm_structured` verify states with no paired non-LLM evaluator in the routing
chain, tripping MR-1 ERROR. `adversarial-verify-loop` already solves the
MR-1 case with its `count_probes` `output_numeric` gate (`operator: ge`,
`target: 3`) — the fix is to copy that pattern, not invent a new one.

## Current Behavior

- `skills/create-eval-from-issues/SKILL.md:341` and `:385` hardcode
  `/tmp/<harness-name>-processed.txt` as the Variant B dedup/processed-items
  marker path, both in the initial-file-creation snippet and the
  `discover`/advance action that appends to it.
- `skills/verify-issue-loop/SKILL.md:167,187` synthesizes one
  `verify-criterion-N` state per acceptance criterion with only an
  `llm_structured` evaluator — no `exit_code`/`output_numeric`/`convergence`
  backstop anywhere in that state's routing chain.
- `skills/create-eval-from-issues/SKILL.md`'s learning-tests-off template
  (used when `LT_ENABLED=false` or `learning_tests_required` is empty, per
  line ~317) keeps `execute.next: check_skill` with only `llm_structured` on
  `check_skill` — same MR-1 gap.
- Loop YAML generated by either skill therefore fails `ll-loop validate`
  with an MR-1 ERROR (and MR-3 WARN for Variant B) the moment a user tries
  to validate/run it, undermining the "generate ready-to-run loop YAML"
  promise both skills make.

## Expected Behavior

- Variant B's processed-items marker is written under
  `${context.run_dir}/<harness-name>-processed.txt` (or an equivalent
  per-run path), not a bare `/tmp/` path, so MR-3 does not fire and
  concurrent/repeat runs don't collide on a shared file.
- `verify-issue-loop`'s per-criterion `verify-criterion-N` states and
  `create-eval-from-issues`' learning-tests-off `check_skill` state each pair
  their `llm_structured` evaluator with a non-LLM backstop in the same
  routing chain — following `adversarial-verify-loop`'s `count_probes`
  `output_numeric` (`operator: ge`, `target: N`) pattern (`shell`
  action_type state that counts/measures something concrete, gating before
  or alongside the LLM judgment) — so MR-1 passes without suppression flags.
- `ll-loop validate` run against a loop generated by either skill returns
  clean (no MR-1 ERROR, no MR-3 WARN) without needing
  `meta_self_eval_ok`/`shared_state_ok` escape hatches.

## Root Cause

- **File**: `skills/create-eval-from-issues/SKILL.md`
- **Anchor**: Variant B section (`### Variant B (multiple issues)`, action
  snippets around `pf = '/tmp/<harness-name>-processed.txt'` and
  `echo "${captured.current_item.output}" >> /tmp/<harness-name>-processed.txt`)
- **Cause**: the template was authored before MR-3's per-run-artifact rule
  existed and was never updated to interpolate `${context.run_dir}`.
- **File**: `skills/verify-issue-loop/SKILL.md` and
  `skills/create-eval-from-issues/SKILL.md`
- **Anchor**: `### Evaluator prompt (llm_structured)` in verify-issue-loop;
  the learning-tests-off branch (`LT_ENABLED=false` path) in
  create-eval-from-issues
- **Cause**: both templates were authored to rely solely on the LLM's own
  pass/fail judgment (`llm_structured`), which is exactly the self-evaluation
  pattern MR-1 exists to catch (SHOR Table 1: LLM self-grades on harness
  edits are ~33-55% accurate) — they were never updated after MR-1 landed,
  unlike `adversarial-verify-loop` which already added `count_probes`.

## Steps to Reproduce

1. Run `/ll:create-eval-from-issues` against 2+ issue IDs to generate a
   Variant B harness YAML.
2. Run `ll-loop validate <generated-harness>.yaml`.
3. Observe MR-3 WARN on the `discover`/advance state's `/tmp/...` path.
4. Run `/ll:verify-issue-loop` against any issue with 2+ acceptance criteria,
   or `/ll:create-eval-from-issues` against an issue with
   `learning_tests_required` empty/absent.
5. Run `ll-loop validate` on the result and observe MR-1 ERROR on the
   `verify-criterion-N` / `check_skill` state(s).

## Impact

- **Priority**: P2 - Both generator skills are advertised as producing
  ready-to-run loop YAML; every generated harness currently fails validation
  out of the gate, forcing manual patching or a suppression flag before
  first use.
- **Effort**: Small - both fixes are template-text edits to the two SKILL.md
  files (interpolate `${context.run_dir}`; add an `output_numeric`
  counter/gate state modeled on `adversarial-verify-loop`'s `count_probes`).
  No FSM engine or validator changes needed.
- **Risk**: Low - purely additive/corrective changes to markdown generation
  templates; no runtime code paths affected.
- **Breaking Change**: No

## Proposed Solution

1. In `skills/create-eval-from-issues/SKILL.md`'s Variant B section, replace
   the two `/tmp/<harness-name>-processed.txt` references with
   `${context.run_dir}/<harness-name>-processed.txt`, matching MR-3's
   `${context.run_dir}` convention already used elsewhere in the repo.
2. In `skills/verify-issue-loop/SKILL.md`, add a `shell` `action_type` state
   (e.g. `count_criteria_pass` or per-criterion) with an `output_numeric`
   evaluator that counts something concrete tied to the criterion (e.g. exit
   code of a grep/test invocation, or a pass counter), gating the
   `llm_structured` verdict — mirroring `adversarial-verify-loop`'s
   `count_probes` (`operator: ge`, `target: N`) shape referenced at
   `skills/adversarial-verify-loop/SKILL.md:319,340`.
3. Apply the same `output_numeric` backstop to
   `create-eval-from-issues`' learning-tests-off `check_skill` state.
4. Regenerate a sample harness/verify loop with each fixed template and
   confirm `ll-loop validate` passes clean.

### Codebase Research Findings

_Added by `/ll:refine-issue` — based on codebase analysis and direct reproduction:_

**Critical: the bug's premise does not reproduce against `ll-loop validate` as currently implemented.**

- `_is_meta_loop()` (`scripts/little_loops/fsm/validation.py:1330`) gates MR-1
  entirely — `_validate_meta_loop_evaluation()` (line 1355) is a no-op unless a
  state's action text matches `_META_LOOP_ACTION_PATTERNS` (line 97-102:
  `loops/[\w-]+\.yaml`, `skills/[\w-]+/SKILL\.md`, `agents/[\w-]+\.md`,
  `commands/[\w-]+\.md`, `.claude/(CLAUDE\.md|settings)`), or
  `fsm.imports` contains `lib/benchmark.yaml`, or an action contains
  `yaml_state_editor`/`replace_action`. Neither `verify-issue-loop`'s
  `verify-criterion-N` states nor `create-eval-from-issues`' `check_skill`/
  `discover`/`advance` states touch harness artifacts — they exercise a
  feature or count a marker file — so `_is_meta_loop()` returns `False` and
  MR-1 never fires on them, regardless of the all-`llm_structured` routing
  chain.
- `_SHARED_TMP_PATH_RE` (`validation.py:114`) is
  `re.compile(r"\.loops/tmp/[\w./-]+")` — it matches only the literal
  `.loops/tmp/` prefix, not a bare `/tmp/...` path. The Variant B
  `/tmp/<harness-name>-processed.txt` writes at
  `skills/create-eval-from-issues/SKILL.md:341,385` do not match this regex.
- **Direct repro** (2026-07-25): hand-built minimal fixtures mirroring both
  templates and ran `ll-loop validate` against each:
  - A `verify-criterion-1` state with only `llm_structured` (no
    exit_code/output_numeric backstop) → reported `is valid`, with only
    MR-4 (`partial_route_ok`) and MR-8 (`evidence_contract_ok`) WARNINGs —
    **no MR-1 ERROR**.
  - A `discover`/`advance` pair writing to bare
    `/tmp/test-harness-processed.txt` → reported `is valid` with **zero**
    warnings — **no MR-3 WARN**.
- Conclusion: as filed, this issue's "Steps to Reproduce" (steps 2-3 and
  5) will not observe the described validator output on the current
  `main` branch. Before implementing the Proposed Solution, either (a)
  re-verify with the actual skill-generated YAML end-to-end (not a
  hand-built approximation — the real generated file might differ enough
  to trip `_is_meta_loop` some other way, e.g. via an `imports:` or
  `yaml_state_editor` reference elsewhere in the template) using
  `/ll:create-eval-from-issues` and `/ll:verify-issue-loop` directly against
  a real issue, or (b) rescope the fix as a validator gap (MR-1 should not
  be meta-loop-scoped when a loop's *purpose* is self-evaluation of a
  feature; MR-3's regex should also flag bare `/tmp/` for cross-run shared
  state) rather than a template-only fix.
- Existing regression-test scaffolding to model a fix/test after either

### Decision Rationale

**Selected**: Option A (re-verify end-to-end against real skill-generated YAML before any code/template change)

## Repro Result (2026-07-25) — INVALID

Option A end-to-end repro run: generated a real `verify-issue-loop` YAML from
BUG-2803's four acceptance criteria, plus a Variant-B-shaped eval harness using
the SKILL.md's literal `/tmp/<harness-name>-processed.txt` scratch path, then
ran `ll-loop validate` on both. **Neither MR-1 nor MR-3 fired.** Both premises
are false:

- **MR-1 does not apply.** `_validate_meta_loop_evaluation()`
  (`scripts/little_loops/fsm/validation.py:1355`) early-returns unless
  `_is_meta_loop(fsm)` (line 1330) — i.e. the loop's action strings write
  harness artifacts (loop YAML / skill / agent / command / project config),
  import `lib/benchmark.yaml`, or reference `yaml_state_editor`/`replace_action`.
  A verification or eval loop for an ordinary product issue is not a meta-loop,
  so its `llm_structured` states are never required to carry a non-LLM
  evaluator. Validation exited 0.
- **MR-3 does not match `/tmp/`.** `_SHARED_TMP_PATH_RE`
  (`validation.py:114`) is `\.loops/tmp/[\w./-]+` — it matches only the
  repo-relative `.loops/tmp/` path, not a bare `/tmp/...` path. Variant B's
  scratch path is invisible to the lint.

Closing as invalid. Both repro YAMLs were deleted after validation; no source
changes were made.

Incidental (real but different, not the reported defect): the generated verify
template *does* draw two WARNINGs — MR-4 (`partial` verdict has no route) and
MR-8 (evaluator prompt omits evidence-contract keywords). That is a small
template-polish enhancement, not this bug.
