# ENH-2804: verify-issue-loop / create-eval-from-issues templates emit MR-4 (and risk MR-8) warnings

## Summary

Loop YAML generated by `/ll:verify-issue-loop` draws one `MR-4` WARNING per
synthesized state from `ll-loop validate`, because the template routes
`on_yes`/`on_no` but never `on_partial` — and MR-4 requires *both* `no` and
`partial` to be routed. `create-eval-from-issues`' `check_skill` state (both
Variant A and Variant B) has the same gap, and additionally leaves its
`evaluate.prompt` as a free-form `<synthesized evaluation criteria>`
placeholder with no instruction to include evidence-contract keywords, so
whether MR-8 fires is left to chance at generation time.

Both skills advertise "ready-to-run loop YAML"; today the output validates
(exit 0) but is noisy. This is polish, not a defect — it is explicitly *not*
the MR-1/MR-3 claim from BUG-2801, which was disproved by repro and cancelled.

## Motivation

A generated artifact that immediately emits N warnings trains users to ignore
`ll-loop validate` output, which is the mechanism the repo relies on to catch
real loop-authoring defects. The fix is a few lines of template text.

Beyond the noise: MR-4 is describing a genuine runtime hazard. An
`llm_structured` evaluator can return `partial`, and a `partial` verdict on an
unrouted state dead-ends the loop — the parent reads it as failed. For a
per-criterion verification loop, "partially satisfied" is a plausible verdict,
so the missing route is a real (if low-frequency) path to a confusing failure.

## Current Behavior

Generating a verify loop from a 4-criterion issue and validating it:

```
$ ll-loop validate verify-bug-2803-...
[WARNING] states.verify-criterion-1: LLM-judged prompt routes only on_yes; a
  `partial` verdict has no route and will dead-end the loop ... (ENH-1917)
[WARNING] states.verify-criterion-2: ... (ENH-1917)
[WARNING] states.verify-criterion-3: ... (ENH-1917)
[WARNING] states.verify-criterion-4: ... (ENH-1917)
... is valid
```

One warning per acceptance criterion. Exit code 0.

## Expected Behavior

- A loop generated by either skill validates clean — no MR-4 warnings, no
  suppression flag needed.
- Each synthesized LLM-judged state routes a `partial` verdict explicitly.
- `create-eval-from-issues`' `check_skill` template instructs the generator to
  write an evaluator prompt that satisfies MR-8's evidence contract.

## Root Cause

- **File**: `skills/verify-issue-loop/SKILL.md`
- **Anchor**: Step 4 "Wire Transitions" (`:122`) and the Step 5 YAML template
  (`:177`, `:197`, `:212`)
- **Cause**: the template specifies only `on_yes` and `on_no`. MR-4's check
  (`scripts/little_loops/fsm/validation.py:1653`) is
  `missing = [v for v in ("no", "partial") if getattr(state, f"on_{v}") is None]`
  — it warns unless *both* are routed, so `on_no: failed` alone is not enough.

- **File**: `skills/create-eval-from-issues/SKILL.md`
- **Anchor**: `check_skill` state in the Variant A template (`:279-289`) and
  the Variant B template (`:370-381`)
- **Cause**: same missing `on_partial`. Separately, the evaluator prompt is a
  `<synthesized evaluation criteria from Step 3>` placeholder with no
  requirement that the synthesized text ask for quoted/verbatim evidence, so
  MR-8 (`evidence_contract_ok`) compliance is incidental rather than
  guaranteed.

Note: MR-4's message text ("routes only on_yes") is slightly imprecise when
`on_no` *is* set — worth a one-line wording fix in `validation.py:1660` while
in the area, but the rule itself is behaving correctly.

### Codebase Research Findings

_Added by `/ll:refine-issue` — based on codebase analysis:_

- **Anchor correction**: `create-eval-from-issues`' `check_skill` blocks are at
  `skills/create-eval-from-issues/SKILL.md:280-290` (Variant A) and `:367-381`
  (Variant B), not `:279-289`/`:370-381` as stated above — off by a line or a
  few in each case (line 279 is a blank separator, and Variant B's state
  starts at 367, not 370, which lands inside the `evaluate.prompt` placeholder
  instead of the state's `check_skill:` key). Content described is accurate;
  only the exact ranges need adjusting.
- **MR-4 fix pattern precedent**: the majority pattern across built-in loop
  YAMLs (e.g. `scripts/little_loops/loops/rn-remediate.yaml:131-132`,
  `loop-router.yaml:114-116`, `apply-research.yaml:152-154`) routes `on_no`
  and `on_partial` to the *same* target state, often with a trailing comment
  explaining why partial is treated like no (e.g. `on_partial: execute  #
  ambiguous → retry skill`). This matches Implementation Step 2's proposed
  fix for `create-eval-from-issues`. A smaller set of loops
  (`harness-single-shot.yaml:151-152`, `rn-decompose.yaml:78-80`) route
  `on_partial` to a distinct, lighter-weight state instead — not needed here
  given the "retry" semantics already chosen.
- **MR-8 canonical phrasing available for reuse**: `scripts/little_loops/fsm/
  evaluators.py:61-71` defines `CHECK_SEMANTIC_EVIDENCE_CONTRACT`, the exact
  wording already used elsewhere in the repo to satisfy the evidence-contract
  keyword check (`VERBATIM`, `quote`, `evidence`):
  > "Provide a VERBATIM quote from the output that supports your verdict...
  > Do not assert a verdict without evidence." This phrasing (or a
  paraphrase preserving all three keywords) is the recommended text to
  inject into Step 3 of `create-eval-from-issues`' synthesis instructions,
  rather than inventing new wording.
- **`verify-issue-loop`'s prompt already contains "evidence"**: the template
  at `skills/verify-issue-loop/SKILL.md:106-112`/`:167-175` ends with
  "Provide a one-sentence reason citing the observed evidence," which
  already satisfies MR-8's keyword check today (contains "evidence"). MR-8
  is therefore not actually at risk for `verify-issue-loop` as currently
  written — only `create-eval-from-issues` has a real MR-8 gap. The Expected
  Behavior section's implication that both templates need evidence-contract
  wording added is slightly broader than necessary; `verify-issue-loop`
  only needs the "no MR-4 warnings" half of the fix.
- **No automated regression test exists for skill-template output**:
  `scripts/tests/test_fsm_validation.py` has full unit coverage for the MR-4
  (`TestPartialRouteDeadEnd`, lines 1606-1788) and MR-8
  (`TestLLMEvidenceContractValidation`, lines 3972-4117) *rules themselves*,
  but nothing exercises the actual generated output of `verify-issue-loop`/
  `create-eval-from-issues` end-to-end. Implementation Step 5 ("regenerate
  one loop from each skill and confirm clean validate") is currently a
  manual verification with no test to prevent regression — worth flagging
  as a follow-up if this needs to stay clean long-term, though out of scope
  for this P3 fix.

## Implementation Steps

1. In `skills/verify-issue-loop/SKILL.md`, add `on_partial: failed` alongside
   `on_no: failed` in the Step 5 YAML template and in the Step 4 wiring rules
   (`:122`) and the "Important rules" list (`:212`).
2. In `skills/create-eval-from-issues/SKILL.md`, add `on_partial:` to
   `check_skill` in both variants. Route it the same way as `on_no` (back to
   `execute`) so a partial evaluation retries rather than dead-ends.
3. In `create-eval-from-issues`' Step 3 synthesis instructions, require the
   generated evaluator prompt to include an evidence-contract clause (ask the
   judge to quote the exact observed output verbatim), matching what
   `verify-issue-loop`'s template already does.
4. Optionally reword `validation.py:1660` so the message names the actually
   missing routes rather than asserting "only on_yes".
5. Regenerate one loop from each skill and confirm `ll-loop validate` returns
   clean with no warnings.
