## Summary

A `ll-loop` or verify-issue run that exhausts its budget without succeeding currently produces a cap-hit and little else, discarding attempts that were already paid for in API calls. Two rules fix that, and they are independent of how the failure is classified.

**First, salvage before propagate.** An exception raised inside the attempt batch or the decision step must break the loop with a named abort reason rather than propagating out of it, specifically so every already-paid trace from that unit reaches storage instead of being dropped on the way up. The reason is recorded on the run, so an aborted unit is distinguishable from a completed one.

**Second, never zero checkpoints.** When the budget ends with no acceptance, write the attempt that came closest to the objective as a checkpoint tagged `best_effort`, so every outer iteration produces exactly one artifact on both the success and the no-success path. That is what makes a budget-exhausted run diagnosable — there is something to read — rather than merely labelled.

## Design

The pattern is taken from a production search-loop framework over an expensive stochastic subject, whose failure-handling discipline is stated once and held everywhere: *every failure mode has a designated resting place, and none of them is an exception escaping the loop.* On the no-acceptance path it writes an `iter_<N>_best_effort.json` checkpoint with `metadata.best_effort=True`, on the stated grounds that "every outer iter produces a checkpoint, never zero."

This is a different guarantee from its neighbours and does not overlap them: stopping-rule work changes when the loop stops; failure-classification work decides whether observable work exists; indeterminate-settlement work settles interrupted work as neither passed nor failed. All three decide what to *call* the outcome; none requires the loop to emit a positively-tagged artifact when the outcome is failure. Note the contrast with making a failed context compaction terminal — there, a best-effort result would be silently *wrong*; here the artifact is explicitly tagged and never mistaken for acceptance.

## Program Design

### Types
- `ExecutionResult.terminated_by: str` (`scripts/little_loops/fsm/types.py:59`) — the existing free-form termination-reason field; its docstring (`:35-49`) enumerates the current fixed vocabulary (`"terminal", "max_steps", "max_iterations_reached", "timeout", "interrupted", "user_stopped", "system_signal", "error", "handoff", "cycle_detected", "stall_detected", "host_pressure_abort", "host_budget_exceeded", "workdir_vanished"`) and warns `terminated_by == "terminal"` alone does not imply success (ENH-2814). A "named abort reason" distinguishing an in-attempt-batch exception from an in-decision-step exception is new vocabulary on this same field, not a new field — the codebase's only alternative pattern for a typed reason, `ConsultOutcome.skipped_reason: Literal[...] | None` (`scripts/little_loops/advisor.py:316`), is `Literal`-typed rather than free-form `str`, so which convention to follow is an open choice, not settled by precedent.
- No existing type represents a `best_effort`-tagged checkpoint artifact anywhere in this codebase (confirmed by repo-wide search, see Integration Map → Conventions in Force) — this is new surface area.

### Signatures
- `FSMExecutor._finish(self, terminated_by: str, error: str | None = None) -> ExecutionResult` (`scripts/little_loops/fsm/executor.py:4264`) — the single funnel every stopping condition and every caught exception already calls; it also fires the `loop_runs`/`usage_events` writes.
- `PersistentExecutor.run(self, clear_previous: bool = True) -> ExecutionResult` (`scripts/little_loops/fsm/persistence.py:1212`) — wraps `FSMExecutor.run()` and then calls `StatePersistence.save_state(self, state: LoopState) -> None` (`:502`) and `StatePersistence.archive_run(self, run_dir: Path | None = None) -> Path | None` (`:585`); neither call is exception-guarded except inside the `terminated_by == "workdir_vanished"` branch.
- `record_loop_run_summary(...)` (`scripts/little_loops/session_store/writers.py:1791`) — writer whose `terminated_by`/`error` columns (`loop_runs` table, `scripts/little_loops/session_store/schema.py:573`) are the existing persistence slots a "reason recorded on the run" plugs into.

### Call Path
`FSMExecutor.run()` (cap hit or caught exception) -> `FSMExecutor._finish(terminated_by, error)` -> `record_loop_run_summary()` (writes `loop_runs` row) -> returns `ExecutionResult` -> `PersistentExecutor.run()` (`self.persistence.save_state()` / `self.persistence.archive_run()`, currently unguarded outside the `workdir_vanished` branch) -> `.loops/.history/<run_id>-<loop_name>/`

### Decision Rules
- **Which `terminated_by` values qualify for a "no acceptance" checkpoint** is UNKNOWN — neither the issue nor the codebase specifies it. Not every value is a failure needing salvage (e.g. `handoff`/`user_stopped` are deliberate stops); per the `general-task.yaml` `partial`-terminal precedent (`:1303`, ENH-2575), whichever values qualify must route to a terminal distinct from both `done` and `failed`, since sub-loop routing treats `done` as `on_yes`.
- **"Closest to the objective" selection metric** is UNKNOWN — no shared scoring utility exists (see Integration Map → Conventions in Force); every existing per-loop analog reimplements this independently in a different shape (deterministic `scores.tsv` sort, LLM-narrated score-history read, model self-report), so there is no established comparison rule to reuse generically.
- **Escape hatch**: none specified. The issue's own Design section names the one case where this pattern must NOT apply — context-compaction failure must stay hard-terminal (`scripts/little_loops/hooks/pre_compact.py`, `scripts/little_loops/session_store/lifecycle.py::compact_session()`, called from `scripts/little_loops/cli/compact_session.py::main_compact_session()` with no surrounding try/except) — because compaction's own internal LCM escalation already guarantees a leaf node is produced, so a `best_effort`-tagged partial result there would misrepresent a failure as salvaged.

### Codebase Research Findings

_Added by `/ll:refine-issue` — 2026-09-13 — based on codebase analysis:_

- The attempt-batch/decision-step exception paths are already asymmetric at the call-stack level today, with no stored phase marker: `_run_action_or_route()` (`fsm/executor.py:3773-3801`) wraps action execution and either routes to `state.on_error` (never reaching `run()`'s outer handler) or re-raises; `_evaluate()`/`_route()`/`_resolve_route()` (`fsm/executor.py:3076-3169`, `:3233`, `:3307`) have no exception wrapping of their own. Both the re-raised action exception and the unwrapped decision-step exception land in the same generic `except Exception as exc: return self._finish("error", error=str(exc))` (`fsm/executor.py:1040-1041`) — the distinction exists today only as "which function's frame raised," not as any attribute on `FSMExecutor`.
- `PersistentExecutor._save_state()` (`fsm/persistence.py:1129-1159`) is an existing per-iteration checkpoint mechanism, but it overwrites a single fixed file (`StatePersistence.save_state()`, `:502-523`, atomic `os.replace` over `<running_dir>/<instance_id>.state.json`) on every `state_enter`/`loop_complete`/`baseline_complete` event (`_handle_event()`, `:1010-1096`, `:1064-1066`) — there is no existing per-iteration (`iter_<N>_*.json`-style) accumulation anywhere in `StatePersistence`. A `best_effort`-tagged checkpoint that must survive past the next iteration needs a new write path, not a modification of this one. `usage.jsonl`/`messages.jsonl` (also written from `_handle_event()`, `:1020-1049`/`:1051-1062`) are the actual append-only per-event logs that already accumulate the "already-paid traces" the issue references.
- Exact propagation of a `save_state()`/`archive_run()` exception outside the `workdir_vanished` branch (`persistence.py:1279-1281`, unguarded): `PersistentExecutor.run()` → `run_foreground()` (`cli/loop/runner.py:476`, wrapped only in a `try/finally` with no `except`, `:467-489`) → `cmd_run()` (`cli/loop/run.py:659-673`, `try/finally` only, narrow `except OSError` around an unrelated lock-release at `:678-687`) → `main_loop()` dispatch (`cli/loop/__init__.py:1088`, zero try/except in the file) → the `ll-loop` console-script boundary (`pyproject.toml:84`). Nothing intercepts it anywhere in this chain — it surfaces as a raw traceback with default nonzero exit. `record_loop_run_summary()` (called from `_finish()` inside `FSMExecutor.run()`, which returns before this block runs) already writes its `loop_runs` row before this failure point, so only the filesystem archive step (`state.json`/`events.jsonl` copy into `.loops/.history/`) is lost when this raises — not the DB row.

## Implementation Steps
