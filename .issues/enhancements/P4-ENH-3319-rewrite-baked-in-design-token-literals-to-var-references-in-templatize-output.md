# ENH-3319: Rewrite baked-in design-token literals to var() references in templatize output

## Summary

`ll-artifact templatize`'s `_report_unlifted_tokens` (`templatize.py:717-740`)
only *reports* baked-in color literals matching known design tokens
(`unlifted-tokens.json`) — it never rewrites the spliced template body to
reference `var(--...)` / the artifact template kit's stamping unit
(`artifact_template_kit.themed_css_vars`, ENH-3035). File real
literal→`var(--...)` rewriting as its own feature.

## Current Behavior

`ll-artifact templatize` produces a spliced `.j2` template body via
`apply_regions` (`scripts/little_loops/cli/artifact/templatize.py:474`),
writes it to disk, and verifies it round-trips byte-for-byte against the
original artifact via `verify_round_trip` (`templatize.py:545`). Only after
that verification succeeds does `cmd_templatize` call
`_report_unlifted_tokens` (`templatize.py:717`, invoked at `templatize.py:923`),
which decodes the already-final `spliced` bytes and calls
`report_token_literals` (`templatize.py:662`) to scan for `#`-hex /
`rgb()`/`rgba()`/`hsl()`/`hsla()` literals whose normalized value matches a
resolved design token (`DesignTokens.resolved`). Matches are written to
`unlifted-tokens.json` as `{"literal", "candidate_names", "occurrences"}`
entries — no byte offsets are captured; the regex match spans are read for
`.group(0)` only and discarded — and logged as a warning. The template body
on disk is never modified. `_report_unlifted_tokens`'s entire body is wrapped
in a bare `except Exception` (`templatize.py:717-740`) specifically so
nothing in this step can affect `cmd_templatize`'s exit code or block
`promote()`.

## Expected Behavior

Under an opt-in `--lift-tokens` flag (default off), a baked-in color literal
matching a resolved design token gets rewritten, in the spliced template
body, to a `var(--color-surface-primary)`-style reference at the literal's
own byte span, and the template gains the token block that defines those
vars (`manifest["theme"] = "design-tokens"` plus an injected
`[[= ll.theme_css =]]` expression inside a `<style>` element, so
`build_ll_namespace`'s existing `ll.theme_css` hook supplies the
declarations at render time). With the flag off, behavior is exactly
today's: report-only, fail-open, byte-exact round trip.

**Not `/*__THEMED_CSS_VARS__*/`.** An earlier revision specified that
placeholder. `render_template` never calls
`artifact_template_kit.stamp_page_shell` — its only caller is
`cli/artifact/policy_builder.py:91`, a build-time HTML-assembly path, and
the render path (`artifact_templates.py:311-345`) exposes `ll.theme_css`
and nothing else. A literal `/*__THEMED_CSS_VARS__*/` comment injected into
a templatize-produced body is therefore inert: it survives verbatim into the
rendered artifact, no `:root {}` block is ever emitted, and every lifted
`var()` resolves to nothing. The Jinja delimiters are frozen at
`artifact_templates.py:268-273` (`[[=` / `=]]`), so the stamp point the lift
injects is the expression `[[= ll.theme_css =]]`, wrapped in a `<style>`
element in `<head>`.

**Byte-exact round trip and real token lifting are mutually exclusive.** A
lifted template renders to `var(--...)` references plus a `:root {}` block —
deliberately *not* the original bytes. So `verify_round_trip`
(`templatize.py:545`), which diffs `render_template`'s output against the
original pre-splice artifact bytes, cannot be the check for a lifted
template. See Program Design § Decision Rules for the two-stage verification
that replaces it. Notably this requires **no change to
`ArtifactTemplate`/`render_template`** — see the rejected alternative below.

## Motivation

ENH-3035's Decisions (2026-08-25) explicitly rejected doing this as part of
the template-kit extraction: setting `manifest["theme"] = "design-tokens"`
whenever `_report_unlifted_tokens` finds matching literals would stamp
`theme_css` vars into a body that still carries the literals — unreferenced
vars *and* unlifted literals, not token lifting. Real lifting requires
locating each literal's span in the template body and splicing in a
`var(--...)` reference (or an `[[= ll.theme_css =]]`-style stamp point),
which is new feature work, not the extraction ENH-3035 scoped.

ENH-3035 was right that stamping `theme_css` *alone* is dead weight. This
issue supplies the other half: the stamp point and the literal rewrite land
**together**, or not at all. A body with `var(--...)` refs and no `:root {}`
block renders colorless; a body with a `:root {}` block and no refs is the
unreferenced-vars dead weight ENH-3035 rejected.

### Rejected alternative: a render-time un-lift hook

An earlier revision of this issue proposed adding a design-token-aware
substitution hook to `render_template`/`build_ll_namespace`
(`artifact_templates.py:311-345`) that resolves `var(--color-surface-primary)`
back to `#fdfbf6` at render time, so `verify_round_trip` keeps passing
byte-exact. **Rejected**: if that hook works, the rendered artifact is
byte-identical to today's, i.e. nothing is lifted at render time — the hook's
entire job is to undo the feature. It would also change the shared render
engine for every `.llat` consumer (`extract.py`, `render.py`,
`fsm/persistence.py::promote_run_artifact`, `dashboard.py`) to buy nothing,
and a textual `var()`→literal substitution would corrupt hand-authored
templates that legitimately emit `var(--name, fallback)` in their output CSS
(`templates/policy-router-builder.html.tmpl:18,27`). The two-stage
verification in Program Design § Decision Rules gets the same safety with
zero render-engine blast radius.

### Conventions in Force
- This module's one span-splicing pass (`apply_regions`, `templatize.py:474-511`) sorts `(start, end, kind, obj)` tuples and hard-errors via `SpliceError` on overlap/out-of-bounds rather than best-effort merging. **This issue deliberately does not extend that list** — see Decision Rules § Splice placement. A literal-rewrite span composed into `apply_regions` would be computed against pre-splice bytes and would therefore match literals *inside extracted data regions*, whose spans overlap the corresponding `Region` and hard-error with `SpliceError` on ordinary artifacts. The rewrite is a separate pass over the already-spliced body, reusing `anchor_sweep._sweep_file`'s reverse-order model (`issues/anchor_sweep.py:59`), the second established span-splicing convention this codebase already carries.
- Splice/round-trip tests assert exact byte equality and error paths via `pytest.raises(SpliceError, match=...)` — evidence: `test_artifact_templatize.py::TestApplyRegions` (`:208-325`).
- Literal matching in this codebase is regex-based over rendered text plus a normalization step (`_normalize_color_value`/`_normalize_hex`), not AST/CSS parsing — evidence: `templatize.py:622-695`.
- A report-only feature graduating to an active rewrite is **filed** as a separate issue — evidence: ENH-3035's Decisions (2026-08-25) explicitly deferred this rewrite to a new ENH (this issue), rejecting a `manifest["theme"]`-stamping shortcut as "dead weight, not token lifting." Note this convention governs *where the work is filed*, not *whether the runtime gates it*; an earlier revision of this issue read it as an argument against a CLI flag, which is a non-sequitur. Both hold: separate issue **and** default-off `--lift-tokens`.
- **The stamp point emits raw CSS only because `build_environment` sets `autoescape=False`** (`artifact_templates.py:279`, inside the frozen-delimiter environment at `:259-279`). `[[= ll.theme_css =]]` interpolates `render_as_css_vars_themed`'s output verbatim; under autoescaping the `{`/`}`/quote characters in that blob would be entity-escaped and every declaration would be inert. The setting is frozen (changing it is a template-format version bump, per that function's docstring), so this is a dependency to record rather than a risk to mitigate — but `--lift-tokens` is a second consumer of that freeze, alongside the byte-exact round trip it was frozen for.
- A documented output guarantee is not changed unconditionally under an existing flagless invocation — the byte-exact round-trip guarantee is stated in `docs/ARCHITECTURE.md:1031` and `docs/reference/CLI.md:4593`, and `fsm/persistence.py::promote_run_artifact` depends on today's behavior with no way to opt out.

A token whose two values coincide makes the assertion pass against the `:root` block too and proves nothing.
- **Var-name/declaration agreement**: for each lifted token, the emitted `var(--x)` name appears verbatim as a `--x:` declaration in `render_as_css_vars_themed`'s output — catches drift from the `.`→`-` mangling at `design_tokens.py:703`.
- **Textual-inverse false rejection**: a source artifact already containing `var(--color-surface-primary)` lifts successfully (a whole-body textual inverse would reject it with exit code 2).
- **Alias-preference ambiguity**: `#e8dcc4` (one alias, one primitive) lifts to `color.border.subtle`; `#fdfbf6` under the light theme (two aliases) stays unlifted with both candidates reported.
- **Hard preconditions — one test each, five in total**: no `<head>`/`<style>`; no root `<html>` (a `<style>`-carrying fragment); a `data-theme` disagreeing with the active theme; `active_theme: sepia` (a real third theme file, which `render_as_css_vars_themed` has no scope for); and a config whose `themed_css_vars` output does not declare every var name the lift would emit. Cover precondition 5 with **two** cases, since name coverage is strictly broader than the degenerate check it replaced: (a) no tokens configured at all, so `themed_css_vars` returns the empty-blocks fallback and declares nothing; (b) tokens that load and emit a non-degenerate blob which nonetheless lacks a declaration for a name the lift matched — the case an exact-string degeneracy check passes and this one catches. All five leave the body entirely unlifted with an unchanged manifest and exit code. **Plus a sixth test on precondition 5's exception path**: a malformed `themes/<active>.json` makes `themed_css_vars` raise a `JSONDecodeError`, and the assertion is that `cmd_templatize` still exits **0** with an unlifted body — not exit 1 via the outer `except Exception`.
- **Promoted output actually carries the lift** (guards AC #13): assert against the *promoted* `out_dir`, not just in-memory state — `manifest.yaml` on disk contains `theme: design-tokens` and `template.*.j2` on disk contains the `var(--…)` refs. Fails if step 6's re-serialization is omitted, which no span-level test detects.
- **Theme-layer alias override**: a token whose semantic layer declares an alias and whose theme layer overrides it with a concrete literal (or the reverse) resolves to the candidate the *layered* raw value implies, not the semantic-only one.
- Unreversible lift → `rejected_dir` / exit code 2, under `--lift-tokens` only. Follow `TestApplyRegions`'s `pytest.raises(SpliceError, match=...)` pattern composed with `TestCmdTemplatizeEndToEnd`'s CLI-level `code == 2` assertions.
- **CSS-context guard (highest-value new coverage)**: an artifact carrying `href="#dedede"`, an id selector `#face {` inside a `<style>` that also contains an `a:hover` rule, and `"#c0ffee"` inside a `<script>` string, where those values are also resolved token values — assert none are rewritten and all are still reported. The `a:hover` is not decoration: it is what distinguishes the correct nearest-preceding-delimiter rule from the "some colon appears earlier" phrasing that would rewrite the selector. Today these are harmless warning lines; after the rewrite an unguarded match is silent artifact corruption, and the two-stage verification will *not* catch it (the inverse map restores it cleanly).
- **Presentation-attribute under-lift is deliberate, not a bug**: an artifact with an inline `<svg>` carrying `fill="#fdfbf6"` (a resolved token value) leaves it unrewritten and reports it in `unlifted`. Pins the accepted v1 limitation (Decision Rules § CSS-context guard → Known under-lift) so a later reader sees it was decided rather than overlooked, and so extending the guard to an attribute allowlist is a visible, deliberate change to this assertion.
- **CSS-value-position acceptance (the guard's other half)**: `box-shadow: 0 0 2px #e8dcc4, 0 0 4px #000;`, `background: #fdfbf6 url(…)`, and `color: #fdfbf6 !important;` all lift. Without these, a guard tightened only against corruption silently under-lifts the border/shadow/gradient colors that make up much of the feature's value.
- Ambiguous literal-to-token-name resolution (AC #5): candidates surviving the alias-preference filter, not the raw candidate count, decide (see the alias-preference bullet above). `test_non_injective_reports_all_candidate_names` (`:1005-1011`) covers only today's report-all behavior and stays unmodified.
- Flag-off regression: an artifact full of matching literals produces byte-identical output and an identical `unlifted-tokens.json` to today's.

## Program Design

### Codebase Research Findings

_Added by `/ll:refine-issue` — 2026-08-25 — based on codebase analysis:_

- **Coordinate-space mismatch (new — not yet reflected in Call Path above)**: `report_token_literals` scans `template_text`, which `_report_unlifted_tokens` decodes from `spliced` (`templatize.py:923`) — i.e. the body *after* `apply_regions` has already run. Its match offsets are therefore in post-splice coordinate space. `apply_regions`'s `Region`/`RegionGroup` spans (`start`/`end`) are byte offsets into the **original pre-splice** `artifact` bytes. A literal-rewrite span cannot be added to `apply_regions`'s existing sorted span list as-is — it must either be computed against the pre-splice artifact bytes directly (a literal-detection pass before `apply_regions` runs), or explicitly translated from post-splice to pre-splice offsets.
- `Region`/`RegionGroup` (dataclasses, `templatize.py`): `Region(start: int, end: int, expr: str, group: str | None, anchor_before: str | None, anchor_after: str | None)`; `RegionGroup(id: str, binding: str, array_path: str, start: int, end: int, iterations: list[tuple[int, int]])` — the concrete shapes `apply_regions` sorts and splices; a literal-rewrite span would need an equivalent shape (or reuse `Region` with a synthetic `expr`).
- Ambiguity-resolution precedent (extends Decision Rules below): no "canonical name" concept exists in `design_tokens.py` (zero hits). Two contested precedents apply from elsewhere, and they disagree: (a) `DesignMdColorCollisionError` (`design_tokens.py:747-770`) is a fail-closed collision guard, but in the reverse direction (name→export-name collisions, raised during DESIGN.md export) — not literal→name selection. (b) `text_utils.classify_file_ref`/`suffix_match_candidates` (`text_utils.py:269-364`) returns an explicit `"ambiguous"` status when more than one candidate remains after a documented filter step, rather than picking one. Neither establishes a pick-first/alphabetical priority rule.

### Call Path

Flag off (default) — **unchanged from today**:
`cmd_templatize` -> `apply_regions` -> `verify_round_trip` -> `_report_unlifted_tokens` (fail-open) -> `promote`.

Flag on (`--lift-tokens`):
`cmd_templatize` -> `apply_regions` (produces `spliced`) -> `verify_round_trip(spliced)` **byte-exact against the original, exactly as today** -> `lift_token_literals(spliced)` -> `verify_lift_reversible(lifted, spliced)` -> write lifted body + `theme: design-tokens` manifest into `tmp_dir` -> `verify_lift_renders(tmp_dir)` -> `_report_unlifted_tokens` (now reporting `lifted` + `unlifted`) -> `promote`.

A failure in any stage routes through the existing `rejected_dir`/exit-code-2 path. The third stage must run *after* the step-6 re-serialization, since reading `tmp_dir` from disk is exactly what makes it catch a skipped re-serialization.

`_report_unlifted_tokens`'s bare `except Exception` (`templatize.py:717-740`) stays exactly as-is: it remains a pure reporting step in both modes. The steps that *can* fail closed (`lift_token_literals`, `verify_lift_reversible`) are new siblings placed before it, not modifications to it — so the fail-open contract and the fail-closed rewrite coexist rather than conflict, and `test_containment_forced_failure_still_promotes_exit_0` keeps passing untouched.

### Decision Rules
- **Splice placement**: the lift is a **separate pass over the already-spliced body**, not a span added to `apply_regions`'s list. Rationale: (1) a pre-splice literal detection finds literals *inside extracted data regions*, which are not part of the template body at all, and whose spans overlap the corresponding `Region` → `SpliceError` on ordinary artifacts; (2) post-splice detection excludes them for free; (3) it dissolves the coordinate-space mismatch documented above rather than requiring offset translation. Apply collected `(start, end, replacement)` spans in **reverse order**, per `issues/anchor_sweep.py:59`. This supersedes the earlier "must compose into `apply_regions`" convention claim.
- **Var-name derivation**: the emitted reference is `var(--{name.replace(".", "-")})` over the **full dotted token path** — `color.surface.primary` → `var(--color-surface-primary)`. This is the same mangling `render_as_css_vars_themed:703` uses to emit the declaration, and the two must not drift; a test asserts the emitted reference appears verbatim in `render_as_css_vars_themed`'s output for the same token. Names beginning with `_` are excluded from the candidate map entirely, mirroring the metadata skip at `:701-702` — a `var()` referencing a `_`-prefixed name would never be declared. (Earlier revisions of this issue wrote `var(--surface-primary)`; that property does not exist.)
- **Ambiguous literal-to-token mapping — alias-preference filter, then fail-closed**: a naive ">1 candidate ⇒ skip" rule blocks **11 of 22 light and 12 of 22 dark colors** on this repo's own profile, and blocks precisely the semantic tokens the feature exists to lift (see Codebase Research Findings above). The cause is structural: every semantic token is declared as an alias (`"{color.paper.0}"`), so it *always* resolves equal to its primitive and *always* collides with it. Rule:
  1. Filter the candidate list to names whose **raw, pre-resolution** value is an alias reference (`{...}`) — i.e. prefer the semantic name over the primitive it points at. A `var(--color-surface-primary)` is the reference an artifact should carry; `var(--color-paper-0)` is the implementation detail behind it.
  2. If exactly one candidate survives, rewrite to it.
  3. Otherwise (zero aliases, or two-or-more aliases — e.g. light `#fdfbf6` → both `color.surface.primary` and `color.text.inverse`) **do not rewrite**; report in `unlifted` with all candidates, as today.
  Rationale for still failing closed at step 3: no "canonical name" concept exists in `design_tokens.py`, and `text_utils.classify_file_ref`'s explicit `"ambiguous"` status (`text_utils.py:269-364`) is the governing precedent for a genuinely undecidable choice. Step 1 is not a pick-first heuristic — it is a structural fact about the token graph, and it must read the raw layered data (`DesignTokens.semantic`/`.theme`), not `resolved`, which has already erased the alias.
  **Reading the raw layers correctly**: unlike `.resolved` (a flat dotted-name→value map, `design_tokens.py:35`), `DesignTokens.semantic` and `.theme` are **raw nested dicts** (`:33-34`) straight from the JSON files. The filter must flatten them with the loader's own `_flatten` and apply the **same layer order the loader uses**. Mirror all four layers verbatim — `_flatten(semantic)`, `_flatten(typography)`, `_flatten(spacing)`, `_flatten(theme_data)` in that order (`design_tokens.py:376-381`) — rather than the two colour-bearing ones. Typography and spacing carry no colors in the shipped `warm-paper` profile, but copying the loader's merge order verbatim costs nothing and cannot drift if that ever changes. Order matters, and not only for tidiness: a theme file may override a semantic alias with a **concrete literal** (or vice versa), which flips that name's alias status and therefore flips which candidate wins. Testing `semantic` alone would pick the pre-override answer. The predicate is: the effective raw value for this name, after layering, is a string of the form `{...}`.
  **Primitives are absent from every raw layer — treat missing as non-alias.** `resolved` is not built from the layered map alone: after `_resolve_references`, the loader injects primitive leaf values directly (`design_tokens.py:381-383`, `for k, v in primitives_flat.items(): if k not in resolved`). So a candidate name like `color.paper.0` is present in `resolved` and in `_flatten(tokens.primitives)`, but in **neither** `semantic` nor `theme`. The predicate must therefore be a `.get(name)` returning "not an alias" for an absent name, never a `KeyError` or a lookup against `primitives`. This is exactly the behavior the filter wants — a primitive is the implementation detail the semantic alias points at — but it must be written deliberately rather than falling out of an unguarded dict access.
- **Theme selection — mandatory, or the lift inverts the artifact's colors**: `report_token_literals` calls `load_design_tokens(config)` with no `theme=`, which resolves against `dt_cfg.active_theme` (`design_tokens.py:370`) — `dark` in this project. But `themed_css_vars`/`render_as_css_vars_themed` put the **light** values in `:root` and dark under `[data-theme=dark]`, and a templatize-produced body has no `data-theme` attribute. Left alone, a dark-authored artifact would lift its dark literals and then render light. The reversibility check (below) cannot detect this — it applies the same resolved map on both sides, so the substitution round-trips perfectly while the *rendered* artifact flips theme.
  Resolution: the lift pass loads tokens with an **explicit** `theme=`, and the lifted body's root element carries the matching `data-theme` attribute. Concretely: lift against `dt_cfg.active_theme`, and inject `data-theme="<active_theme>"` on `<html>` alongside the `[[= ll.theme_css =]]` stamp. If the body already carries a `data-theme` attribute whose value differs from the active theme, **do not lift** (route to `unlifted` with a reason) rather than rewriting the author's attribute. A test asserts a dark-active lift emits the lifted declarations in the `[data-theme=dark]` block with the original artifact's literal values (see § Declaration agreement is textual, not computed).
- **`active_theme` must be `light` or `dark` — otherwise refuse to lift**: `design_tokens.active_theme` is a **free-form string** in the config schema (`config-schema.json:1851-1855` — "name of the active theme file (without .json extension) under themes_dir"), so a project may legitimately run `active_theme: sepia` with a `themes/sepia.json`. But `render_as_css_vars_themed` (`design_tokens.py:688-707`) emits exactly **two** scopes, `:root` (light) and `[data-theme=dark]` (dark) — there is no third. Lifting under `active_theme: sepia` would resolve the literals against the sepia palette, inject `data-theme="sepia"`, and then render with the **light** `:root` values, because `[data-theme=sepia]` matches no emitted block. This is the same color inversion the rule above prevents, arriving through a different door, and neither the reversibility check nor the `data-theme`-agreement check sees it. Rule: the lift proceeds only when `dt_cfg.active_theme` is `light` or `dark`, **or** `tokens.source == "design_md"` (no theme mechanism at all — `themed_css_vars` sets `dark = light` at `artifact_template_kit.py:44`, both scopes are identical, and the attribute is inert). Any other `active_theme` value ⇒ no lift, per § Hard preconditions.
- **Declaration source, and the render-time availability hole — decided, revisitable**: the declarations come from `[[= ll.theme_css =]]`, i.e. `themed_css_vars(config)` evaluated **at render time, against the rendering project's config** (`artifact_templates.py:311-318`). This is not the same guarantee as the lift-time check. `themed_css_vars` degrades to `":root {\n}\n[data-theme=dark] {\n}"` — two *empty* blocks — whenever the rendering context has no tokens configured (`artifact_template_kit.py:38-49`), and a `.llat` directory is portable: `render.py`, `extract.py`, and `fsm/persistence.py::promote_run_artifact` may re-render it later, potentially in a project with no design tokens. In that case every lifted `var()` resolves to nothing and the artifact renders **colorless**, with no error. AC #12's all-or-nothing guarantee is a *templatize-time* guarantee and cannot cover this.
  Decision for v1: keep `[[= ll.theme_css =]]` (it is the hook ENH-3035 built, and it costs zero render-engine change, preserving AC #7), and close the near half of the hole with a lift-time precondition — **refuse to lift unless every var name the lift would emit is actually declared in `themed_css_vars(config)` at lift time** (see § Hard preconditions, precondition 5, which covers the degenerate empty-blocks fallback and the no-tokens-configured case as instances of missing coverage). The residual — a lifted `.llat` re-rendered in a *different*, token-less project — is accepted and must be **documented** in both `docs/reference/CLI.md` and `docs/ARCHITECTURE.md` as a stated limitation of `--lift-tokens`, not left implicit.
  Recorded alternative, if portability later outranks token-liveness: snapshot the frozen `render_as_css_vars_themed` output into the template as `assets/design-tokens.css` and reference it with `[[= ll.assets['design-tokens.css'] =]]`. `load_assets` (`artifact_templates.py:307`) is unconditional and needs no `manifest["theme"]`, so this is also a zero-render-engine-change path; it makes the template fully self-contained and immune to the hole above, at the cost that a re-render no longer picks up edits to the project's tokens. Not chosen for v1 — flip to it only as a deliberate decision, since it changes AC #2's asserted mechanism.
- **Declaration agreement is textual, not computed**: `render_template` returns a *string*; there is no CSS cascade in this test environment, so "the ref resolves to the value the original artifact had" is not a checkable assertion. The checkable form, and the one the ACs state: for every lifted token `x`, the rendered output contains the declaration `--x: <the original literal>;` inside the scope block that matches the injected `data-theme` — `[data-theme=dark] {` for a dark lift, `:root {` for a light one (or for a `design_md` source, where both blocks carry the same values).
- **Injection happens after delimiter escaping, by construction**: `apply_regions` runs `escape_literal_delimiters` over every non-region byte range (`templatize.py:497,510`). Because the lift is a post-splice pass, the injected `[[= ll.theme_css =]]` is *not* escaped and stays a live Jinja expression. Moving literal detection or injection to a pre-splice position would silently escape the stamp point into inert text — a second route to the colorless-artifact failure in § Impact/Risk 2.
- **Emit bare `var(--name)`, not the two-argument `var(--name, #literal)` fallback form** — decided, revisitable. The two-arg form (precedent: `templates/policy-router-builder.html.tmpl:18,27`) would make a failed stamp degrade gracefully instead of rendering colorless. Rejected for v1 because it leaves the literal in the body, so a re-run of `templatize` re-reports every already-lifted literal as `unlifted` — the report contradicts itself — and the inverse map must then distinguish "fallback literal I emitted" from "literal I failed to lift". The graceful-degradation need is met instead by the hard preconditions below: no stamp point placeable ⇒ no lift at all, so a colorless render is unreachable.
- **CSS-context guard — mandatory**: `_HEX_LITERAL_RE = r"#[0-9a-fA-F]+"` (`templatize.py:625`) has no word boundary and no context check. It matches `href="#dedede"`, an id selector `#face`, and `"#c0ffee"` in a JS string. Today a false positive is a harmless warning line; **under rewriting it is silent artifact corruption**, and the reversibility check will not catch it because the inverse map restores it cleanly. Rewrites therefore fire **only in CSS-value position**. An earlier revision defined that as "inside a `<style>` element or a `style="…"` attribute, after a `:` and before a `;`, `}`, `)`, or the attribute's closing quote" — that phrasing is wrong in both directions and must not be implemented as written:
  - **False positive it admits.** In `<style> a:hover { color: red } #face { … } </style>`, the selector `#face` *is* "after a `:`" (from `:hover`) and *is* "before a `}`". The rule as phrased rewrites it — precisely the corruption AC #3 exists to prevent.
  - **False negatives it creates.** The terminator list omits `,`, whitespace, and `!`, so `box-shadow: 0 0 2px #e8dcc4, 0 0 4px #000;`, `background: #fdfbf6 url(…)`, and `color: #fdfbf6 !important;` all go unlifted. Border, shadow, and gradient colors are a large share of what this feature exists to lift, so this is not a cosmetic gap.

  **The rule to implement**, scope test first, then position test:
  1. **Scope**: the match lies inside a `<style>…</style>` element or inside the value of a `style="…"` attribute. (This alone rejects `"#c0ffee"` in a `<script>` and `href="#dedede"`.)
  2. **Position**: scanning backwards from the match start to the nearest character in the set `{ ':', ';', '{', '}' }`, that character is `:`; **and** scanning forwards from the match end to the nearest character in `{ ';', '}', '{' }`, that character is `;` or `}`.

  Formulating it as "nearest preceding delimiter is a colon" rather than "some colon appears earlier" is what rejects the `#face` selector case: a `{` or `}` intervenes between `:hover`'s colon and the selector. Formulating the forward test against `{ ';', '}', '{' }` rather than an enumerated terminator set is what admits the `,`/whitespace/`!important` value forms, since it constrains where the *declaration* ends rather than what character immediately follows the literal. Within a `style="…"` attribute the closing quote bounds the search and is treated as a `;`.

  A match outside CSS-value position is reported (today's behavior) and never rewritten.

  **Known under-lift: color-valued presentation attributes, chiefly inline SVG.** The scope test (part 1) admits only `<style>` elements and `style="…"` attributes, so `<rect fill="#fdfbf6">`, `stroke="…"`, `stop-color="…"`, and `<meta name="theme-color" content="…">` are rejected and stay permanently in `unlifted`. These are genuine design-token colors in a genuine color-valued position — this is not the `href="#dedede"` false-positive class the guard exists to reject — and inline SVG is common in the artifacts this command templatizes, so the gap is not hypothetical. **Decision for v1: accept the under-lift**, keep the scope test to the two CSS contexts, and record it in Scope Boundaries and the doc updates so it is a stated limitation rather than an accident of the guard's phrasing. Rationale: an attribute allowlist is a second, differently-shaped matching rule (whole-attribute-value equality, no delimiter scan) with its own false-positive surface, and it can be added later without disturbing anything specified here. Revisit by extending part 1 with an allowlist of attribute names whose entire value must be a single color literal — `fill`, `stroke`, `stop-color`, `flood-color`, `lighting-color`, `bgcolor`, and `content` on `<meta name="theme-color">` — never by loosening the delimiter scan.
- **Scope**: the rewrite inherits `report_token_literals`'s v1 scope verbatim — **colors only** (`#rgb`/`#rgba`/`#rrggbb`/`#rrggbbaa` plus `rgb()`/`rgba()`/`hsl()`/`hsla()`). `space`, `radius`, `font`, and bare-number token namespaces are out of scope and are neither reported nor rewritten.
- **Reversibility (replaces "round-trip compatibility") — span-tracked, not textual**: a lift is valid iff undoing it reproduces the verified pre-lift body byte-for-byte. The inverse is applied **only at the spans the lift itself recorded**, and additionally removes the injected stamp block (the `<style>[[= ll.theme_css =]]</style>` insertion and the `data-theme` attribute, both recorded as spans at injection time). Two reasons this cannot be a whole-body textual `var()`→literal substitution, as an earlier revision specified:
  1. The lifted body is not the pre-lift body plus var-substitutions — it also gained the stamp block. A var-only inverse can never reproduce the pre-lift bytes, making the check unsatisfiable by construction.
  2. A textual inverse also rewrites `var(--name)` occurrences that were **already present in the source artifact** — hand-authored artifacts legitimately emit `var()` (the `policy-router-builder.html.tmpl:18,27` precedent this issue cites elsewhere) — turning them into literals and diverging from the pre-lift body. That is a spurious exit-code-2 rejection of a perfectly valid lift.
  The check remains self-contained inside `templatize.py` — no render-engine participation, no new hook in `ArtifactTemplate`/`render_template`. What it actually proves is that the span application is correct and total; it deliberately does **not** prove CSS-context correctness (that is the guard's job) or theme correctness (that is the theme rule's job). The lifted template's *rendered* output is deliberately not byte-identical to the original artifact (it carries `var()` refs plus a `:root {}` block from `ll.theme_css`); that difference is the feature, not a regression.
  Note this check is **near-tautological by construction** — it undoes spans the lift itself just recorded, so it catches span arithmetic and nothing else. It is cheap and worth keeping, but it is the *weaker* of the two post-lift checks; the load-bearing one is § Post-lift render verification below.
- **Post-lift render verification — a runtime check, not just a test (mandatory)**: Impact § Risk 2 (inert stamp point ⇒ colorless artifact) and § Risk 4 (lifted body never re-serialized ⇒ pre-lift template promoted at exit 0) are both **silent in production**: every span-level assertion and `verify_lift_reversible` stay green, the exit code stays 0, and the defect surfaces only in the AC #2 render-through *test*. Guarding the two highest-impact failure modes with test coverage alone is not enough — the same omission in a later refactor ships a broken artifact.
  Rule: under `--lift-tokens`, after step 6 has re-serialized `template.{suffix}.j2` and `manifest.yaml` into `tmp_dir` and **before** `promote()`, `cmd_templatize` re-renders the lifted `tmp_dir` and asserts one property of the output string:

  **For every `var(--x)` reference the lift emitted, the declaration `--x:` appears in the rendered output.** This single assertion catches a missing/degenerate `ll.theme_css`, a `manifest["theme"]` that never reached disk, var-name mangling drift, **and** an unevaluated or escaped stamp point (an inert stamp emits no declarations at all).

  **Do not also assert "no residual `[[=`/`[[%` in the rendered output"** — an earlier revision specified that as a second check, and it spuriously rejects valid lifts. `escape_literal_delimiters` (`templatize.py:327-339`) exists precisely so a source artifact containing `[[=`/`[[%`/`[[#` survives templatize: it wraps each occurrence in `[[% raw %]]…[[% endraw %]]`, which renders back as **literal `[[=` text in the output**. Any artifact that mentions Jinja/template delimiters — plausible in this repo, whose artifacts document this very template format — would render output containing `[[=` and get exit code 2 plus a `rejected_dir` for a perfectly good lift. This is the same false-rejection class as the whole-body textual `var()` inverse rejected in § Reversibility ¶2. The declaration check above already covers the inert-stamp-point failure mode that the delimiter check was meant to catch, so the correct move is to drop it, not to weaken it.

  If a delimiter check is nonetheless wanted as belt-and-braces, the only safe form is a **delta** against the pre-lift render: `rendered_lifted.count("[[=") == artifact_bytes.decode("utf-8").count("[[=")`. That comparison is sound because stage 1 (`verify_round_trip`) has already proven the pre-lift render is byte-equal to `artifact_bytes`, so the original artifact's own delimiter count is the correct baseline. A bare "count == 0" is not.

  Failure routes to `rejected_dir` with exit code 2, exactly like the other two verification stages. Implementation is cheap: `verify_round_trip` (`templatize.py:545-556`) already performs precisely this `load_manifest` → `ArtifactTemplate` → `render_template` sequence — the new check is that sequence minus the `difflib` comparison, and should be factored to share it. It also re-validates the mutated manifest through `load_manifest` for free, confirming `theme: design-tokens` survives the re-dump (`_dump_manifest_yaml` is `yaml.safe_dump(..., sort_keys=False)`, so the appended key serializes last and cleanly — `templatize.py:962-965`).
  This promotes AC #11 and AC #13 from test-only assertions to enforced runtime invariants; their tests stay, now exercising a guard that also holds in production.
- **Hard preconditions — no partial lift**: the body is lifted only if **all five** hold:
  1. The `[[= ll.theme_css =]]` stamp point can be placed — a `<head>` or an existing `<style>` element exists.
  2. A **root `<html>` element exists** to carry the injected `data-theme` attribute. The `<head>`/`<style>` check does not imply this: a fragment, or a body destined to be wrapped by a host shell, can carry a `<style>` and no `<html>`. Without the attribute a dark lift renders against `:root` (light) — Risk 3 again, through a third door.
  3. The body carries no `data-theme` attribute whose value disagrees with the active theme (§ Theme selection).
  4. `dt_cfg.active_theme` is `light` or `dark`, or `tokens.source == "design_md"` (§ `active_theme` must be `light` or `dark`).
  5. **Every `var(--x)` the lift would emit has a matching `--x:` declaration in `themed_css_vars(config)` evaluated at lift time.** This is the lift-time mirror of AC #15's render-time check, and it is deliberately *not* the exact-string comparison against the degenerate fallback `":root {\n}\n[data-theme=dark] {\n}"` that an earlier revision specified. Two reasons that phrasing was wrong: (a) it is brittle — it breaks silently the moment `artifact_template_kit.py:38-49`'s fallback text is reworded, since a reworded fallback is no longer `==` the pinned literal and the precondition starts passing on exactly the case it exists to reject; (b) it is too weak — a project whose tokens load fine but declare **none** of the names the lift wants to emit produces a non-degenerate string and passes, then renders colorless anyway. Name coverage subsumes the degenerate case for free (empty blocks declare nothing, so coverage fails on the first emitted name) and also subsumes the otherwise-unlisted "`load_design_tokens(config)` returns `None`, no tokens configured at all" case, which reaches the same empty-blocks return (`artifact_template_kit.py:38-41`). Evaluate coverage against `themed_css_vars`'s output text, not against `tokens.resolved` — the point is to check the blob that will actually be interpolated at render time, including `render_as_css_vars_themed`'s `_`-skip and `.`→`-` mangling, rather than to re-derive it. Lifting against a token set that cannot emit the needed declarations produces a colorless artifact immediately, not just on a later re-render (§ Declaration source).
     **Evaluate this precondition inside a `try`/`except Exception`, treating a raised exception as a failed precondition** (no lift, `lift_skipped_reason` set, exit code unchanged). `themed_css_vars` does not only return the degenerate string — it can *raise*: `_load_json` (`design_tokens.py:79-83`) returns `{}` for a missing file but calls `json.load` unguarded, so a malformed `themes/light.json` or `themes/dark.json` propagates a `JSONDecodeError` out of `load_design_tokens`. Unguarded, that escapes into `cmd_templatize`'s outer `except Exception` and converts a "this project can't be lifted" case into **exit 1**, which is a different and much worse outcome than the no-lift-exit-0 this precondition is specified to produce. Note the guard is needed for the *raise* path only: a merely **missing** theme file yields `{}` and is self-consistent (the lift and `render_as_css_vars_themed`'s corresponding block both fall back to the semantic-layer values), so it is not a hole and must not be treated as one.
  If any fails, nothing is rewritten, the manifest is untouched, everything is reported as `unlifted`, `"lift_skipped_reason"` names the failed precondition (a **payload-level** key, not a field on `UnliftedToken` — see § Types), and the exit code is unchanged — a body with `var()` refs and no declarations must never reach `promote()`.
- **Stamp insertion position — pinned, because it is observable**: the injected `<style>[[= ll.theme_css =]]</style>` goes **immediately after the `<head>` open tag, ahead of every author `<style>`**. Position is not a free choice: `render_as_css_vars_themed` emits `:root { … }` declarations, and an artifact's own `<style>` may declare `:root { --color-…: … }` too. Same selector, same specificity ⇒ source order decides. Injecting first means author declarations override the token block; injecting last means the token block silently clobbers whatever the artifact author wrote. The former is the correct default and the one this issue specifies. (In the alternative branch — prepending `[[= ll.theme_css =]]` at the top of an *existing* `<style>` — the same rule already holds by construction.)

- **Priority**: P4 — nothing is blocked on it. `templatize` output is usable
  today; lifting makes it *themeable*, which is a quality improvement over
  the ENH-3035 baseline rather than a gap.
- **Effort**: Large — ten implementation steps across a CLI flag, a new
  span-splicing pass, a CSS-context guard, an alias-preference candidate
  filter, explicit theme handling, a span-tracked and render-verified
  three-stage verification, a report schema change, and two doc updates, plus
  roughly eighteen new tests. Not the "expose spans and splice" Small the
  first revision implied. The change does, however, touch exactly **one**
  source file — `templatize.py`; `cli/artifact/__init__.py` needs no edit
  (AC #7) — so the size is depth in one module, not breadth across the CLI.
- **Risk**: Medium-High. Four failure modes, none of which the reversibility
  check can see — but modes 2 and 4 are now caught at **runtime** by the
  post-lift render check (AC #15), not merely by tests:
  1. The unguarded hex regex (Decision Rules § CSS-context guard) — a false
     positive silently corrupts a promoted artifact. Mitigated by landing the
     guard before the rewrite (step 2).
  2. Wrong stamp mechanism — an inert placeholder ships a colorless artifact
     while every span-level test still passes. Mitigated by the runtime
     post-lift render check (AC #15), which refuses to promote a body whose
     rendered output lacks a declaration for an emitted `var()` — an inert or
     escaped stamp point emits no declarations, so that one assertion covers
     it — plus the render-through-`render_template` test.
  3. Theme inversion (Decision Rules § Theme selection) — a dark artifact
     rendering with the light palette. Reachable three ways: an implicit
     `theme=` load, a missing root `<html>` to carry `data-theme`, and an
     `active_theme` outside `{light, dark}` that matches no emitted scope.
     Mitigated by the explicit `theme=` load, the `data-theme` injection, and
     preconditions 2 and 4.
  4. Lost lift (new) — the lifted body and `theme: design-tokens` manifest
     are never re-serialized before `promote()`, because both files are
     written at `templatize.py:901,903` ahead of the verification the lift
     follows. Ships the pre-lift template at exit 0 with every span-level and
     reversibility test green. Mitigated by the runtime post-lift render check
     (AC #15), which reads `tmp_dir` back from disk and so cannot pass against
     in-memory-only state, plus the render-through and promoted-output tests.
  `--lift-tokens` defaulting off bounds all four. A fifth failure mode —
  render-time token unavailability producing a colorless artifact — is
  *accepted and documented* rather than mitigated (Decision Rules
  § Declaration source, AC #14).
- **Breaking Change**: No, given `--lift-tokens` defaults off. It would be
  yes without the flag — the byte-exact round-trip guarantee is documented in
  `docs/ARCHITECTURE.md:1031` and `docs/reference/CLI.md:4593`, and
  `fsm/persistence.py::promote_run_artifact` depends on it with no opt-out.

## Scope

**In scope:**
- Colors only, matching `report_token_literals`'s v1 scope
  (`#rgb`/`#rgba`/`#rrggbb`/`#rrggbbaa`, `rgb()`/`rgba()`/`hsl()`/`hsla()`).
- Rewriting matched literals to `var(--...)` in CSS-value position only,
  under an opt-in `--lift-tokens` flag.
- Injecting the token-declaration block (`[[= ll.theme_css =]]` in a
  `<style>`, `data-theme="<active_theme>"` on `<html>`, and
  `manifest["theme"] = "design-tokens"`) so the emitted refs resolve — the
  rewrite and the stamp point land together or not at all.
- An alias-preference filter plus fail-closed remainder for ambiguous
  literal→name matches (Decision Rules).
- Explicit theme selection so a lifted artifact renders in the theme it was
  authored in.
- Two-stage verification: byte-exact round trip on the pre-lift body, then
  span-tracked reversibility of the lift.

## Scope Boundaries

**Out of scope:**
- Any change to `ArtifactTemplate`/`render_template` or the shared `.llat`
  render path (see Motivation § Rejected alternative).
- Non-color token namespaces (`space`, `radius`, `font`, bare numbers).
- Color literals in **presentation attributes** rather than CSS — inline SVG
  `fill`/`stroke`/`stop-color`, `bgcolor`, `<meta name="theme-color">`. The
  CSS-context guard's scope test admits only `<style>` elements and
  `style="…"` attributes, so these are reported and never rewritten. An
  accepted v1 under-lift, not a false-positive rejection; see Decision Rules
  § CSS-context guard → Known under-lift for the revisit path.
- Cross-notation color equivalence (`#ff0000` vs `rgb(255,0,0)`) — inherited
  from `_normalize_color_value`'s existing no-component-parsing rule.
- Changing default (flag-off) behavior in any way.

1. With `--lift-tokens` **off** (the default), `ll-artifact templatize` is bit-for-bit identical to today: same template body, same byte-exact `verify_round_trip`, same `unlifted-tokens.json` `unlifted` list, same fail-open exit code. Covered by a dedicated regression test; every existing test in `TestReportTokenLiterals`, `TestCmdTemplatizeTokenReport`, and `TestCmdTemplatizeEndToEnd` passes **unmodified**.
2. With `--lift-tokens` **on**, a color literal in CSS-value position resolving to a single token (after the alias-preference filter) is rewritten in the spliced body to `var(--<dotted.name with . → ->)` — e.g. `var(--color-surface-primary)`, matching `render_as_css_vars_themed:703`'s mangling exactly. The body gains a `[[= ll.theme_css =]]` expression inside a `<style>`, `data-theme="<active_theme>"` on `<html>`, and `manifest["theme"] = "design-tokens"`. **Verified by rendering**: the test runs the lifted template through `render_template` and asserts the output carries the `--color-…` declarations, no longer carries the injected `[[= ll.theme_css =]]` expression (**that specific expression** — not a global "no `[[=`" assertion, which false-rejects artifacts whose escaped literal delimiters render back as `[[=` text), carries no `/*__THEMED_CSS_VARS__*/` text, and — per Decision Rules § Declaration agreement is textual, not computed — that for every lifted token `x` the declaration `--x: <the original artifact's literal>;` appears inside the scope block matching the injected `data-theme` (`[data-theme=dark] {` for a dark lift, `:root {` for a light one). There is no CSS cascade in the test environment; "the ref resolves to the original value" is asserted in this textual form, never as a computed style.
3. A matched literal **outside** CSS-value position — `href="#dedede"`, an id selector `#face {` inside a `<style>` that also contains a `:`-bearing rule such as `a:hover`, `"#c0ffee"` inside `<script>` — is never rewritten and is still reported. Tested explicitly with token values chosen to collide with all three. Conversely, a literal **inside** a declaration value is rewritten regardless of what character follows it: `box-shadow: 0 0 2px #e8dcc4, …`, `background: #fdfbf6 url(…)`, and `color: #fdfbf6 !important;` all lift. The guard is the two-part scope-then-nearest-delimiter rule (Decision Rules § CSS-context guard); a rule phrased as "somewhere after a `:` and before a `;`/`}`" fails the `#face` case, and one phrased as an enumerated immediate-terminator set fails the three acceptance cases. The scope test's exclusion of color-valued **presentation attributes** (inline SVG `fill`/`stroke`/`stop-color`, `bgcolor`, `<meta name="theme-color">`) is an accepted v1 under-lift rather than a corruption guard: such a literal is reported and never rewritten, a test pins that behavior, and both doc updates state it (Decision Rules § CSS-context guard → Known under-lift; Scope Boundaries).
4. Verification is two-stage and both stages are tested: (a) `verify_round_trip` passes byte-exact on the pre-lift body, unchanged from today; (b) undoing the **recorded lift and stamp spans** on the lifted body reproduces the pre-lift body byte-for-byte. The inverse is span-tracked, never a whole-body textual `var()`→literal substitution — proven by a test where the source artifact already contains a `var(--color-surface-primary)` and the lift still succeeds. A failure in either stage routes to `rejected_dir` with exit code 2.
5. Candidate resolution runs the alias-preference filter first (prefer the semantic name whose raw value is an alias reference over the primitive it points at); if exactly one survives it is used, otherwise the literal is **not rewritten** and is reported in `unlifted` with all candidates. Tested against this profile's real collisions — `#e8dcc4` lifts to `color.border.subtle`, light `#fdfbf6` (two semantic aliases) does not lift. A raw candidate count > 1 alone must **not** block the lift; that rule blocks ~half of all colors on this repo's own profile.
6. `unlifted-tokens.json` keeps its filename and its `unlifted` key, and gains a `lifted` list recording what was rewritten plus a payload-level `lift_skipped_reason` string; the `_comment` string no longer claims "Report-only — not rewritten." `UnliftedToken` keeps its exact three-key shape — the skip reason is a **top-level** key, never a fourth field on the entry, since `TestReportTokenLiterals` asserts full dict equality and AC #1 requires it pass unmodified.
7. `scripts/little_loops/artifact_templates.py`, `scripts/little_loops/artifact_template_kit.py`, and `scripts/little_loops/cli/artifact/__init__.py` are unmodified by this issue — `templatize.py` is the only source file it edits. (`__init__.py` dispatches the argparse namespace to `cmd_templatize` as-is at `:47`, so a flag registered on the subparser needs no threading; an edit there is a no-op.)
8. `docs/reference/CLI.md` (~`:4593`) and `docs/ARCHITECTURE.md:1031` describe both modes; neither still states that token lifting is report-only. Both also state the two accepted limitations of `--lift-tokens`: the render-time token-availability residual (AC #14) and the presentation-attribute under-lift (Scope Boundaries — inline SVG `fill`/`stroke`/`stop-color`, `bgcolor`, `<meta name="theme-color">` are reported, never rewritten).
