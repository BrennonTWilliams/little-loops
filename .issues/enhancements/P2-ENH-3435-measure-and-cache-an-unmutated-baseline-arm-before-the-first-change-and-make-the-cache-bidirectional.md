## Summary

An `ll-harness` verdict of the form "this change improved things" is a claim against a before-number, and today that number is remembered rather than measured. The delta must come from an unmutated arm run on the same task, at the same n, under the same conditions as the candidate, or the claimed delta describes two different systems. Make the baseline an explicit phase of the run: before the first proposal, execute n unmutated runs and record the result. That also calibrates magnitude, which is what makes any subsequent proposal meaningful — "make this better" is not actionable when the baseline is already at zero, exactly as "make this harder" is not.

Make the store bidirectional, which is the part that pays for itself. The measure path, the compare path, and any post-hoc analysis write and read the same rows, so a rollout paid for once is reusable in either direction instead of being re-paid per analysis. Concretely: the candidate arm's own repetitions become the next baseline once that candidate is accepted. In a system where every measurement is an API call, this is a direct cost argument sitting inside a verdict-integrity mechanism.

Store resilience is part of the contract: a partial or condition-mismatched baseline must degrade to re-measuring (on the measure path) or refusing (on the compare path), never to a silently wrong baseline.

## Current Behavior

`ll-harness` comparisons are incumbent-relative: a candidate is graded against whatever the incumbent lineage last produced, and any "before" number cited in a verdict is remembered from an earlier run rather than measured as part of this one. There is no baseline store at all today — `harness_events` holds every repetition, but nothing reads it back as a "before" arm. The two sibling guards are now in place: n-run redundancy (ENH-3415) supplies a sound n, and the frozen external reference (ENH-3421) supplies an external anchor. Both assume a baseline exists; neither makes producing the unmutated incumbent-arm baseline a phase of the run itself. This issue is that remaining piece.

## Expected Behavior

`ll-harness` is a one-shot CLI: it runs whatever is on disk and has no proposal phase of its own. The baseline arm is therefore a **separate invocation on the unmutated subject**, made by the loop before it mutates anything, and the candidate arm is a later invocation on the mutated subject that reads the baseline back:

1. `ll-harness <runner> <target> --measure-baseline` runs n repetitions on the subject as it currently exists on disk and records them as the baseline for that subject (keyed on the subject's *content*, not `head_sha` — see Design). If a full, condition-matched baseline for that content already exists, it is reused and the subject is not re-run. The run reports the tally and exits per the normal banding — a 0/n baseline is valid information ("the baseline is already at zero"), not an error.
2. `ll-harness <runner> <target> --compare-baseline` runs n repetitions on the (now mutated) subject, resolves the **incumbent content** (for `skill`: the HEAD version of the target file; for `prompt`/`cmd`/`mcp`: the cell named by `--baseline-of`), looks up a baseline for that content under matching conditions and n, and reports a delta with provenance. If no such baseline exists, or it is partial or condition-mismatched, the run **refuses** with an explicit "no measured baseline" state (exit 2) — it never compares against a remembered number, and it never re-measures (the subject on disk is already mutated, so it cannot).

Verdicts compute deltas only against a measured baseline. The baseline persists in `harness_events`, which the measure path, the compare path, and post-hoc analysis all read and write, so a rollout paid for on any path is reusable by the others — in particular, the candidate rows written by `--compare-baseline` become the baseline for that content once it is accepted, with no re-measurement. Every reported delta states whether its baseline was freshly measured or reused, along with the n, conditions, and `head_sha` it was measured under.

Ordering ("before the first change") is enforced by refusal, not by the CLI observing proposals: the candidate run cannot report a delta unless a baseline was already recorded for the incumbent content. As a corollary, `--compare-baseline` on `skill` also refuses when the working-tree content hash equals the HEAD content hash ("subject is unmutated; nothing to compare").

## Design

Mechanics borrowed from evolutionary-search harness design, where the baseline arm is treated as mandatory loop structure rather than optional rigor:

- **Baseline phase before the first proposal — as a separate invocation.** Per task, before the loop's first proposal or mutation is applied, the loop invokes `ll-harness ... --measure-baseline`, which executes n runs of the subject as it stands — same task, same effective n as the candidate arm will use, same conditions (model, host, timeout, criteria) — and records the result. The candidate arm later invokes `--compare-baseline`. The n is whatever the candidate arm will use, so the two arms are directly comparable; nothing about the sample machinery is redefined here. The CLI never checks out or stashes an incumbent; it only measures what is on disk and refuses a delta when no baseline exists for the unmutated content.
- **Key on content, not on `head_sha`.** Meta-loops (`harness-optimize.yaml`) mutate skill files in the working tree and commit only on acceptance, so the incumbent and the candidate share `head_sha`. `record_attempt`'s docstring (`session_store/writers.py:1297`) states that `dirty` is deliberately excluded from `_cell_key`. A baseline keyed on `_cell_key(runner, target, head_sha)` alone would therefore let the candidate run read *its own arm* as the baseline. The baseline is matched on `(runner, target, input_hash, target_content_hash, conditions_fp)`; `head_sha` is **not** part of the match. Rationale: after the loop commits an accepted candidate, HEAD moves, and a `head_sha`-keyed lookup would miss the n candidate rows just written for that content and re-pay them — for exactly the primary consumer, the "pays for itself" argument would fail on every accepted iteration. `head_sha` is carried as provenance instead: the report shows the baseline's `head_sha` and flags "measured at a different HEAD" when it differs from the current one. The conditions fingerprint is the honesty mechanism; a visibly stale `head_sha` is the honest signal.
- **The input and the full grading configuration are part of the identity.** Two more things distinguish "the same measurement" beyond content: *what was asked* and *how it was graded*. The key therefore carries a fourth component, `input_hash` — for `skill`, a hash of the canonical `runner_args` (the task); for `mcp`, a hash of the canonical `--args` JSON; `""` for `cmd`/`prompt`, whose input *is* the target — and exact condition matching runs through a single `conditions_fp` column: a sha256 over a canonical JSON serialization of every condition-relevant invocation argument (the readable conditions below plus `--exit-code`, the trace flags `--trace-mode`/`--require-order`/`--require-artifact`/`--forbid-path`, and `--hosts`). Enumerating one column per grading flag would re-pay this migration every time a grading flag lands; a fingerprint covers them all at once. The fingerprint is never NULL on baseline-eligible rows, so pre-migration rows are excluded by construction and no NULL-vs-NULL vacuous matching remains anywhere in the match path — the readable condition columns are provenance and post-hoc query surface, not match keys. (Third review.)
- **Resolving the incumbent content.** The compare invocation only knows the *mutated* hash, and the store may hold rows for several hashes at the same `head_sha` (every rejected candidate the loop reverted without committing also landed there). "The baseline for this runner/target" is therefore ambiguous unless the incumbent is named. For `skill` (the only file-shaped non-DSL runner), the incumbent is **the HEAD version of the target file**: `_hash_bytes(git show HEAD:<target_path>)`. This holds for `harness-optimize.yaml`, which `git commit`s on acceptance and `git checkout $BEST -- <targets>` on rejection, so the incumbent always equals HEAD content. For `prompt`, the target *is* the content (`_hash_bytes(args.target)`), so a mutated prompt is a different cell with no discoverable incumbent; for `cmd`/`mcp` there is no content hash at all. All three require `--baseline-of <attempt-id>`, which resolves to that attempt's `(runner, target, input_hash, target_content_hash)` and uses every authoritative row matching it under the current `conditions_fp`. Because `--baseline-of` resolves the baseline key independently of the current invocation's arguments, the compare gate also refuses when the resolved key's `input_hash` differs from the current invocation's — the candidate must run the same input the baseline measured. `--baseline-of` is also accepted on `skill` as an explicit override of the HEAD resolution. The CLI never checks out or stashes anything; `git show` reads a blob.
- **Stored bidirectionally, in `harness_events`.** There is no second store and no separate result shape: a baseline *is* the set of authoritative rows for the incumbent content under matching conditions. `--measure-baseline` writes ordinary repetition rows (loudly); `--compare-baseline` writes the candidate's rows the same way and reads the baseline back via `history_reader.harness.baseline_for(...)`. Post-hoc analysis reads with the same function and writes with `record_attempt`. Bidirectionality in practice: the candidate rows written under `--compare-baseline` at content Y are the baseline for Y once Y is accepted and the next `--measure-baseline` runs — the measurement is paid once. See "Decision: baseline store" under Program Design (Option A, selected).
- **Both arms share a `_cell_key`.** `_cell_key` is `(runner, target, head_sha)` with no content hash, so baseline and candidate rows land in the **same cell** and their repetition indices interleave. This is accepted: `_cell_key`'s encoding is documented in `record_attempt`'s docstring and EVENT-SCHEMA.md, and changing it would break `--retry-of`'s `prior.cell_key != cell_key` check against existing rows. `baseline_for` therefore does **not** filter by `cell_key`; it filters by `runner`, `target`, `input_hash`, `target_content_hash`, and `conditions_fp`, and `authoritative_attempts(cell_key)` is not a sufficient scaffold on its own (it would return both arms mixed). `_read_target_history()` already pools across criteria and is unaffected.
- **Conditions must actually be written.** `harness_events` has `semantic_prompt` and `semantic_model` columns, but `_record_harness_event` (`cli/harness.py:206`) passes neither, and `docs/reference/CLI.md` documents that `semantic_prompt` "is not written by any caller today". A conditions match on unpopulated columns compares NULL to NULL and passes vacuously. The writer change is part of this issue: every row written on the measure and compare paths carries `semantic_prompt = args.semantic`, `semantic_model` = the judge model `_grade` resolves (`evaluate_llm_structured`'s `DEFAULT_LLM_MODEL` today — thread it through explicitly rather than assuming), plus the new `timeout_s` and `host_cli` columns. "Model" is two conditions, not one: `semantic_model` (the judge) and `subject_model` (the prompt runner's `--model`; NULL for the other runners). Both land on the row and in the fingerprint; exact *matching* runs through `conditions_fp` (see the identity bullet above) — these readable columns are the provenance and post-hoc query surface, which is also why the vacuous NULL-match failure mode cannot recur: the fp is never NULL on baseline-eligible rows.
- **Degrade, never lie.** "Partial" concretely means fewer than n authoritative (non-superseded) rows for the incumbent content under matching conditions, or zero graded rows among them (no rate can be computed). On `--measure-baseline`, a partial or mismatched baseline is re-measured; on `--compare-baseline` it is refused (the subject is already mutated, so re-measuring is impossible). Moreover, the compare gate runs **before the candidate arm**: the baseline-lookup refusals (no baseline / partial / fingerprint or input mismatch) are computable without running anything, and gating first matches the `--retry-of` precedent ("gated before the run", `cli/harness.py` `--retry-of` help). A refused compare performs zero subject invocations and writes no candidate rows — the earlier "candidate rows written regardless" behavior only pays off if a loop accepts despite a refusal, which is precisely the behavior the refusal exists to prevent. A stored baseline with *more* than n matching rows reuses its most recent n; n is a **threshold** on available rows, not a matched field (rows don't carry n). "Re-measure" in an append-only table means: n new rows are appended (`record_attempt` allocates repetition indices monotonically per cell, so they take indices n..2n−1 or later), and `baseline_for` selects the **most recent n** matching rows (`ORDER BY id DESC LIMIT n`), never all of them. There is no "corrupt entry" case under Option A — SQLite rows are typed and the reader is a query, not a parser. The failure mode being guarded against is a silently wrong baseline — a plausible-looking number that no longer describes the system it claims to. Resilience is explicitly unit-testable and must be tested.
- **The delta is a pass-rate difference with both intervals, never a banded verdict.** `delta = candidate.passed/candidate.graded − baseline.passed/baseline.graded`, reported alongside both arms' Wilson intervals (`wilson_ci`, already used by `_report_samples`). At the default n=3 the delta's granularity is one third and the intervals will usually overlap; the report shows that rather than hiding it behind a PASS/FAIL band. If the candidate arm has zero graded samples (all abstained/errored), `delta` is `null` and the text report says so; the run's exit code still comes from `_band_samples` on the candidate tally alone. `--compare-baseline` refuses at effective n=1 (a delta between two booleans is not a measurement). The existing exit-code contract (0/1/2/3) is unchanged for a run that produces a verdict; the delta is additive report content.
- **Refusals exit 2, not 1.** Exit 1 is FAIL, and the `harness_exit` fragment (`loops/lib/common.yaml`) routes it as "candidate failed" — a loop could not distinguish "no baseline measured" from a genuinely failing candidate. Exit 2 is already "the run could not produce a verdict" (timeout, internal error, `cmd_mcp` setup failures). All baseline refusals (no baseline / partial / mismatch / n=1 / `--baseline-of` missing / unmutated subject / flag combinations) use exit 2. This deliberately diverges from the `--retry-of` refusal precedent (exit 1), which predates loops consuming the exit code as a routing signal.
- **Provenance on the delta.** A verdict that reports a delta names its baseline: n, the readable conditions, `head_sha` (and whether it differs from the current HEAD), whether the baseline was freshly measured or reused, and the attempt ids it was derived from. Two honesty notes ride alongside: `measured on a dirty tree` when the baseline rows carry `dirty=1` (the content hash pins the target file, not the rest of the repo a skill may read), and `subject model not pinned` when the baseline's `subject_model` is NULL (see the known limitation below).
- **Loud writes when baseline is on.** Harness event writes are best-effort today (`contextlib.suppress` in `_record_harness_event`). With either baseline flag set, a swallowed write would mean the baseline (or the candidate rows the next baseline reuses) silently never landed, so the write failure must propagate and exit non-zero — the precedent is the `--retry-of` path, which already does this.

On the run model (ENH-3397): baseline runs are ordinary `attempt_kind='repetition'` rows. Nothing about attempt classification changes; the baseline arm simply is another content hash the existing machinery scores — the content hash, not the cell, is what makes it a *distinct* subject from the mutated candidate.

**Known limitation — ambient subject model on the `skill` runner.** Only `prompt` takes `--model`; `skill` runs under whatever model the host CLI resolves at invocation time, and the measure and compare invocations can be days apart. A host default-model change between arms therefore passes every condition check today: `subject_model` is NULL for `skill` rows, so the delta's provenance carries an explicit `subject model not pinned` warning rather than a false claim of condition parity (matching this issue's "degrade, never lie" rule). Capturing the *effective* model from the host result would close this properly but needs a `RunnerResult`/`host_runner` change — named as a follow-up in Scope Boundaries.

**No in-repo caller exists today.** `harness-optimize.yaml` invokes `${context.scorer}`, not `ll-harness`, and already has its own `baseline_score` state; the only `ll-harness` reference under `loops/` is the `harness_exit` fragment's docstring. Loop-side wiring is **out of scope** for this issue (see Scope Boundaries); the two-invocation sequence ships as a documented example in `docs/guides/EVALUATION_GUIDE.md`, and a follow-up may make it the scorer for `harness-optimize.yaml`. The JSON `baseline.delta` field is the loop-consumable output.

## Scope Boundaries

- **In scope**: `--measure-baseline` / `--compare-baseline` / `--baseline-of` on the four non-DSL entry points (`cmd_skill`, `cmd_prompt`, `cmd_cmd`, `cmd_mcp`), the five-column `harness_events` migration (`timeout_s`, `host_cli`, `subject_model`, `input_hash`, `conditions_fp`) and the writer change that populates every condition column, HEAD-content incumbent resolution for `skill`, `baseline_for` reader, the bidirectional read/write contract, partial/mismatch degradation on both paths, the delta definition, and delta provenance reporting.
- **Out of scope — loop wiring.** No loop in the repo invokes `ll-harness` today (`harness-optimize.yaml` uses `${context.scorer}`). Making the two-invocation sequence a scorer for `harness-optimize.yaml` is a follow-up; this issue ships the documented example only.
- **Out of scope — `cmd_dsl`.** The DSL runner has no per-task n (it refuses `--samples > 1`, `cli/harness.py:1497-1504`) and already writes its own aggregate + per-task cell rows. A DSL baseline arm is a task-set-breadth question, not a repetition-depth one, and needs its own definition. `cmd_dsl` rejects both new flags with an explicit "not supported on the dsl runner" message (same shape as its `--samples` refusal). A follow-up issue defines the DSL baseline arm.
- **Out of scope**: n-run redundancy and its `--samples` semantics (ENH-3415, done); the frozen external reference guard (ENH-3421, done); the repetition/infra-retry/continuation attempt model (ENH-3397, done); widening the evidence surface beyond the current channels; scoring runs on an efficiency vector; capturing the *effective* subject model from host output (a `RunnerResult`/`host_runner` change — the `subject model not pinned` provenance warning is the in-scope mitigation); any checkout/stash/worktree mechanism for running an incumbent from a mutated tree (the loop sequences the two invocations). Those are separate concerns that compose with this one.

## Acceptance Criteria

1. `ll-harness <skill|prompt|cmd|mcp> <target> --measure-baseline` runs the effective n repetitions on the subject as it exists on disk and records them as `repetition` rows carrying `target_content_hash`, `input_hash`, `conditions_fp` (both never NULL), `semantic_prompt`, `semantic_model`, `subject_model`, `timeout_s`, and `host_cli` (a test asserts `input_hash`/`conditions_fp` are non-NULL on every written row and the remaining columns are non-NULL whenever the corresponding arg is set). If a full baseline — same `(runner, target, input_hash, target_content_hash)` and `conditions_fp` — already exists, the subject is **not** re-run and the report says `reused`. The run's exit code follows the normal banding (a 0/n baseline exits 1 and is still recorded). A write failure on this path exits non-zero instead of being suppressed.
2. `ll-harness ... --compare-baseline` refuses with an explicit "no measured baseline" state (**exit 2**, message names the runner/target/incumbent content hash it looked for) when no baseline exists for the incumbent key, when the stored baseline has fewer than n authoritative rows or zero graded rows, when its `conditions_fp` differs from the current invocation's, or when the baseline's `input_hash` differs from the current invocation's (possible only via `--baseline-of`, whose key is resolved independently of the current arguments). It never compares against `_read_target_history()` or any other remembered number, and it never re-measures. The gate runs **before the candidate arm**: a refused compare performs zero subject invocations and writes no candidate rows (a test patches the invoke closure and asserts zero invocations per refusal class).
3. Incumbent resolution: for `skill`, the baseline is looked up under `_hash_bytes(git show HEAD:<target_path>)`. A test mutates a skill file in a dirty tree without committing, runs `--compare-baseline`, and asserts (a) the candidate's own repetitions are *not* read back as the baseline and (b) rows for a *second* rejected mutation at the same `head_sha` are not either. A second test asserts `--compare-baseline` on an unmutated `skill` (working-tree hash == HEAD hash) refuses. For `prompt`/`cmd`/`mcp`, `--compare-baseline` without `--baseline-of <attempt-id>` refuses; with it, the baseline is every authoritative row sharing that attempt's `(runner, target, target_content_hash)` under the current conditions.
4. Baseline matching is on `(runner, target, input_hash, target_content_hash, conditions_fp)` and **not** `head_sha` or `cell_key`: a test commits the mutated content (moving HEAD), runs `--measure-baseline`, and asserts the candidate rows written under the *previous* HEAD are reused with no new runs, and that the report carries the baseline's `head_sha` with a "measured at a different HEAD" note.
5. The store is bidirectional: one test shows rows inserted directly via `record_attempt` (post-hoc) consumed as the baseline by `--compare-baseline` without re-running the subject, and one shows `--compare-baseline`'s candidate rows consumed by a later `--measure-baseline` (AC4's scenario) and read back by `history_reader.harness.baseline_for` with the same result.
6. Partial or mismatched baselines degrade by path: on `--measure-baseline`, one test seeds fewer than n rows, one seeds n rows under mismatched conditions, and one seeds n rows under a different input (different `input_hash`); each asserts the subject is re-measured and `baseline_for` afterwards returns the **most recent n** rows (the new ones), not the seeded ones and not all of them. A fourth test seeds n+2 *matching* rows and asserts reuse takes the most recent n of them with zero new runs (n is a threshold, not a matched field). On `--compare-baseline`, the first three seeds each assert a pre-run refusal (exit 2, zero subject invocations) and no re-measurement.
7. A reported delta is `candidate pass rate − baseline pass rate` with both arms' Wilson intervals, and names its baseline's provenance: `measured`/`reused`, the n, the readable conditions, the baseline `head_sha`, and the attempt ids it came from — plus the `subject model not pinned` note when the baseline's `subject_model` is NULL and the `measured on a dirty tree` note when baseline rows carry `dirty=1`. `delta` is `null` when the candidate arm has zero graded samples. Both the text and `--output json` renderings carry these fields; the exit-code contract for a run that reaches a verdict is unchanged.
8. `--compare-baseline` refuses at effective n=1; `--measure-baseline` and `--compare-baseline` together, or either with `--retry-of`, refuse; `cmd_dsl` refuses all three flags. Each refusal exits 2 with an explicit message.
9. Existing single-shot and n-sample verdict behavior is unchanged when no baseline flag is given (including the best-effort write suppression); the test suite passes.

## Program Design

### Decision: baseline store

`decision_needed: true` is set for this one choice. Both options satisfy every AC; they differ in how many sources of truth exist for a harness measurement.

**Option A**: `harness_events` is the store.

> **Selected:** Option A — reuses the existing, recently-exercised `harness_events` migration/reader pattern (ENH-3407 added the same shape of nullable condition columns) instead of standing up a second, drift-prone store.

A baseline *is* the set of authoritative (non-superseded) `harness_events` rows for the incumbent's content under matching conditions. `--measure-baseline` writes ordinary repetition rows (loudly); `--compare-baseline` reads them back via a new `history_reader.harness.baseline_for(...)`. Post-hoc analysis reads with the same function and writes with `record_attempt`, so AC5's bidirectionality is the existing table's read/write surface, not new plumbing. AC6's "partial" is "fewer than n authoritative rows, zero graded rows, or a conditions mismatch" — no JSON-corruption story to test, but the partial-row and mismatch cases are. Requires a schema migration adding `timeout_s`, `host_cli`, and `subject_model` columns, **and a writer change**: `semantic_model` and `semantic_prompt` columns exist but `_record_harness_event` never populates them (second review), so the measure/compare paths must start passing them or the conditions match is vacuous. `target_content_hash`, `head_sha`, and `dirty` are already written. Cost: a migration plus the writer change; `history.db` is the only place the baseline lives, so an unavailable DB refuses the baseline flags outright (it already degrades `--retry-of` the same way).

**Option B**: a JSON file cache under `.ll/harness-baselines/<key>.json`. `read_baseline`/`write_baseline` on a `BaselineResult` file, following `.ll/evidence-verdict-cache.json` (gitignored per-file cache with invalidate-on-mismatch) and delegating writes to `file_utils.atomic_write_json` (`file_utils.py:35`). Independent of `history.db` availability, and the corruption story is literally testable with a malformed file. Cost: every baseline measurement is now stored twice (the repetition rows still land in `harness_events`), the two can drift, and the post-hoc "write the same shape back" path has to be built and kept in sync with the row shape by hand.

**Recommended**: Option A — ENH-3397/3407/3408 already made `harness_events` the cell-keyed record of every repetition, and a delta computed from the same rows the run wrote is the strongest form of "measured, not remembered."

### Decision Rationale

**Selected**: Option A — `harness_events` is the baseline store.

Two `ll:codebase-pattern-finder` agents independently gathered evidence for each option and scored them on consistency, simplicity, testability, and risk (0–3 each, 12 max):

| Dimension | Option A (`harness_events`) | Option B (JSON file cache) |
|---|---|---|
| Consistency | 3 | 2 |
| Simplicity | 3 | 1 |
| Testability | 3 | 2 |
| Risk | 2 | 1 |
| **Total** | **11/12** | **6/12** |

**Key evidence for A**: `session_store/schema.py`'s `_MIGRATIONS` list already has a directly analogous entry — the v49/ENH-3407 migration added five nullable condition/run-model columns (`cell_key`, `repetition`, `attempt_kind`, `continuations`, `superseded_by`) to this exact `harness_events` table via the same append-only `ALTER TABLE` + `SCHEMA_VERSION` bump mechanism this issue's `timeout_s`/`host_cli` columns would use. `record_attempt`'s `**event_fields` pass-through already generalizes to new writer kwargs with no dataclass/writer-shape change, and `history_reader/harness.py` has a ready-made column-list/dataclass/`_AUTHORITATIVE_PREDICATE` scaffold a `baseline_for(cell_key, *, n, conditions)` reader slots into directly. ~15+ existing migration tests (`test_session_store_schema.py`) make the migration path well-trodden.

**Key evidence against B**: the cited precedent (`.ll/evidence-verdict-cache.json`'s `VerdictCache`) does not actually use `file_utils.atomic_write_json` as the Design text assumes — it writes via raw `path.write_text`, so the atomic-write delegation would be a new pairing, not a repeat of that file's own implementation. More materially, Option B stores every baseline measurement twice (rows still land in `harness_events` regardless), which the issue's own Program Design text already flags as a drift risk, and its bespoke invalidation logic (version/algo/params/refs-signature checks) would need to be redesigned from scratch rather than reused.

On a tie, Consistency (codebase fit) is the tiebreaker per the scoring rules — Option A wins there too, so the result is unambiguous.

### Types

- `BaselineKey`: `runner: str`, `target: str`, `input_hash: str`, `target_content_hash: str` — the match key. **No `head_sha`** (provenance only, see Design). `input_hash` is `""` for `cmd`/`prompt` (input *is* the target), a canonical hash of `runner_args` for `skill`, and of the canonical `--args` JSON for `mcp`. `_baseline_key(...)` serialises it the way `_cell_key` does (JSON array, `separators=(",", ":")`) for log/report readability; the reader queries the four columns directly rather than a serialised key column. For `prompt`/`cmd`/`mcp`, the key is resolved from `--baseline-of`'s row; for `skill`, `target_content_hash` is the HEAD blob hash.
- `BaselineConditions`: the readable fields — `semantic_model: str | None`, `subject_model: str | None`, `semantic_prompt: str | None`, `timeout_s: int`, `host_cli: str` — rendered in provenance and available for post-hoc queries — plus `conditions_fp: str`, a sha256 over the canonical JSON of those fields plus the exit-code expectation, the trace flags, and `--hosts`; never NULL on baseline-eligible rows, and the only thing `baseline_for` matches conditions on. `n: int` is a threshold, not a matched field: rows don't carry n, so reuse requires at least n matching rows and uses the most recent n.
- `BaselineResult`: `key: BaselineKey`, `conditions: BaselineConditions`, `tally: SampleTally` (`cli/harness.py:697` — passed/graded/failed/abstained/errored + Wilson bounds), `attempt_ids: list[int]`, `head_sha: str | None` (of the rows; provenance), `measured_at: str`. `source: Literal["measured", "reused"]` is **read-side provenance set by the reader, never persisted** — a stored row always describes a measurement.
- `BaselineDelta`: `candidate: SampleTally`, `baseline: BaselineResult`, `delta: float | None` (candidate pass rate − baseline pass rate; `None` when the candidate has zero graded samples), `source: Literal["measured", "reused"]`, `head_sha_differs: bool` — what `_report_samples` renders.

### Signatures

- `_baseline_key(runner: str, target: str, input_hash: str, target_content_hash: str) -> str` — sibling of `_cell_key` (`cli/harness.py:144`); display/logging only.
- `_conditions_fp(args, judge_model: str | None) -> str` — sha256 over the canonical JSON serialization of the readable conditions plus `args.exit_code`, the trace flags (`trace_mode`, `require_order`, `require_artifact`, `forbid_path`), and `args.hosts`; `None` fields serialise as `null`. The single condition-match column.
- `_incumbent_content_hash(args, runner, target_path: Path | None) -> str | None` — for `skill`: `_hash_bytes(git show HEAD:<repo-relative target_path>)` via `_git_output`; `None` when git is unavailable, the file is untracked, or the runner is not file-shaped. Returns `None` rather than raising so the caller can produce the refusal message.
- `baseline_for(db_path, *, runner, target, input_hash, target_content_hash, conditions: BaselineConditions) -> BaselineResult | None` — new in `history_reader/harness.py`, beside `authoritative_attempts` (`:186`) and sharing `_AUTHORITATIVE_PREDICATE`. Filters on `runner`, `target`, `input_hash`, `target_content_hash`, and `conditions_fp` — plain equality; all non-NULL on baseline-eligible rows, so no NULL-comparison pattern enters the match path (**not** `cell_key`, which both arms share); `ORDER BY id DESC LIMIT conditions.n`. Returns `None` when fewer than `n` rows match or none of them is graded; more than `n` matching rows reuse the most recent `n`.
- `read_baseline(key: BaselineKey, conditions: BaselineConditions) -> BaselineResult | None` — thin wrapper over `baseline_for` with `DEFAULT_DB_PATH` resolved through `resolve_history_db` (same precedent as `_retry_gate`).
- `_run_sample_loop(...) -> tuple[int, SampleTally, list[dict]]` — **refactor**: today it returns only the exit code and prints the report inline; the baseline phase needs the tally. Either return the tally alongside the exit code (callers that ignore it keep working via a small shim) or split the report call out of the loop. Name this refactor in the plan; it is not optional.
- `_run_baseline_phase(runner_label, args, n, invoke, record) -> tuple[int, BaselineResult]` — new in `cli/harness.py`, sibling to `_run_sample_loop` (`:1036`). Calls `read_baseline` first; on a full match, prints the reused tally and returns without invoking. Otherwise drives n runs through `_run_sample_loop` with loud recording and returns the exit code from `_band_samples` plus the fresh `BaselineResult`. Only reached with `--measure-baseline`.
- `_compare_baseline(args, key, conditions, candidate: SampleTally) -> BaselineDelta | str` — returns the delta from a pre-resolved `BaselineResult`, or a refusal message (no baseline / partial / fingerprint or input mismatch / n=1 / non-skill-without-`--baseline-of` / unmutated subject), mirroring `_retry_refusal`'s message-or-None shape (`:156`). All store-consulting refusals are computed by the **pre-run gate** (see Call Path), so a refusal costs zero subject invocations. Refusals exit **2**.
- `_record_harness_event(..., loud: bool = False, semantic_prompt=None, semantic_model=None, subject_model=None, timeout_s=None, host_cli=None, input_hash=None, conditions_fp=None)` — `loud=True` bypasses the `try/except` the same way `retry_of is not None` already does; the seven new kwargs pass straight through `record_attempt`'s `**event_fields`, and `input_hash`/`conditions_fp` are always non-NULL on the baseline paths.
- `_report_samples(..., delta: BaselineDelta | None = None, baseline: BaselineResult | None = None)` — additive keywords; `delta` renders the comparison, `baseline` alone renders a measure run's provenance (`measured`/`reused`). Appends the delta line(s) to the text report and a `baseline` object to the JSON payload.
