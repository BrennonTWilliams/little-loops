## Summary

Every improvement comparison `ll-harness` can make today is incumbent-relative. `--compare-baseline` (ENH-3435) measures a candidate against the unmutated HEAD content of the same target, and `harness-optimize.yaml` scores each iteration against a `baseline` captured at the start of *that run*. Neither holds a reference that survives across runs: once a run commits its winner, the next run's incumbent *and* its run-start baseline are both that winner. A lineage where each run genuinely beats the previous run's winner can therefore drift away from any fixed standard while every comparison still passes — the cross-run regression is invisible because nothing outside the lineage is ever re-measured.

The guard is structural: a candidate is measured against two opponents — the incumbent (is the lineage still improving?) and a **pinned** baseline whose content identity is fixed at pin time and never re-derived from HEAD (is the lineage still ahead of a fixed reference?). Each comparison is three-valued (`ahead` / `behind` / `inconclusive`, decided from a Newcombe score interval on the *difference* of the two pass rates, built from the Wilson CIs `ll-harness` already computes), and the pair is reported as one named outcome. Because sampled pass rates are noisy, `ahead` of the incumbent but `behind` the pin is a reachable, reportable state — and it is the signal that the lineage has drifted below its anchor.

Scope: the pin and the frozen arm exist for the `skill` runner only. It is the only runner whose target is a stable *name* with a separate content identity (`target_content_hash` of the skill file); `prompt`/`cmd` targets *are* their content, and `cmd`/`mcp` record `target_content_hash = ""`, so there is nothing for a pin to hold that survives a mutation (see D6).

## Current Behavior

- `ll-harness <runner> --compare-baseline` (`cli/harness.py:1907`, `_run_compare_arm()`) reports exactly one delta, against `baseline_for()` rows keyed on the HEAD content hash (`_incumbent_content_hash()`, `:1732`) or an explicit `--baseline-of` attempt. There is no second arm and no way to name a reference other than "current HEAD" or "one prior attempt".
- `harness-optimize.yaml` captures `baseline` once per run (`baseline_score` state, `:111-117`) and ENH-3421's `reference:` (`gate` state, `:199`) blocks any iteration that regresses below it — so drift *within* a run is already blocked. But `${captured.baseline}` lives in the per-run context: the next run re-captures it from the freshly committed HEAD, so across runs the reference rolls forward with the lineage.
- No comparison result anywhere is three-valued: `BaselineDelta.delta` is a raw rate difference or `None` (`cli/harness.py:1610-1623`), with no notion of an inconclusive result despite both tallies carrying Wilson CIs.

## Expected Behavior

- A `skill` target can carry a **pin**: a recorded content hash of that target (plus HEAD SHA, timestamp, reason) that is written only by an explicit `--pin-baseline` invocation of the `skill` subcommand and never recomputed from HEAD. Pinning is a flag on the existing subcommand (`ll-harness skill <target> [args] --pin-baseline`), not a separate verb, so it shares the evaluator flags, `--samples`, and target/input resolution the frozen arm's lookup needs (D6). `skill` pins the HEAD blob of the target; `--pin-baseline` on `prompt`/`cmd`/`mcp`/`dsl` is refused (exit 2) — those runners have no stable target-name-plus-content identity for a pin to key on.
- A pin is only written when the pinned content already has a full-n measurement under the current input and conditions, with `n >= 2` (first pin and re-pin alike; `--pin-force` overrides and is recorded). Because `BaselineConditions.n` is a *threshold* (the reader needs at least n matching rows), a pin measured at `--samples N` satisfies a later compare only when that compare's n is `<= N`; the refusal text and docs say so.
- When a pin exists for the target, `ll-harness skill <target> --compare-baseline` reports **two arms**: the existing incumbent arm and a frozen arm resolved by calling `baseline_for()` with the pinned content hash under the current input and conditions. Each arm is classified `ahead` / `behind` / `inconclusive` from the Newcombe difference interval (D4), and the pair is reported as one named outcome in both the text and `--json` reports.
- The exit code is unchanged (still the candidate tally's banding alone); the dual outcome is report content, exactly as `delta` is today. The only new refusal is fail-closed: a pin that exists but has no full-n matching rows under current conditions refuses before any subject invocation with an actionable message that spells out the re-measurement procedure (D8), via a new `_frozen_baseline_refusal()` shaped like `_compare_baseline_refusal()`.
- Re-pinning is refused unless the proposed new pin has a measured pass rate at or above the active pin's under the current conditions. If the active pin has *no* full-n measurement under the current conditions (typical after a judge/`n`/timeout change), the re-pin is refused with the D8 procedure for the *active* pin's content — the comparison is undefined, and fail-closed is the rule. Re-pinning content whose hash equals the active pin's is refused as a no-op. `--pin-force` overrides all three. Pin history is append-only, one file per entry.

## Scope Boundaries

- **In scope**: the pin record and its CLI flag (`skill` runner only), a `proportion_diff_ci()` helper in `stats.py`, the second arm in `ll-harness skill --compare-baseline`, the three-valued classification, the widened `BaselineDelta`/report/JSON shape, docs and tests.
- **Out of scope (follow-up, if ever wanted)**: pins for `prompt`/`cmd`/`mcp`. Those runners would need a user-supplied stable pin name (their `target` is the content, or their `target_content_hash` is `""`), which is a different key design; this issue refuses `--pin-baseline` there.
- **Out of scope (follow-up issue)**: wiring the dual outcome into any loop's routing (`harness-optimize.yaml` or otherwise) and deciding what a loop *does* on `ahead`/`behind`. This issue makes the signal exist and be durable; consuming it is a separate change with its own MR-lint implications.
- **Out of scope**: any change to `evaluate_convergence()`'s `reference` field or the FSM evaluator layer (see D1).
- **Out of scope**: `evaluate_comparator()`'s `.loops/baselines/` file mechanism — unrelated and unwired; left untouched.
- **Out of scope (follow-up)**: a `--measure-pin` mode that materialises the pinned blob into the working tree, measures it, and restores the file. This issue documents the manual procedure (D8) instead.
- **BUG-3479 is resolved (landed on `main`)**: `_incumbent_content_hash()` used to hash the *stripped* `git show` output while measured rows carried `_hash_file()`'s raw-bytes hash, so on a real checkout the two never matched — the pin stores the former and the frozen arm looks rows up by it, so before this fix landed the frozen arm would have failed closed forever. The fix shipped in commit `295078de4` (2026-09-15); `_incumbent_content_hash()` now hashes raw blob bytes and matches `_hash_file()` (see Codebase Research Findings below). ## Design

This is a different axis from the evaluator-hardening siblings in EPIC-3475 (ENH-3462/ENH-3463 keep the *measuring instrument* honest); this keeps the *subject* honest by pinning a permanent second opponent.

Complements the unmutated baseline arm shipped as ENH-3435, and is a different thing: that baseline is a control arm measured inside a single harness run (it answers "did this change help relative to no change"); this issue's baseline is a standing external opponent for the lineage (it answers "is the lineage still ahead of a fixed reference"). A run that has both can distinguish a change that helps from a lineage that is drifting.

### Decisions

- **D1 — Layer: `ll-harness` CLI, not the FSM evaluator.** The epic is "Harden ll-harness Verdicts"; `--compare-baseline` is wired into no loop or skill today, so there is no consumer to break; and the ENH-3421 decision record (`.ll/decisions.d/a2c57916-…`) already rejected stacking a second FSM-layer check on `harness-optimize.yaml`'s `gate` for cost and single-`evaluate`-per-state reasons. No `EvaluateConfig` field is added, so MR-2's `_has_baseline_reference` allowlist and `EvaluateConfig`'s `to_dict`/`from_dict`/docstring/API.md mirror are **not** touched.
- **D2 — The frozen baseline is pinned *content*, re-measured, not a stored score.** A stored number goes stale the moment the scorer, task set, judge model, or conditions change. The pin records `target_content_hash` (the HEAD blob hash at pin time, same `_hash_bytes` as `_incumbent_content_hash()` — raw blob bytes once BUG-3479 lands, so it equals `_hash_file()` of the unmodified file) plus `pinned_head_sha`, `pinned_at`, `reason`, `forced`. The pin deliberately carries **no `input_hash`** and no conditions: the frozen arm is the pinned content measured under the *current* input (`_input_hash(runner_args)` / `--args`) and the *current* `conditions_fp`, so one pin serves every input and every evaluator configuration, and changing either simply requires the pinned content to be measured under it (D8).
- **D3 — Reuse `baseline_for()`; do not add a second store.** `baseline_for()` keys on whatever `target_content_hash` the caller passes. Passing the pinned hash instead of HEAD's yields the frozen arm, with the reader's existing full-n / conditions-fp / authoritative-rows guarantees and caching for free (rows measured on the pinned content are reused until conditions change). The earlier finding that "neither existing mechanism has a key component set at freeze time" is correct about the *callers*, not the reader: the pin record supplies that component. This supersedes the earlier Program Design line calling for a "new frozen-external-baseline record distinct from `BaselineResult`" — the only new type is the pin, and the frozen arm *is* a `BaselineResult`.
- **D4 — Each comparison is three-valued, from a Newcombe difference interval, not CI overlap.** A new `proportion_diff_ci(k1, n1, k2, n2, z=1.96) -> tuple[float, float]` in `stats.py` returns the Newcombe (1998, method 10) score interval for `p1 − p2`, built from the two `wilson_ci()` bounds: with `(l1,u1)`, `(l2,u2)` and `d = p1 − p2`, `lower = d − sqrt((p1−l1)² + (u2−p2)²)`, `upper = d + sqrt((u1−p1)² + (p2−l2)²)`. `_arm_verdict()` calls it with the candidate as `1` and the arm as `2`: `ahead` if `lower > 0`, `behind` if `upper < 0`, else `inconclusive`. A zero-graded tally on either side is `inconclusive` (checked before calling, since `wilson_ci` raises on `n <= 0`).
  *Why not "the two 95% CIs are disjoint"*: that rule is far too conservative at `ll-harness` sample sizes. Measured against `wilson_ci`: at the default `n=3`, 3/3 vs 0/3 is `inconclusive` (intervals `[0.44,1]` and `[0,0.56]` overlap); at `n=10`, 10/10 vs 5/10 is still `inconclusive`; `drift` would need the candidate's interval to sit strictly between two disjoint intervals, unreachable below ~20 samples. Under Newcombe, 3/3 vs 0/3, 5/5 vs 1/5, 10/10 vs 5/10, and 8/10 vs 3/10 all classify `ahead` (difference lower bounds 0.21, 0.19, 0.12, 0.07). Overlapping intervals do not imply an insignificant difference; the difference interval is the correct test.
  *Reachability at real n (measured 2026-09-15 by exhaustive enumeration of every `(candidate, incumbent, pin)` tally under this rule)*: at the default `n=3`, `ahead` is exactly one cell of 16 (3/3 vs 0/3) and **`drift` is unreachable** — it needs `ahead` of the incumbent *and* `behind` the pin, which at `n ≤ 5` cannot both hold. `drift` first appears at `n=6` (one cell: 3/6 vs 0/6 vs 6/6), has 5 cells at `n=10`, 18 at `n=12`, and is broadly reachable only from `n≈12`. Because `BaselineConditions.n` is a threshold, the pin's measured `N` caps the `n` of every later compare, so **pin at `--samples 10` or more and compare at `--samples 10` or more**; this floor is stated in the `--pin-baseline`/`--compare-baseline` CLI help, in `docs/guides/EVALUATION_GUIDE.md`, and as a one-line `note: n=<n> is below the drift floor (6); outcome is at most regression/inconclusive` on the compare report (text and JSON `baseline.notes`) whenever a pin is present and `n < 6`. AC6's hand-built-tally test must be paired with a reachability test that asserts `drift` at `n=6` for `(3, 0, 6)` and asserts no `drift` cell exists at `n=3`, so the floor cannot silently move.
  With a scalar transitive score, "beats incumbent but loses to pin" would imply the incumbent was already below the pin; the outcome is meaningful only because sampled rates are interval-valued. `paired_direction()` (`stats.py:43-79`) is the vocabulary precedent for naming an inconclusive result, but it needs paired per-item outcomes that `ll-harness` repetitions don't have. Vocabulary lives as a string-tuple constant + helper (the `fsm/verdicts.py` convention), in `cli/harness.py`. **`_arm_verdict()` reads only `passed`/`graded`** — it must not read `SampleTally.ci_lo`/`ci_hi`, because the candidate tally's bounds are only assigned inside `_report_samples()` (`cli/harness.py:1478-1479`), *after* `_run_compare_arm()` has built the `BaselineDelta`; reading them there would see `None` and classify everything `inconclusive` while hand-built-tally unit tests still passed.
- **D5 — Named pair outcome.** The pair `(vs_incumbent, vs_pin)` is reported verbatim as two fields plus one derived `outcome` label, in precedence order: `drift` when `vs_incumbent == "ahead"` and `vs_pin == "behind"`; `regression` when **either** arm is `behind` otherwise (the candidate is measurably worse than at least one reference — a clear incumbent loss must not be filed as inconclusive); `improvement` when both are `ahead`; `inconclusive` when neither arm is decisive or the arms disagree only through an inconclusive side (name follows the `q_high_low`-style bucket precedent in `cli/issues/impact_effort.py:194-211`). Full table: `(ahead,ahead)→improvement`, `(ahead,behind)→drift`, `(behind,*)→regression`, `(*,behind)→regression`, all remaining cells `→inconclusive`. `drift` is the lineage-local-optimum signal this issue exists to surface.
- **D6 — Pinning is explicit, `skill`-only, gated, monotone, and append-only.** Pinning is a flag on the `skill` subcommand, `ll-harness skill <target> [args] --pin-baseline [--pin-reason …] [--pin-force]`, registered in `_add_evaluator_flags` next to `--measure-baseline`/`--compare-baseline` (the flags are shared, so `prompt`/`cmd`/`mcp`/`dsl` accept the flag syntactically and refuse it in `_baseline_flag_refusal()` with exit 2). Also refused when combined with `--measure-baseline`, `--compare-baseline`, or `--retry-of`, and when `n < 2` (same reason as `--compare-baseline`'s `n >= 2` rule: a single-sample pin is not a measurement). `--pin-force`/`--pin-reason` without `--pin-baseline` are refused too. The flag is deliberately *not* a bare `--force`: the flags sit on the shared evaluator set, and `_retry_refusal()`'s docstring (`cli/harness.py:191-196`) records that `--retry-of` intentionally has no `--force`, so an unqualified `--force` would read as applying to it.
  A standalone `pin-baseline` verb was rejected: the monotone check and the frozen lookup both need `BaselineConditions` (n, semantic prompt/model, subject model, timeout, host) and `input_hash`, which would mean re-declaring the evaluator flags and `runner_args`. *Why `skill` only*: `read_pin()` must key on something stable across mutations. `skill`'s `args.target` is a skill *name* and its content identity is the file's hash — a pin keyed on the name survives edits to the file. `prompt`'s target *is* the prompt text and `cmd`'s target *is* the command string (`cli/harness.py:782,806`), so a mutated candidate has a different target and can never find its pin; and `cmd`/`mcp` write `target_content_hash = ""` on every row (`:2446`, `:2574`), so there is no content hash to pin. The earlier draft's "`prompt`/`cmd`/`mcp` pin via `--baseline-of`" path was therefore unreachable-by-construction and is dropped.
  `skill` pins `_incumbent_content_hash()` of the target (HEAD blob, not the working file). **A pin is refused when the working file differs from HEAD** (`_hash_file(skill_path) != _incumbent_content_hash(skill_path)`): `--measure-baseline` keys its rows on the *working* file's hash (`cmd_skill` `:2257`/`:2307`), so a dirty target would make the measurement gate below fail as "unmeasured" and hand out the D8 procedure, which is wrong advice while the blob is still on disk. The refusal says "target is modified in the working tree; commit or `git checkout -- <path>` before pinning" and is checked before the measurement gate. Never automatic (contrast `EvaluateConfig.auto_promote`, whose rolling overwrite is the drift shape this issue guards against). **Every pin write, first or subsequent, is refused unless `baseline_for()` finds a full-n measurement of the content being pinned under the current input and conditions** (an unmeasured pin would make every later compare fail closed under AC5). A re-pin is additionally refused when (a) the active pin has no full-n measurement under the current conditions (the ≥ comparison is undefined; the refusal carries the D8 procedure for the active pin's content), (b) the new content's rate is below the active pin's, or (c) the new hash equals the active pin's (no-op). `--pin-force` overrides all of these and sets `forced: true` on the entry. Rule (b) deliberately compares **point rates**, not the D4 interval: the anchor must never move down, and at small n an interval test would let a noisier-but-equal candidate replace it. The cost is that at `n=3` (rates 0/.33/.67/1) an equal-quality re-pin can be refused by sampling noise; the refusal text says so and points at `--pin-force` and at re-pinning at a larger n.
  **Storage when no project root resolves**: `read_pin()` returns `None` when `resolve_ll_dir()` returns `None` (no pin ⇒ single-arm compare, D7); `write_pin()` never invents a root — `_run_pin_phase` refuses with exit 2 ("no project root (`.ll/`) found; run from inside the project") before any read.
  Storage is **one file per pin entry**, following `.ll/decisions.d/` (the only append-only JSON convention in the codebase; see the 2026-09-15 finding below): `.ll/harness-pins/skill--<target>/<stamp>-<uuid4>.json`, written with `atomic_write_json()`, where `<stamp>` is the compact UTC form `%Y%m%dT%H%M%SZ` (no colons — `_now_iso()`'s `HH:MM:SS` is kept verbatim as the JSON `pinned_at` field, but colons are not filename-safe on every platform). The active pin is the entry with the greatest `pinned_at` (ties broken by full filename, which makes same-second ties deterministic but uuid-ordered rather than write-ordered — acceptable, two pins in one second is not a real workflow). A single growing `pins: [...]` list was rejected because a committed file that every pin rewrites merge-conflicts across `ll-parallel` epic branches, whereas independent fragment files union cleanly. Entries are never deleted. The directory resolves from the **project root** via `resolve_ll_dir()` (`paths.py:45`; never `Path.cwd()`), committed like `.ll/decisions.d/` — `.gitignore` already un-ignores `/.ll/`, so no gitignore change is needed — not `.loops/` (per-machine).
- **D7 — Pin absent ⇒ single-arm behaviour unchanged.** No pin means today's one-delta report, byte-for-byte for the existing keys; `test_delta_json_payload` etc. keep passing. The dual shape is additive (`baseline.vs_incumbent`, `baseline.frozen`, `baseline.vs_pin`, `baseline.outcome`), never a rename of existing keys. `baseline.frozen` is an object with the same sub-shape as the existing `baseline` payload (`source`, `n`, `conditions`, `conditions_fp`, `head_sha`, `attempt_ids`, `notes`, `baseline_pass_rate`, `baseline_ci`) plus `pinned_head_sha`, `pinned_at`, `reason`, `forced`; the existing inline payload construction in `_report_samples()` (`:1502-1523`) is factored into a `_baseline_payload(shown) -> dict` helper used for both arms. The frozen arm **omits** `head_sha_differs` and the text-mode "(measured at a different HEAD)" note — its rows were measured at a different HEAD by construction, so the note would be noise; the text line prints `pinned_head_sha` instead. For parity with the incumbent arm, `baseline.frozen` also carries `delta` (candidate rate − pinned rate, `None` when the candidate is ungraded), and the text `Pinned:` line ends with `rate=<p> [lo, hi]` and the `Arms:` line reads `Arms: vs-incumbent=<v> (Δ<+d>) vs-pin=<v> (Δ<+d>) → <outcome>`.
  **`--baseline-of` on `skill` with a pin present**: the frozen arm still attaches. The pin is independent of how the incumbent arm was named — `--baseline-of` only swaps which `BaselineKey` the incumbent arm reads — so `cmd_skill`'s compare branch calls `read_pin()` on both the HEAD-resolved and the `--baseline-of` paths, and the same dual report results. Covered by a dedicated test (Step 5).
- **D8 — Measuring pinned content after HEAD has moved is a documented manual procedure.** `--measure-baseline` measures the file on disk; once the lineage commits past the pin, the pinned blob is no longer in the tree, and every conditions change (n, judge model, timeout, host) invalidates the cached frozen rows and re-triggers the AC5 refusal. The refusal message and `docs/guides/EVALUATION_GUIDE.md` spell out the exact steps: `git show <pinned_head_sha>:<target-path> > <target-path>` (the path is recorded on the pin), then `ll-harness skill <target> [same args] --measure-baseline` with `--samples` at least the n the next compare will use, then `git checkout -- <target-path>`. This works because after BUG-3479 the restored file's `_hash_file()` equals the pinned hash. Automating this (`--measure-pin`) is a follow-up.

### Signatures

- New `proportion_diff_ci(k1: int, n1: int, k2: int, n2: int, z: float = 1.96) -> tuple[float, float]` (`stats.py`, next to `wilson_ci()` at `:14`) — Newcombe score interval for `k1/n1 − k2/n2`; raises `ValueError` on `n1 <= 0` or `n2 <= 0` exactly as `wilson_ci` does (D4).
- `_compare_baseline_refusal(key: BaselineKey, conditions: BaselineConditions) -> str | None` — existing pre-run compare gate (`cli/harness.py:1889`), **unchanged**; still gates the incumbent arm.
- New `_frozen_baseline_refusal(pin: BaselinePin, key: BaselineKey, conditions: BaselineConditions) -> str | None` — same shape (pure, zero side effects, one `read_baseline()`), but its message is the D8 procedure with `pin.pinned_head_sha` and `pin.target_path` substituted and the `--samples` floor stated. A separate function because `_compare_baseline_refusal()`'s text ("run --measure-baseline on the unmutated subject first") is wrong advice for the frozen arm — the pinned blob is no longer on disk.
- `baseline_for(db_path: Path | str, *, runner: str, target: str, input_hash: str, target_content_hash: str, conditions: BaselineConditions) -> BaselineResult | None` (`history_reader/harness.py:330`) — **reused unchanged** for the frozen arm by passing the pinned hash (D3).
- New `read_pin(runner: str, target: str) -> BaselinePin | None` (list the entry directory, parse each fragment, return the one with the greatest `pinned_at`, filename as tiebreak; `None` when `resolve_ll_dir()` returns `None` or the directory is absent) / `write_pin(pin: BaselinePin) -> Path` (write one new `<stamp>-<uuid4>.json` fragment via `atomic_write_json()`, creating the directory on first write; never touches existing fragments; raises `FileNotFoundError` when `resolve_ll_dir()` returns `None`, which `_run_pin_phase` turns into the exit-2 refusal) — `cli/harness.py`. Both resolve `.ll/` from the project root via `resolve_ll_dir()` (D6).
- New `_pin_refusal(pin: BaselinePin, active: BaselinePin | None, key: BaselineKey, conditions: BaselineConditions, *, working_hash: str | None, force: bool) -> str | None` — the D6 gate, evaluated in order: `working_hash != pin.target_content_hash` → refusal (dirty target; not bypassed by `force`, since a pin of content that cannot be measured is never useful); no full-n measurement of the content being pinned → refusal; `active` present and `active.target_content_hash == pin.target_content_hash` → refusal (no-op); `active` present and no full-n measurement of the active content under current conditions → refusal carrying the D8 procedure for the *active* pin; `active` measured and new rate < active rate → refusal; `force` bypasses the latter four. Pure over at most two `read_baseline()` results.
- New `_arm_verdict(candidate: SampleTally, arm: SampleTally) -> str` and `_pair_outcome(vs_incumbent: str, vs_pin: str) -> str` — pure functions (D4/D5), unit-testable without a DB. `_arm_verdict` returns `inconclusive` when either `graded == 0`, else calls `proportion_diff_ci(candidate.passed, candidate.graded, arm.passed, arm.graded)`.
- `_run_compare_arm(...)` (`cli/harness.py:1907`) gains `frozen: BaselineResult | None = None` and `pin: BaselinePin | None = None`; `_report_samples(...)` (`:1455`) renders the extra fields when `delta.frozen` is set, via the new `_baseline_payload(shown: BaselineResult) -> dict[str, Any]` helper (D7), and appends the D4 drift-floor note when a pin is present and `n < 6`.
- New `_run_pin_phase(target: str, target_path: Path, key: BaselineKey, conditions: BaselineConditions, head_sha: str | None, args) -> int` — called from `cmd_skill` when `--pin-baseline` is set, before the measure/compare branches; exit 2 on refusal with zero DB writes and zero subject invocations.
- `_baseline_flag_refusal(...)` (`:1706`) gains the `--pin-baseline` rules (D6): refused on `runner != "skill"`, combined with `--measure-baseline`/`--compare-baseline`/`--retry-of`, with `n < 2`, and `--pin-force`/`--pin-reason` without `--pin-baseline`.

_Added by `/ll:refine-issue` — 2026-09-14 — based on codebase analysis:_

- `_run_compare_arm()`/`_run_baseline_phase()` (`cli/harness.py:1880`,`:1789`) confirmed scoped to one CLI invocation: the "baseline" arm is either just-run samples or previously-stored rows for the same content identity — no notion of a lineage of successive generations exists in either function; each call is stateless with respect to prior `--compare-baseline` invocations beyond what `baseline_for()` finds.
- `BaselineDelta` (`cli/harness.py:1585-1598`) is `candidate, baseline, delta, source, head_sha_differs` — `delta` is `None` (not a banded verdict) when the candidate has zero graded samples, and the CLI's exit code always comes from the candidate tally alone; `delta` is additive report content, never a pass/fail input today. A four-way outcome (beats both / incumbent-only / baseline-only / neither) as this section's Call Path proposes has no existing shape to extend — `BaselineDelta` reports one delta against one reference, not two.
- MR-2's `_has_baseline_reference()` (`fsm/validation/meta_rules.py:581-596`) is a hand-maintained field allowlist (`[ev.previous, ev.source, ev.reference]` plus `ev.target` if string) that recognizes which `EvaluateConfig` fields count as "a captured baseline value is referenced" — not dynamic; a new frozen-baseline field would need to be added to this list by hand to be recognized by the lint rule, distinct from adding the field itself.
- Existing fail-closed precedent directly reusable for a frozen-baseline refusal: `_compare_baseline_refusal()` (`cli/harness.py:1862-1878`) is a pre-run, zero-side-effect existence check (not staleness) that refuses with exit 2 before any subject invocation when no full-n baseline row set exists; ENH-3421's `reference` resolution is separately fail-closed on an unresolvable (but present) value, distinct from "value absent."
